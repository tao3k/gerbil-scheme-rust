#+TITLE: Completion-driven owner flow: architectural candidate and focused qualification
#+STARTUP: overview

* Decision and evidence boundary

Optimize the request topology rather than select more dispatcher threads. Native
Scheme remains Gerbil -> Gambit C -> O2 on fixed owner threads. Scheme retains
macros, arbitrary procedures, GC, exceptions, continuations, Actors and green
threads. Rust handles routed admission, owned results and instance lifecycle.
No Scheme operation moves into Tokio or Rayon; no SMP work is included.

The previous grouping candidate still allocates owner tasks per offered window.
Its Rayon path retains a parallel-submission barrier before caller collection.
The Python =tokio-pipeline= implementation already replenishes bounded work, but
still spawns a Tokio task per request and retains 128-request group boundaries.
The new driver must reuse the native API rather than build another evaluator or
move Scheme scheduling into Rust. Existing Python selections and defaults remain
unchanged; this candidate is an explicit Rust library API.

* Architectural change

=gerbil_scheme_python::owner_flow= is an optional, caller-polled driver over the
existing =AsyncInstanceTicket= interface. One future manages a routed invocation;
it creates no request or owner Tokio tasks, no worker thread and no Rayon
submission barrier. Native per-request channels remain unchanged. This removes
an executor scheduling layer without replacing the native queue or its close
fence. Normal hooks acquire no diagnostic clocks.

The driver groups inputs into owner-affine FIFO lanes, admits them in rotating
owner order and maintains an explicit finite in-flight credit limit. Ready
completions refill credits without waiting for all owners to finish a turn.
Soft per-owner quotas prefer balanced admission; otherwise idle credits can be
borrowed by owners with remaining work. At most the head native ticket of each
lane needs polling because that native owner's execution is serial. Ready
results enter original-index slots immediately; output ordering does not impose
a cross-owner observation barrier. Work per poll is bounded before yielding the
Rust future. This yield does not schedule or preempt Scheme green threads.

A single invocation can span more inputs than its credit limit. The driver's
credit is per invocation, not a global reservation against other callers. It
therefore does not fix the separately recorded competing-probe =QueueFull= case.
Native queue bounds, rejection and pool close still belong to the existing
admission API. No silent QueueFull retry or deadline extension is introduced.
Submission panic becomes that request's =TaskPanicked=; other accepted peers are
observed. Observation timeout or dropping the caller future never cancels Scheme;
callers retain responsibility for accepted-work and opaque-token retirement.

* Tokio and Rayon responsibilities

Tokio supplies async I/O and application orchestration. The short native-admission
path does not require a separately scheduled task for each request. The candidate
runs on the caller's =block_on= future; the two Tokio workers remain configured in
the matched experiment, but do not execute the driver or Scheme. This placement
is explicit, rather than advertised as faster two-worker parallel Scheme entry.

Rayon remains available for substantial independent Rust computation before or
after native requests. This workload contains no such computation: parallelizing
microsecond admission adds work distribution and a barrier. Compare existing
Rayon 2/4 directly with the explicit owner-flow strategy rather than introduce an
untested automatic mode switch or infer that Rayon is universally slow.

* Same-window diagnostic closure

windows and 65,536 request rows are correlated: each row's first eight spans sum
exactly to its native-completion offset; all ten sum to its collection offset;

Zero separate task-collection span in the driver follows from observing and
placing the result in one operation; it does not mean zero collection cost.
The observation span includes that work, and final vector materialization still
contributes to window recovery. Removing the stage is an architectural change,
not permission to omit its remaining costs from timing.

A retained negative driver window in the Rayon 4 comparison (CPU, block zero,
forward arm, window three) delivers at 25.038 ms. The critical request on owner
one completes at 23.464 ms; same-window recovery is 1.575 ms. Its admission
returns in 0.208 microseconds and its owner-wait lower bound is 23,346.375
microseconds; Scheme execution is 4.167 microseconds. Its four SDK collection
counts are all 84. This locates this critical request's delay before native entry,
not in its own Scheme/GC span. Earlier queued requests and OS descheduling still
contribute to that interval; unchanged counters on this request do not prove
that no other request collected or identify the OS cause. The Rayon 4 owner's
mean waiting regression above remains visible.

* Next architectural boundary

[[file:30.28-shared-owner-capacity-and-batch-fairness.org][30.28]] implements the next shared-capacity/backpressure stage and records its
explicit Scheme batch negatives. The remaining items below retain their original
planning context; they are not all completed by that later stage.

The reusable completion driver is the first implemented topology change, not a
claim that the complete concurrency architecture is finished. The next boundary
is shared owner capacity across concurrent callers, followed by application-level
resident/batched work and incremental result consumption:

1. Pool-owned capacity must account for every accepted request until native
   completion, including Scheme failure, Rust panic and observation timeout.
   Returning credit when a caller merely stops waiting would permit unbounded
   native backlog. Preserve the existing atomic close/admission fence and drain
   semantics. Reuse and extend existing lifecycle/model obligations if this
   protocol changes; the current model is not new-flow fairness acceptance.
2. Stateful work keeps its owner and per-session ordering contract. Stateless
   routing may use available owner capacity only after independence validation;
   moving a Scheme object, closure or continuation between VMs remains forbidden.
   Fairness must include concurrent callers and short probes, not just one burst.
3. Reuse owner-resident typed inputs where identity/mutation contracts permit.
   Expose explicit native Scheme batch/service operations to reduce repeated FFI
   and type construction. Do not silently fuse arbitrary Scheme calls: exceptions,
   dynamic bindings and continuation boundaries require their original semantics.
4. Keep the completion consumer incremental across its invocation; couple
   admission to both native capacity and bounded unconsumed results. Tokio
   orchestrates async flow; Rayon handles substantial independent Rust computation.
   Scheme retains its Actor and green-thread scheduler inside each owner.

These steps need protocol evidence and focused same-load comparisons before
production admission. The present driver does not reserve global credits, remove
Python's outer 128-request grouping or change the default Python API. It does not
solve the historical mixed competing-probe QueueFull case or certify industrial
readiness. The next experiment must target the demonstrated shared-capacity and
queueing boundary, rather than repeat the full thread-count matrix.
