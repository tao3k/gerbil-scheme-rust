* Actual protocol candidate

ABI v4 adds =configure_scheme_service_wake_on(owner, SchemeServiceWake::NativePort)=.
Its fixed-owner ticket confirms actual Scheme configuration. The default remains
=Watcher=. Mode changes require drained Scheme jobs and cooperative leases.
Switching to the candidate wakes and joins the old watcher before the root
Scheme thread reads its port; switching back drains notifications and creates
one watcher. A native receipt precedes the Rust-side mode flag.

Scheme directly waits on the existing native input port. Rust publication and
Scheme completion both notify that port through nonblocking writes. Full-pipe
notification is already readable; IO failure is not reported as successful work.
The bounded drain and ready-queue check preserve level-triggered work visibility.
Dynamic-wind restores port timeout settings after timeout, exception or return.
Gambit still schedules green threads, Actors, native IO, timers and continuations.
Rust does not choose which Scheme thread executes or move a live Actor.

The candidate also avoids an empty native completion-collection call when no
host service job remains. This is a coupled protocol candidate: measurements do
not separately attribute gains to reader transfer or empty-call removal. Feed,
class routing, work/slot budgets, result layout and application algorithm remain
the same. The watcher and disabled cooperation remain production defaults.

* Follow-up on the remaining tail

One further same-configuration observed pair completed all 40 samples and native
cleanup. It is diagnostic evidence, not a third unobserved speedup result.
In candidate slowest-one-percent observations, publication-to-dequeue occupied
91.4% of CPU-load actual latency and 63.2% of mixed-load actual latency. Native
select overlapped 54.7% and 25.0%, respectively. Owner phase overlap on CPU was
wait 55.6%, advance 26.1%, submit 7.4%, retirement 2.2%; on mixed load it was
wait 31.2%, submit 31.9%, advance 0.1%. Analyzed tails had no lost history.

A candidate CPU probe waited about 131.8 ms before dequeue inside a native wait
whose full enclosing CPU was only 0.058 ms and GC wall was zero; the corresponding
select returned descriptor-ready. Another advance phase took 101.845-ms wall
with 0.141-ms CPU and no GC. A mixed probe intersected 60.633 ms of submit, with
0.750-ms enclosing CPU and 59.990-ms GC wall. A different written notification
completed its producer wake in about two microseconds, but the native select
requesting 0.936 ms returned approximately 10.306 ms after publication. Neither
case supports blaming type arithmetic or merely increasing Rust worker count.
Coalesced notifications do not prove which producer wrote the outstanding byte.

The direct port removes a Scheme notification handoff and improves observed
throughput, but cannot establish a p99 bound across OS/native blocking, VM GC
and later Scheme execution. These observations do not prove a lost wake or
identify a particular kernel scheduler policy. No speculative GC/SMP patch or
unmeasured routing change is promoted. Subsequent optimization must preserve
this paired evidence and distinguish runnable-owner resumption from native
collector wall time and post-construction service waiting.

* Follow-up clock-scope correction

[[file:30.40-independent-notification-and-mixed-tail.org][30.40]] verifies that SDK GC CPU uses process time, while owner CPU uses a
thread clock. GC CPU is not isolated collector CPU and must not be subtracted
from GC wall or summed across owners. The original observations above remain
unchanged; the new report retains the process/owner distinction and all negatives.
