* Root-cause boundaries

The benchmark now has ten correlated stages: input copying/entry, ready-to-worker,
validation, admission plus owner wait, native type construction, Scheme including
GC, native projection, root retirement, result observation and task collection.
Synchronous/asynchronous profiled batch APIs share one native execution body.
Normal batch calls do not acquire phase clocks. Diagnostics are explicitly marked
and run separately from unprofiled throughput A/B. Admission return supplies a
separate queue-wait lower bound because native work can start before submission
returns. Native SDK GC counters are preserved separately from wall-clock spans.

The dominant observed waits in this short workload are upstream/downstream of
brief native execution. More Rust workers do not increase a fixed owner's native
service capacity. The common admission mutex has measurable contention but its
return span is much smaller than queued waiting in this cohort. It continues to
fence close against admission; moving channel sends outside that fence would
require a protocol change and is not this optimization.

Tokio originally spawns one Rust task per native request and collects handles in
input order. Rayon parallel submission has a completion barrier before caller-side
ticket waits. These mechanisms explain what the observed stages include; they do
not prove that every historical extreme came from the same mechanism. Native
construction and GC still contribute, especially for larger batches. Mixed inputs
explicitly contain Scheme waits; they are not a CPU-only scheduler measurement.

* Minimal optional Rust candidate

The shared implementation is
=gerbil_scheme_python::owner_dispatch= behind =owner-dispatch=. It has no Python
runtime dependency. The existing =instance-backend= feature names the same native
runtime dependencies through that feature. Existing Python dispatcher selections
and default execution paths do not call the new helpers.

=tokio_owner_window= uses one Rust task per distinct owner, admits that owner's
requests in order, observes every accepted ticket, and collects completed groups
with =JoinSet=. Original result positions are restored. =rayon_owner_submit=
parallelizes owner groups and returns original-position native tickets for caller
waiting. Native request count, batch shape, validation, queue capacity, close
fencing, root lifetime, timeout and complete Scheme work remain unchanged. A
submission panic becomes one request error while accepted peers still drain.

At a 128-order window with one-item native batches and four owners, Tokio task
count changes from 128 to four. With batch 32 it is already four in the control;
that case does not receive a task-count reduction. Rayon work-item grouping is
not a claim that its internal task count equals the number of input items. The
candidate reduces dispatch granularity but introduces grouping/restoration and
per-owner collection barriers. The negative results below are expected to matter
for admission. No automatic heuristic or default promotion is made.

Rust callers must poll the async helper inside a Tokio runtime with its time driver
enabled and drain its future/results. It does not cancel accepted Scheme execution
or take over Scheme-root ownership. Retained-token cleanup remains with the owner
API/caller. Complete generic cancellation/unload guarantees are not inferred from
numeric-result qualification.

* Correct recovery measurements and preserved extreme

Native response p99 and window-delivery p99 have different populations. Their
difference is not result-recovery time. The final benchmark records each window's
caller return minus its own last native completion, including raw paired window
arrays and =window_recovery_p99_ns=. This is the remaining Rust delivery/collection
wall span after all native work finishes; it still includes OS scheduling.

An earlier exploratory four-owner CPU single-item Tokio-2 grouped run has native
response p99 26.944 ms and window-delivery p99 108.844 ms. Its maximum native
completion is already 108.798 ms. Thus an isolated native straggler dominates that
window; the two p99 values cannot diagnose an 81.9 ms collection cost. Those old
unprofiled records cannot split that exact straggler further into pre-dispatch,
owner waiting, GC or execution. Later diagnostic samples do not recreate its
exact magnitude, so no unique historical root cause is fabricated. The original
negative and this limit remain recorded.

* Admission conclusions and remaining boundaries

Four-owner CPU single-item Tokio-4 grouped throughput improves 18.60% / 16.04%
in F1/F2 (82,826 -> 98,231 / 84,933 -> 98,553 orders/s). Native p99 changes
11.848 -> 2.551 ms / 17.245 -> 2.798 ms. Recovery does not improve universally:
F1 grows 0.100 -> 0.272 ms; F2 falls 0.414 -> 0.145 ms. These are specific
observations on a loaded host, not a fixed improvement guarantee or a complete
fairness win. Tokio-2 F1 has a native p99 regression 4.286 -> 58.194 ms, while
F2 loses throughput. Rayon-2 F2 loses rate and has native p99 1.978 -> 91.831 ms;
Rayon-4 loses rate in both final cohorts. Mixed-load and larger-batch negatives
remain in the complete tables. Direct A/A and cross-cohort variation bound
confidence. Earlier pre-policy cohorts with 9.94% / 19.04% Tokio-4 CPU gains
retain their original captures and are not merged into the final source figures.

Owner progress measures the least completed-order count when the first owner
finishes its full window share. Single-owner 128 is trivial; at batch 32, zero
can mean another owner has not returned its first batch, not no Scheme progress.
Actor peer minima and full per-owner p99 vectors remain separate in the captures.
Neither metric proves sustained fairness or stateful-session ordering across
independent callers. The candidate does not satisfy a general throughput/p99/
fairness promotion gate. Existing production defaults therefore remain unchanged.

The earlier competing-probe QueueFull failure is not repaired by this probe-free
matrix. Python/GIL costs, resident input placement, long-term allocator behavior,
full deployment packaging and arbitrary extension unloading keep their separate
qualification. There is no new model, SDK patch, SMP change or Bash script.
