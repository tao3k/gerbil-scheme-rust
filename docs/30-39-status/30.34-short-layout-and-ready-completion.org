* Two application layouts with one complete Scheme runtime

The previous short probe is a one-element native batch. It constructs a batch
envelope, enters an Actor mailbox/barrier and creates/joins a coordinator for
one order. The new application path uses a disjoint explicit native tag/version
=[77,1]= plus one numeric order and returns one numeric result. Scheme executes
the same =orders-handler/rank= order-line algorithm directly on a persistent
Scheme service worker. It bypasses the batch coordinator, not Scheme execution.
No classification depends on guessed runtime duration or input-length heuristics.

The short entry accepts at most four order lines and rejects larger work. Its
fixture is stateless; stateful sessions and continuations continue to use the
existing stable Scheme Actor lane contract. The original batch quantum range,
full service payloads, Actors, green threads, exceptions, continuations, GC,
evaluator and native compile chain remain available. The application tag has two
numeric header fields so it cannot collide with any valid one-field batch quantum.

| Path | Input/result | Scheme execution | Completion protection |
|------+--------------+------------------+-----------------------|
| Explicit short | Tagged native order / numeric result | Existing order algorithm on service worker | Same internal strong job graph, take/root/project and retained native capacity |
| Batch | Existing native batch envelope / result vector | Persistent Actor workers and existing coordinator barrier | Same service job and native capacity protocol |

Both use the actual =SchemeServiceRequest= interface and
=submit_scheme_service_backpressured_on=. The specialized application schema is
not a second generic codec or a VM-less Rust implementation. Scheme selects its
workers; Rust controls only host admission, native conversion/projection and
cross-instance dispatch. Shared Scheme GC and non-yielding CPU computation still
couple the two paths. A different layout alone is not latency isolation.

* Completion head-of-line blocking

The existing client flow polls only =lane.active.front_mut()=. If the first
Scheme job waits while later jobs finish, the completed peers cannot be observed
or return the client's invocation window credits. Native slot/work credits have
already retired independently; the stuck credits are client flow credits.
This is a concrete completion-collection dependency, not evidence of a slow GC.

The explicit =owner_flow_ready_backpressured= API polls pending receivers and
collects one ready result per owner per pass. Original result positions and
per-owner admission order remain unchanged. Later completion can refill without
waiting for the earliest job. Accepted work remains live through timeout/drop;
native capacity still returns only after projection/root retirement. Existing
flow APIs, backend selection and defaults are unchanged.

The native regression holds the first Scheme batch on a latch, permits only two
client in-flight tickets, and requires a completed peer to refill a third request
before releasing that latch. It then checks outputs in their original positions.
This independently validates the collection fix; it is not a timing benchmark.

alternate AB/BA. The control retains batch probes and FIFO completion observation;
the candidate combines native short probes with completion-ready observation.
This measures the combined pipeline, not independent per-component speedups.

Both arms impose the same explicit client bulk cap of three callbacks per owner,
held through projection. This leaves capacity for the one probe producer in this
workload. Native credits and root retirement remain unchanged. This is not a
pool-wide class quota against arbitrary independent producers. The client cap
and compared paths differ from the earlier synchronous/service experiment;
its results must not be spliced into the older baseline.

Throughput uses median native bulk completion time. Short actual latency starts
before admission; scheduled latency also retains delayed arrivals from the serial
probe generator. Native short construction, pending-before-projection and
projection spans are separate. Pending includes Scheme work, waits and owner
interleaving; it does not isolate CPU execution. Per-owner finish maxima and
progress, Actor peer minima, cleanup and all negative observations remain recorded.

* Model and native boundary

The existing lifecycle model is reused unchanged: its admitted jobs already
permit arbitrary completion order and retain native roots/credits until retirement.
This client completion observation and application layout introduce no new native
ownership transition. The prior finite model pass is historical safety evidence;
it does not replace current native GC, short-contract, latch/refill or drain tests.
No second model or new unverified Scheme scheduler is introduced.

The native test includes short requests while long handlers remain latched,
forced GC, oversized short rejection, the completion-ready refill control,
existing same-Actor multishot continuations and errors, backpressure and full close.
The earlier retained test failure supplied a 48-line order to the new four-line
entry. The fixture now uses the same four-line corpus as the benchmark; the
contract is not weakened. That failed run remains a failure, not a clean drain
receipt. Final gates and directed measurements follow below.

The combined candidate loses approximately 0.5% / 19% mixed throughput. The
layout-only candidate changes mixed throughput -7% / +7%, and worsens actual
short p99 in both captures. These are not admitted mixed-throughput improvements.
Short pending spans decrease, but the work before owner construction dominates
the slowest probes: in the layout-only mixed candidate, 98% / 87% of summed
latency among the slowest one percent is before construction. This is derived
per observation from actual latency minus native service span, not subtraction
of unrelated percentiles. It includes admission, host preparation, dispatch,
owner queueing/wake and OS scheduling; it does not isolate those components.

The concrete conclusion is that shorter native payload/Actor overhead does not
solve route selection or pre-construction delay. Completion-ready behavior is
validated functionally by the latch oracle, but the combined performance path
remains explicit and unpromoted. The subsequent actual classified route API and
its separate negative evidence are recorded in
[[file:30.35-class-specific-native-service-routing.org][30.35 Class-specific native service routing]].
