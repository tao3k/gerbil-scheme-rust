#+title: Native Expander Startup and Concurrent Dispatch Benchmark Matrix
#+date: 2026-10-19

* Admission order

First close the cold expander and bounded owner-destruction gates through the
installed Python API. Native Scheme types, macros, continuations, exceptions,
GC and internal actor/green-thread scheduling must remain available. Rust may
only distribute requests across fixed native VM owners. No SMP work is included.
All existing five-second native gates remain unchanged. A timeout remains a
failure even if a later warm request succeeds.

* Concrete startup diagnosis

The canonical native executable completes expander startup and evaluation with
SDK module files. With byte-identical wheel copies it exceeds five seconds.
A standalone inode-preserving control succeeds. SDK-to-copy content hashes,
valid code signatures and native linker identities were checked.

A fresh bundle's raw dlopen took approximately 400ms. Ordinary Darwin signature
registration took less than 1ms; Library Validation took approximately 252ms.
After those normal checks, same-process dlopen took approximately 0.5ms. No
validation check, quarantine flag, entitlement or system protection was disabled.

Parallel prevalidation is rejected: 32 threads completed only 16 of 172 modules
inside five seconds. The hardlink-alias hypothesis was also rejected: the
current closure had no duplicate native bundle content. APFS clones and local
ad-hoc resigning did not close the gate. These negatives are retained.

The successful native control coalesced the 35 dynamically observed bootstrap
parts into one physical Gambit bundle. Each logical module retained its own
compiler-generated linker export and lazy initialization. Logical paths were
hardlinks within that one standalone namespace. Expander startup and evaluation
then completed inside five seconds. This is ordinary Scheme -> Gambit C ->
native compilation, not Scheme-to-Rust lowering or an SDK/SMP rebuild.

Production integration consumes the official expander's entire declared native
closure, partitions only when linker basenames collide, reuses the existing
native compiler identity cache, and ships explicit logical-to-physical mappings.
Every VM copies its own physical bundles; only aliases within one VM share an
inode. This does not permit shared mutable module state across owners.
Installed four-VM verification passed on wheel SHA256
=b0ec6b97ecf5a5f82587509fba08741ca2b0dc50f8779fd9f13ee6a0330cddb6=.
The official closure includes modules that export public C functions as well as
the Gambit linker. Those modules remain separate. A grouped image must expose
exactly its original set of Gambit linker symbols; extra or missing exports fail
the build. =-module-ref= and =-linker-name= preserve the original Gambit identities.
Logical module initialization is still lazy and owned by the ordinary loader.

All four native first DSL calls completed inside five seconds: 807.25, 479.26,
493.14 and 478.44ms. Runtime-defined hygienic macros, interpreted closures held
across GC, Scheme exceptions/recovery and clean destruction passed. The installed
suite passed 10 tests in 5.417s, with no skips. Closure inventory/publication tests
passed 27 cases, including escaping/missing/shadowed aliases, private metadata
preservation and grouped-native tamper rejection. Strict instance-runtime Clippy
passed. This is local capability evidence for these cases, not universal Scheme
conformance, portability or remote exact-head CI.

After full expansion, shutdown joined all four owners, reported zero roots and
removed the private directory. No timeout was widened and no pending owner was
force-terminated or falsely reported clean. The prior timeout receipts remain
unchanged in 30.10; the new source/artifact receipts are separate.

The provisional grouped dynamic modules use =-O0=. The original installed SDK,
main runtime archive and statically compiled ledger/Actor workload retain their
existing compiler settings. Phase compilation with =-O1= and a trial of the
existing GCC policy reached the 120-second build gate. The failed cold builds
remain failed; cache-assisted builds are not counted as cold build passes. One
=-O0= native build completed in 95s, and the later export-contract build completed
in 39.06s using validated compiler-cache hits. Macro/expander throughput at =-O0=
requires its own matched comparison before optimal performance can be claimed.
See [[https://gambitscheme.org/4.9.8/manual/][the Gambit 4.9.8 compiler documentation]] for the native module/linker controls.

* First measured configuration: preserve all four modes

The first four-way comparison uses four fixed Scheme VM owners, two Tokio
workers, two explicitly bounded Rayon workers, 128 requests/cohort, 32 Actor
items/request, 48 integer line calculations/item, quantum 1 and cooperative
1ms waits on selected items. Each mode has a warmup, then four measured cohorts
in balanced reversed/rotated orders. All modes run on the same live VM states.
Native replies, per-item totals, rank permutations and worker assignments are
checked. Raw per-request values are retained, not averages of round p99s.

| Mode | Actor items/s median | Pooled native-ready p99 | Rank displacement p99 |
|------+----------------------+-------------------------+-----------------------|
| Direct | 11,795.07 | 248.96ms | 9 |
| Tokio | 11,375.88 | 261.75ms | 9 |
| Rayon admission | 11,021.88 | 246.13ms | 9 |
| Rayon blocking | 7,713.30 | 409.28ms | 9 |

Each Actor worker completed 1,024 items/cohort; Jain worker fairness was 1.0.
The retained =ready_ns= clock covers admission-window start through native
result-ready. It excludes Python input reading and result projection and is
not an end-to-end per-request Python p99. Window waits now consume one common
five-second budget in every mode. Rayon blocking has fewer in-flight jobs at
small worker counts and is intentionally a distinct control.

No relevant compiler processes were captured immediately before/after the run,
but strict checks overlapped this period and load was not recorded per round.
The host was not isolated; these are observational results, not an admitted
optimal configuration or stable speedup. Negative results remain. No default
worker count or backend was changed in response to this single configuration.

The new package also completed the existing 8,320-call reuse control: native
GC live bytes stayed 517,312 per VM with zero roots, malloc live stayed
29,491,472 bytes across checkpoints and fell to 2,879,392 after close. RSS
remained approximately 92MiB after shutdown; mappings/allocator reservation
are still distinct from live-root retention. This run does not assert immediate
OS page return or indefinite leak freedom.

* Measurement and selection rules

- Keep the same live VM states in paired comparisons. Initialize and warm both
  arms before balanced ABBA/Latin-square orders. Use a fresh process per topology
  cell so intentionally retained image mappings do not pollute later cells.
- Report startup separately. Never count cached module preparation as cold open.
- Record offered arrival, enqueue, owner start, native construction, Scheme
  service, GC, native-ready, response delivery and Python projection. A cohort
  native-ready p99 is not end-to-end Python request p99.
- Include queue/admission waiting in latency, including rejected, timed-out and
  unfinished work. Avoid coordinated omission and averages of per-round p99s.
- Report throughput, pooled p50/p95/p99, validated sample count and uncertainty;
  add p99.9 only with sufficient samples. Preserve every raw round and outlier.
- Record per-owner and per-Actor completions, Jain fairness, maximum completion
  gap and oldest-request age. A throughput winner may still lose the fairness
  or p99 budget; no single maximum is optimal for all load classes.
- Track CPU time, OS thread count/context switches, native roots, post-GC live
  bytes, malloc live/reserved bytes, file descriptors, mapped images and current
  RSS. Reserved/mapped memory is not automatically a live-object leak.
- Performance admission requires a quiet host with recorded compiler/host-load
  observations. Do not stop unrelated acceptance work to obtain a clean sample.
  Keep contaminated runs and label them; do not select favorable reruns.
- Keep exact source, SDK, dependency, binary and wheel identities. No numerical
  optimum or speedup is admitted until the full capability gate and matched
  workload checks pass on the measured artifact.
