#+TITLE: Selective Wake and Nonexclusive Short Claim
#+DATE: 2026-10-22

* Decision from existing evidence

The predecessor's final pair improved mixed throughput and short p99 but worsened
CPU maximum owner finish spread by 34.55%. CPU short placement was
=[336,141,99,64]= across 640 probes. The initial mixed regression remains in
[[file:30.53-shared-capacity-and-late-owner-binding.org][the preceding report]] with its own source identity. These observations identify
coordination questions; they do not establish that broadcast caused all of the
finish-spread regression or that equal owner counts maximize throughput.

Fixed-order broadcast wakes every destination for one queued short request.
Every running owner then races for the same queue. Rotating broadcast order alone
would retain the fanout; hard assignment to a sleeping owner would introduce
head-of-line waiting for its GC/OS scheduling. Neither addresses the ownership
boundary adequately. The new explicit policy separates notification duty from
payload ownership and keeps running-owner claims nonexclusive.

* Protocol and type boundaries

=SchemeShortWake::Broadcast= remains the default. A configured short facility
can opt into =Selective= through =configure_wake= while its native budgets and
pending admission are idle. =wake_policy= reads the actual host policy. A single
transition broadcast refreshes owners still sleeping under the previous policy;
this is outside measured work and is not the steady-state algorithm.

| State / event | Protocol |
|---------------+----------|
| Owner about to wait | Clear wake, recheck inbox and claim visible work; register under the queue lock only after a failed claim |
| Queued payload / returned capacity | Select the oldest registered owners with usable declared capacity; keep at most one logical duty per owner and issue no more new duties than queued inputs lacking duties |
| Notification | Remove selected owners from the waiting list; notify their weak wake handles after unlocking |
| Owner resumes | Remove its registration and duty before attempting a claim |
| Owner claims | Reserve real short/work/slot credits and use the original admission-plus-queue fence; only now commit the owner |
| Ordinary inbox interrupts a wait | Withdraw registration/duty and relay notification before entering arbitrary application work |
| Target fails or closes | Remove its registration/duty and notify another eligible waiter; close the facility if no targets remain |
| Cancellation / pre-claim timeout | Remove only that Rust input and pending slot; clear obsolete duties when the queue becomes empty |
| Accepted timeout / close | Keep native roots, fixed owner and credits through Scheme completion/projection; close wakes pending-capacity callers and drains unassigned inputs |

Capacity is an availability observation, not a reservation or predicted duration.
An already-running owner can claim a payload even when a peer has been notified.
A notification therefore cannot carry a Scheme value, reserve a head request or
change Actor affinity. Failed speculative acquisition does not publish a retry
event; genuine capacity return does. No timer, busy polling thread, hard wall-clock
Scheme budget or new Rust executor is introduced.

Registration, selection, withdrawal and queue publication share the existing
queue mutex. Final claim retains the admission fence and capacity identity check.
User destruction, result sends, permit returns and pipe notifications remain
outside locks. Owner failure independently closes the source, so publication's
under-queue closed check from the predecessor remains required.

Ports cache an immutable destination index established during configuration.
Actual owner IDs remain separate and are checked at claim; capacity identities
stay frozen until shutdown. This removes repeated linear destination searches
without introducing a shared mutable owner map or weakening close ownership.

* What fairness means here

FIFO ordering applies to eligible wait registrations, preserving skipped waiters'
relative order. It does not force equal counts across busy or differently paced
VMs. Opportunistic claim remains possible to preserve progress, so a fast running
owner can still take more requests. Logical wake duties are bounded; physical
notifications already in flight can become stale after cancellation or a peer
claim. Owners recheck live queue state rather than trusting those bytes.

The native wait registration means an owner is entering Scheme's service wait;
it is not proof that the OS thread is asleep or immediately runnable. Selective
notification alone cannot guarantee a runnable-time bound for a paused target.
The native workload must demonstrate whether reduced fanout outweighs registration
and relay costs. Scheme continues to own Actors, green threads, GC, continuations,
exceptions and native computation. Rust handles cross-instance admission only.

* Reused model and executable controls

The existing lifecycle model gains a waiting-owner list and a set of notification
duties. Existing pool staging, native capacity, committed owner, root and drain
transitions are reused. =selectiveShortStep= joins the original aggregate CI gate.
Scenarios exercise notification without binding, active-peer claim, interrupted
wait relay, publication before registration, cancellation and accepted timeout /
close drain. Existing owner-migration and premature-root-release mutations remain.
Finite safety checks do not prove OS liveness, performance or an equal-count bound.

Real-pipe controls check single-request fanout, bursts, capacity return, failure
relay and rejected dead-owner registration. The native four-VM fixture runs both
policies, concurrent typed short submissions, admission cancellation/expiry,
accepted observation timeout and queued/capacity-waiter close with root-balanced
cleanup. Policy changes reject outstanding work and closed admission.

The protocol clearly reduces placement concentration in these captures, while
CPU finish spread and CPU short p99 remain unresolved. Mixed throughput is
essentially unchanged. There is no default or general-performance promotion;
all earlier regressions remain admitted negative evidence for their own snapshots.
Equalizing short placement does not equalize completion of an independently
scheduled bulk pipeline, per-VM allocation/GC or OS execution. The existing
sharing model permits those delays; notification fairness cannot prove them away.

The historical =probe_actual_p99_ns= field uses native projection-completion
timestamps, not the time when a Tokio caller resumes. Admission can therefore
exceed native-completion latency when the caller resumes after native completion.
The final CPU scheduled-probe p99 was 15.404042 ms / 38.393833 ms (control /
candidate); mixed was 3.224667 ms / 1.894917 ms. Those observations remain visible,
not relabeled as native execution time or proof of OS/GC attribution. Both captures
ran on the shared local host with other work untouched and no profiler. No quiet-
host or stable tail improvement is claimed.

The next design obligation is bulk supply/retirement fairness at owner boundaries,
with native execution/GC variability kept separate from wake fairness. Per-owner
waiting flags, shared queue coordination, placement acknowledgement and Scheme
service progress are distinct costs. These results do not justify blindly replacing
Arc, changing default budgets, hard owner binding or further unchanged timing runs.
