#+title: Executed-work budgets across short routing and Scheme completion
#+startup: overview

* Status and acceptance boundary

This is an uncommitted ABI 14 experiment. Defaults remain unchanged. No
performance acceptance is claimed from native correctness or finite-model
success. Historical negative captures and unattributed watchdog failures remain
open. Rust distributes across fixed owners; Scheme retains its complete runtime,
actors, green threads, exceptions, continuations and GC.

* Three independent authorities

| Quantity | Bulk batch | Short request | Lifetime / authority |
|----------+------------+---------------+----------------------|
| Retained admission work | 8 items | 1 item | Existing Rust reservation through independent result retirement |
| Executed application work | 8 x 48 line records | 4 line records | Scheme handler reports completed safe spans |
| Item completion progress | 8 item IDs | 1 item ID | Existing idempotent Scheme ledger; no early credit refund |

A record is a workload-specific logical cost, not CPU cycles or elapsed time.
These rows are not interchangeable. In particular, changing admission charges to
384 would break the existing work limit of 32 and would not implement a CPU
budget. Results still independently release their own roots and capacity.

* Protocol

- An idle owner opts in through =configure_scheme_service_work_on(owner, 4)=.
  Zero disables the policy and remains the default. Positive work budgets require
  existing cooperative class arbitration; disabling that arbitration first is
  rejected. Selecting any completion policy resets the work experiment.
- Scheme application handlers bind =gerbil-rs-service-work-checkpoint= once.
  A completed safe span reports its logical cost, at most the configured bound.
  The order workload uses four-record spans; short and bulk use the same record
  computation and native types. Arbitrary handlers need not opt in and are not
  preempted or restricted by Rust.
- Short submission registers a dispatch obligation before worker publication;
  actual Scheme worker start settles it. Queued opposite-class lease requests
  remain in the existing Scheme budget queues. Start does not mean completion.
- At a work boundary, a pending short dispatch, an opposite-class waiter, or a
  new short-result ready generation requires an execution opportunity. The
  current lease is suspended using the existing continuation-safe dynamic extent,
  Scheme yields once, then reacquires through the existing class arbiter.
- Without these obligations, a checkpoint updates bounded fuel and work counts;
  it takes no mutex, allocates no queue entry and does not yield. The original
  Actor quantum and service policies are unchanged in both A/B arms.
- The optional =more-work?= checkpoint argument is false at the terminal span.
  That span is still charged, but the already computed result proceeds directly
  to the existing handler release/completion path instead of yielding first.
- A ready generation is offered once, rather than yielding repeatedly while a
  retained result remains queued. Existing short-first harvest, completion token,
  per-result projection, root release and capacity retirement remain authoritative.
  The offer is a scheduling opportunity, not proof that the host already retired
  the result. Once the last short-ready ID is harvested, its generation is
  settled because the host now owns its completion token. This does not release
  its root or capacity early. A later uncontended bulk must not yield for that
  already harvested generation. No start acknowledgement writes an unactionable
  native wake byte.

The executed-work counters count reported completed spans, including spans
replayed by continuations. An exception inside a span can end it before a report;
these counters are not an exact count of every instruction or partial failed
span. A checkpoint captured by a retained continuation becomes inert after its work
policy is disabled or replaced, and cannot charge a replacement policy.
The item ledger independently prevents continuation reentry from reporting
one item twice. Work counters do not release capacity or erase Scheme roots.

* Bounds and limitations

The cooperative bound applies at application-declared safe spans. It is not a
wall-clock deadline and cannot preempt arbitrary Scheme code, GC, OS descheduling
or type construction outside those spans. The single-owner Runtime model keeps
GC and OS unavailability separate. Its four-record abstract compute transition
refines existing item execution without changing item admission or custody.
Neither route separation nor these checkpoints alone explains historical
millisecond outliers; no same-spike OS/GC attribution is available.

* Executable verification

Native qualification exercises the public API, eight 48-record orders versus
four-record short work, no extra handoff without competition, malformed Scheme
input, recovery, deterministic class contention, exception unwind and continuation
reentry. Existing lifecycle qualification retains full types, native roots,
GC/multishot continuations and independent close/cleanup gates.

The existing =service_sharing= Runtime model is refined, not replaced. It covers
partial executed spans without item completion, a competing short execution and
independent retirement, continuous uncontended bulk execution, cancellation/close,
and a required counterexample when a contended work boundary is bypassed.

* Implementation cost and final gates

The first implementation updated global work totals and capped fuel at every
checkpoint and checked a modulo boundary for each line. The final implementation
uses four-record span loops and accumulates executed work in the owning lease.
Release/suspension commits that lease's total before changing its owner; the
native observation includes any unsettled count. Exception/nonlocal exits and
continuation reentry use the existing dynamic extent. Admission reservations,
completed item identities, class rules and result/root retirement are unchanged.
The Runtime model's exhausted/not-exhausted work state abstracts this accounting
representation; the logical protocol/model source did not change for this
amortization. Native exact-count and grant/suspension conservation gates validate
the concrete implementation; this is not a machine-checked compiler refinement.

* Decision and next architectural boundary

Performance acceptance FAILED. No new commit, staging or push to PR #18. Defaults
remain unchanged. Mixed short-tail improvement does not compensate for systematic
CPU throughput loss and bulk-tail negatives. The incremental comparison also uses
the previously uncommitted joint-dispatch protocol in both arms; even a favorable
increment alone would not authorize publishing the complete patch stack without
an accepted-baseline comparison.

The three cost/custody contracts are implemented and tested, but preserving CPU
throughput with this checkpoint representation remains unresolved. Further work
should remove the fixed cost of the uncontended path through a Scheme-owned
execution plan or compiler specialization, rather than collecting more unchanged
samples or tuning class thresholds. Any run-to-completion fast path must explicitly
state the maximum already-started nonpreemptible cost: it cannot silently promise
four-record handoff for new arrivals while executing an unchecked 48-record body.
That bound and continuation reentry must be part of the cost/type/model contract
before such a path is implemented. Full Scheme execution remains authoritative.
