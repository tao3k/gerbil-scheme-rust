#+TITLE: Bounded queue receipt and native result progress
#+STARTUP: overview

* Protocol gap and actual API

The previous pooled-short API waits for two owner-to-client events: placement
acknowledgement and then the native result. The intermediate acknowledgement
can resume the Tokio caller before it begins polling the result receiver. Two
observable events do not necessarily mean two actual scheduler resumptions: a
receiver can already be ready when first polled.
That dependency is required when a caller needs placement immediately, but not
when it only needs the final typed value. Owner execution and completion may
advance while the client is still waiting to resume from placement.

The explicit =SchemeShortPool::submit_queued= path acknowledges publication into
the existing bounded Rust queue. It returns =QueuedSchemeTicket= around the existing final result receiver;
it does not return or promise a selected owner. Only a running native owner
claims the payload and acquires active/request/work credits. It then executes
the complete Scheme VM using the existing service protocol. There is no extra
queue, coordinator task, poll loop, execution lease or Rust-side Scheme runtime.
The original =submit= placement contract remains available and unchanged.

Only the queued result ticket carries the existing pending-input cancellation
guard. Ordinary =AsyncInstanceTicket= retains its original layout and path.
Dropping an unclaimed ticket removes its Rust payload and returns its pending
slot, with no Scheme root or native credit to release. After actual claim, the
guard can no longer find/retract the input; caller timeout/drop cannot return
native credit or abandon Scheme roots early. Both =wait_completed= and
=wait_observed= retain that guard for their whole observation lifetime.
Close drains queued inputs through the same result channel without requiring a
placement receiver. The original queue deadline is checked before claim;
expiry is resolved by owner inspection, client observation timeout/drop, or
close, not by adding an independent per-input timer. The result wait still has
its own explicit finite observation budget.

* Notification and refill ownership

The old pending guard invokes queue cancellation after placement has already
claimed and removed its input. Previously that unsuccessful cancellation still
called =capacity_available=, reevaluating other requests' notification duties
from a stale client acknowledgement. The cancellation path now publishes only
when it actually removed a queued payload. An empty source is checked using
its existing length publication; no second completion/claim flag is introduced.

Actual native credit return still publishes through =CapacityEvents=, and the
owner retains its existing bounded refill opportunity. No completed result is
held behind another projector, no client acknowledgement owns native capacity,
and no capacity notification is deferred across arbitrary Scheme work. The
queued API removes the intermediate placement wake itself rather than merely
reordering result send and credit return. These source dependencies motivate
the experiment; they are not a claim that every observed tail has this cause.

* Reused joint model

Reuse the existing unassigned =poolStaged= queue, owner claim, capacity/root
ownership, selective notification and Tokio final-reply actions. The refinement
distinguishes optional placement polling from awaiting the final result. Queue
receipt creates no native root/credit and holds no Tokio polling slot. A native
owner can claim/run before a placement observer resumes; the queued path has
no placement-observation dependency. A stale cancellation after claim is a
stutter for queue/capacity ownership. Existing native publication and Scheme
Actor/green-thread progress remain independent of client consumption.

Directed cases cover bounded root-free queue receipt, full native reply without
placement polling, legacy placement acknowledgement, pre-claim cancellation,
post-claim timeout, close and a required premature-native-credit mutation.
These refine the existing model, not a second scheduler model. Finite safety
checks cannot establish OS fairness, wall-clock p99 or native correctness.

* What this negative result changes

Final-result polling starts before completion for all 640 candidate requests in
each load. The control has 68 CPU and four mixed results already ready on its
first final-result poll. This verifies that the protocol change actually reaches
the receiver, but does not measure the exact number of Tokio/OS resumptions.

Candidate send p99 is 7.21 microseconds (CPU) and 6.63 (mixed). Mixed pooled
send-to-final-ready-poll delay bounds increase from 46.08--49.42 microseconds to
388.04--390.92. Mixed native short p99 moves only from 494.83 to 500.25
microseconds. The larger client tail cannot be equated with a comparable
increase in native Scheme execution. The sender interval alone does not explain
that receiver wait. These timestamps do not isolate OS runnable/blocking time.

The experiment rejects the assumption that removing placement acknowledgement
alone yields a better joint progress protocol. A claim event is observable
progress before native completion, distinct from capacity availability. Its
notification can precede final-result readiness. Whether that earlier wake
provides useful scheduler lead time remains a hypothesis, not a proven OS
explanation. Preserve that progress distinction when considering a combined
claim/completion wait that can coalesce notifications; do not replace it with
client-held native capacity, a second execution lease, repeated yields or timer
threshold changes. Owner refill fairness still needs an independently valid
opportunity rule. The existing model and the new typed queue boundary provide
those ownership distinctions; native performance acceptance remains open.
