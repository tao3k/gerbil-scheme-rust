#+TITLE: Gerbil Scheme Actors, fixed owners and Rust executors
#+STARTUP: overview

* Decision and acceptance boundary

Use a resident Gerbil Scheme asynchronous service on each fixed VM owner as
our architectural target. Gerbil Scheme's Actor mechanism and green threads
own in-VM execution. Tokio handles asynchronous cross-instance dispatch and
notifications. Rayon is an optional bounded preparation executor for expensive,
pure Rust work. It does not run Scheme, move continuations or schedule Gerbil
Actors. Keep synchronous batches as an explicit finite-call API and control.

This is an architecture decision for subsequent implementation, not a claim
that the resident path has passed performance acceptance. The library already
contains synchronous and asynchronous paths; the remaining work is to align
their progress and resource contracts. Defaults are unchanged. No new A/B is
required for this review. The existing native watchdog failure remains open;
no rejected runtime candidate is approved for PR #18.

* Source facts and three alternatives

| Alternative | Execution authority | Publication boundary | Principal risk |
|------------+---------------------+----------------------+----------------|
| Synchronous batch | Fixed owner enters Gerbil; Gerbil Actors execute | Foreign call returns after all active Actors acknowledge | Batch barrier delays host-side recovery; callbacks can create a wait cycle |
| Resident asynchronous service | Same fixed owner; resident Gerbil Actors execute and suspend | Per-job readiness, then bounded owner recovery | Incorrect coupling of construction, recovery and client consumption |
| Resident service with on-demand Rayon preparation | Same as resident; Rayon only prepares owned Rust inputs | Bounded prepared windows feed the same service | Extra queues, preparation barriers and shared physical CPU contention |

These are not three competing schedulers for a Scheme VM. The third is an
optional preparation stage of the second. Cheap input should not require an
additional executor hop. Direct dispatch remains useful for synchronous callers;
Tokio is useful when external asynchronous work exists, not a prerequisite for
Gerbil scheduling.

* Execution and ownership contract

1. Before first native construction, a stateless root-free input may be rerouted.
   A stateful session remains pinned according to its existing routing contract.
2. Only the fixed owner enters its VM. Native construction establishes owner
   affinity for roots, Actor state and captured continuations. No Rayon work
   stealing or Tokio resumption transfers that ownership.
3. Gerbil controls Actor mailboxes, green-thread execution, suspension and
   continuation reentry. Rust notifications express readiness, never an in-VM
   execution grant. Do not layer a Rust per-handler execution lease over Gerbil.
4. A suspended invocation retains the state required for legitimate reentry.
   Exceptions, cancellation and repeated continuation entry must use the existing
   invocation ownership protocol; neither a wake nor an observed yield proves
   that execution completed or a root can be released.
5. Gerbil Actors and the owner share an OS thread. They are not separate physical
   CPU consumers. Other owners, Tokio workers and Rayon workers compete for the
   same host CPUs, allocator and memory bandwidth.

No general latency bound follows from Actor routing alone. Cooperative service
opportunities exist at actual Gerbil scheduling/checkpoint boundaries. An
arbitrary handler or foreign function can execute a long indivisible span.
Declare that boundary explicitly; do not claim preemption, weaken continuations,
or insert a callback on every handler merely to make a model appear fair.

* Service cycle and independent capacity domains

The cycle is: reserve bounded root-free input space; prepare a window; publish
it without waiting for all later windows or owner registrations; owner claims
and constructs native inputs; Gerbil executes; owner recovers completed values
and retires their native resources; Rust publishes independently consumable
results; clients consume them.

| Domain | What its credit bounds | Who releases it |
|--------+------------------------+-----------------|
| Prepared input | Owned Rust bytes plus declared work, including preparation in flight | Transfer, cancellation, timeout or failed preparation |
| Native admission | Requests admitted to one owner | Per-result retirement or terminal cleanup |
| Gerbil execution | Declared actual work between cooperative boundaries | Gerbil's existing budget/continuation protocol |
| Result transport | Reserved delivery slots and bounded owned result storage | Client consumption or receiver drop |

These credits cannot be interchangeable. An admitted result must have a bounded
recovery destination, or an explicit terminal policy, before execution can make
it ready. Reserve delivery capacity before native acceptance; do not block the
owner waiting for a client to free native capacity. Unknown result byte sizes
need an explicit limit, bounded chunk protocol or fallible projection contract;
a request-count bound alone does not bound memory.

A slow consumer necessarily stops further admission when its result reservation
budget is exhausted. The required property is that already admitted work can
retire without needing a new admission credit or a client callback. It is not
unlimited admission independent of consumer speed.

Projected owned Rust values no longer need Scheme roots. Opaque Scheme handles,
closures and continuation-bearing values may legitimately keep roots on their
owner until explicit release. Preserve that capability and account for it
separately; do not force JSON or pretend every value can be detached from its VM.

* Wait dependencies and protocol exclusions

An edge A -> B means A cannot progress until B progresses. A cycle identifies
a possible protocol deadlock, not proof that a captured watchdog used that path.

| Cycle | Explanation | Required exclusion |
|-------+-------------+--------------------|
| Client -> owner -> Gerbil Actor -> client | Synchronous caller blocks the callback executor needed by its Actor | Async callback/reply bridge, or a separate callback execution context |
| Owner -> result transport -> client -> native capacity -> owner | Recovery awaits a consumer that awaits admission released by recovery | Reserve result space; separate native retirement from final consumption |
| Owner -> Rayon preparer -> native capacity -> owner | Owner joins preparation which awaits a credit held until owner recovery | Root-free bounded preparation, admission outside Rayon work, no owner join |

The resident service avoids the synchronous all-Actor return barrier, but it
still needs a bounded owner recovery opportunity at safe native boundaries.
Always recovering first can starve supply; always constructing first can bury
ready short results. Use pending obligations and independent credits to select
a bounded service window, rather than layering another unconditional yield or
using client polling as the owner progress engine.

Wake protocol: publish a durable generation before signalling; the waiter
registers then rechecks the generation; consume observed generations rather
than counting notifications as jobs. Coalesce wake signals while preserving
pending obligations. Transport readiness, Tokio task resumption, native
execution and client consumption are distinct transitions. No model assumption
may turn an unpolled future into actual consumption.

* Shared CPU and duplicate scheduling cost

Model host CPU occupancy across owners, Tokio and Rayon. This is an abstraction
for competition, not a proposal for a global runtime CPU semaphore. CPU
oversubscription can produce runnable delay without any protocol deadlock.
Safety checks alone cannot establish host scheduling fairness or p99.

For a prepared window, Rayon is worthwhile only when the reduction in pure
Rust preparation time exceeds enqueue, join, copying/allocation and CPU
interference costs. There is no measured break-even point established by this
review. Do not enable Rayon by request count alone or change the default.

Count unnecessary cross-runtime handoffs separately from unavoidable native
construction, execution, GC and projection. The model's 48-item / 6-window
example counts 96 per-item round trips versus 12 window round trips, or 24 when
adding a preparation executor round trip. These are symbolic topology counts,
not observed counts in the current library, not FFI timing, and not a speedup
prediction. A resident Gerbil service may still need multiple bounded native
entries. Gerbil mailbox operations are not themselves Rust executor hops.

* Model refinement and what it establishes

The =gerbil_service_architecture= refinement imports =service_sharing_cases=
and therefore the same native root, admission, Actor and completion state.
It does not instantiate another native lifecycle, Actor mailbox or work budget.
The added state records architecture choices, symbolic host CPU occupancy,
wait dependencies and a small generation-based notification contract.

Directed checks cover synchronous and resident dependencies; three wait-cycle
controls; optional bounded Rayon preparation; physical CPU competition; invalid
foreign entry and oversubscription controls; publication before waiter arming;
coalesced and lost wakes; cancellation before native construction; native
retirement before client consumption; and symbolic boundary counts. The native
retirement witness executes the existing model's real construction/execution/
projection actions rather than replacing them with a synthetic completion bit.
Both existing job domains use the same refinement through the current Rust
Quint gate. Supplied dependency graphs are architecture contracts, not extracted
wait graphs from the runtime. CPU occupancy and wake rules are abstractions,
not a verified Tokio or OS implementation.

* Actual API audit and resident producer progress

The following audit covers the pool stream / registered producer / resident
service path. It is not an exhaustive proof of arbitrary user callbacks or all
library APIs. No internal capacity wait cycle was established in this path.
In particular, the dependency controls above must not be reported as an observed
native deadlock or as the cause of the historical watchdog.

| Actual boundary | Order found in source | Progress implication |
|-----------------+-----------------------+----------------------|
| Pool plan | Validate count/owners; create ready channels; register producers; publish bounded windows | Delivery storage exists before native acceptance; no wait for client consumption during publication |
| Registration | Await producer semaphore; lock admission table; validate capacity identity; enqueue producer with try_send; unlock; notify | No table lock spans the await; failed enqueue drops the registration permit |
| Producer claim | Inspect source; acquire active then work then native slot; recheck lifecycle; remove matching-price input; construct on owner | Waiting futures are polled, not synchronously joined; root-free reservations do not migrate entered state |
| Completion | Harvest native identities/slots; project each result; release each native/active permit through its retirement guard | No synchronous wait for a client to read a result |
| Reply | oneshot send or per-owner ready queue try_send | Publication cannot block the owner on transport capacity under the original-count/unique-result contract |
| Failed slot transfer | Preserve native and stream permits in retirement drain; fail owner service | Failure must not manufacture returned credits before native cleanup |

The per-owner ready queue can hold the whole finite input count. At most that
many logical results exist across all owner queues; channel metadata can scale
with owners times count. This bounds finite result slots, not arbitrary payload
bytes. No byte-bound claim or support for an unbounded output stream is added.
Opaque owner-bound handles retain their separate explicit-release contract.

Source locks follow requests -> offers when both are needed. Reclaimed native
credits are released outside source locks. Source wake first clones weak signals
under its signal lock, then invokes them after releasing that lock. Rejection
extracts jobs under the source lock and calls failure delivery outside it.
These observations exclude the corresponding source/table/wake lock cycles in
the audited path; they do not prove all possible OS blocking is absent.

** Concrete repeated scheduling removed

Previously =owner_loop::waker= performed both a =Work::Wake= mailbox enqueue
(with a new started flag) and a native pipe notification for every producer
wake. The mailbox token was a durable progress record, not application work.
Several capacity/source events could leave several tokens for repeated owner
turns even though pipe writes already coalesced. This duplication is established
by source and descriptor controls, not a measured throughput attribution.

For resident Gerbil service owners, the waker now publishes a boolean producer
duty before notifying the existing pipe. Only service programs create this wake
port; ordinary blocking owners retain the original mailbox token path.
The owner rearms transport, claims producer duty, and repeats its service cycle
when duty was present. Application inbox, short-port and offer rechecks remain.
Gerbil's Actor scheduling, execution budgets, native result tokens and exception/
continuation ownership are unchanged. No new thread, timer, queue or per-handler
execution lease is introduced.

The actual ordering is:

1. Publisher makes source/capacity state visible, stores producer duty, then
   claims or coalesces the pipe notification.
2. Before native sleep, owner reopens pipe publication, then atomically claims
   producer duty. A claimed duty requires another owner turn.
3. Publication before the duty check is either claimed or has a pipe notification.
   Publication after the check owes a fresh notification (or one already owed
   by another publisher). A pipe byte is a hint; it is not the work ledger.
4. Empty open input, cancellation, close and registration still use their existing
   state. Coalescing does not grant capacity, execute Scheme or release roots.

Removing mailbox tokens without the durable duty/recheck would be incorrect:
an old pipe byte may already have been consumed while its coalescing claim
remains set. The new model control demonstrates precisely that unsafe removal.
It does not claim the previous mailbox-based implementation lost that wake.

The existing architecture refinement now separates the two arming atomics so
publication before, between and after them can be checked. The descriptor
controls exercise the actual waker, pipe and coalescing state. Existing native
service scenarios cover suspended Gerbil work, exceptions, continuations,
capacity return before client consumption, cancellation, timeout and shutdown.
The unresolved benchmark watchdog remains a separate failure record.

* H4: accepted Scheme work while Rust publication is paused

The retained 49.798625 ms spike contains a 21.211833 ms pre-construction interval
and a 28.538042 ms construction-end/projection-start interval. No bulk completion
was observed on any owner during the former. That does not establish source
emptiness, active execution, mutex contention or a process-wide scheduling pause.
The original capture retains no source queue/lock state or Scheme ready-queue
state at those instants.

H4 predicts a concrete cycle: subsequent Rust input preparation or source seal
must advance before already accepted Scheme tasks can execute, project results
and return native credits. The source audit rejects the simpler claim that the
iterator is called under =Shared.requests=: preparation and indexed staging are
outside that mutex; =Shared::publish= appends an already prepared batch. The

* Implementation candidate: shared supply without blocking owner progress

The work now moves from additional historical non-reproduction witnesses to a
concrete protocol improvement. Existing owner code could synchronously wait for
shared source queues, offer payloads/slots and producer signal metadata before
its next Scheme service turn. A source-level dependency is sufficient to improve
that boundary; it does not attribute the historical 49.798625 ms spike or exit 70.

The actual producer and owner offer path now implement these transitions:

| Boundary | Implemented behavior |
|----------+----------------------|
| Uncontended shared access | Immediate try-lock; no wait future allocation |
| Contended shared access | Enable an owned notification, then recheck before returning Pending |
| Pending source/offer entry | Return speculative active/work/slot credits before returning to the owner service loop |
| Unlock | Release all transaction data guards before dispatching registered notifications |
| Owner retry | Persistent notification uses the existing durable native producer wake and pipe |
| First native entry | Payload commit remains unique; entered Scheme objects stay on that owner |
| Optional peer assistance | Busy peer metadata/source/target slot skips assistance; input remains owned |
| Failed unpublished offer | Sole-capability rollback returns the Rust request without acquiring the busy target slot |
| Source signal fanout | Preallocated once-initialized weak slots; partial registration is usable immediately |
| Pipe publication | Existing nonblocking one-byte write, retaining coalescing and error semantics; no writer mutex |

=SupplyMutex= and =SupplyWait= are internal synchronization types. =Head= separates
work, temporarily empty/open input and exhausted input; contention is Poll::Pending,
not a false end-of-source. The producer caches proven exhaustion for its deadline
query rather than taking a source lock there. A pending take releases speculative
credits; accepted tasks retain their original native credit/root guards. A
transaction-local notification list ensures nested queue/offer unlocks cannot
invoke a reentrant owner callback under an outer supply data lock. The list
allocates only when a contended release actually owes notifications.

=Source::poll_head= and =poll_take= replace blocking source cursor methods in
=ServiceProducer=. =Pump::claim_offer= owns a persistent offer wait and owner
waker. Both ready work and unlock events return through the existing owner service
cycle; no new runtime thread, timer retry, task-per-message or Scheme scheduler
is introduced. Gerbil still owns Actor/green-thread execution, GC, continuations
and exceptions. Rust handles cross-instance dispatch and typed boundary custody.
