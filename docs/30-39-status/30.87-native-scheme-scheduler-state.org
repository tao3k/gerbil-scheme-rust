#+TITLE: Native Scheme scheduler state without a shadow activation ledger
#+STARTUP: overview

* Scope and status

This opt-in ABI32 candidate keeps Rust responsible for cross-instance dispatch.
Each fixed owner still executes a complete Gerbil/Gambit VM. Scheme retains
Actor and green-thread scheduling, GC, exceptions and continuations. No SMP
change or default selection is included. Native correctness and performance
acceptance are separate gates; rejected predecessors remain in the evidence
history.

The preceding fused-event candidate reduced source-level critical sections but
failed net-cost acceptance. This candidate removes the duplicated Runtime
job/Actor activation inventory from its selected path, rather than adding
another lease, per-handler callback or yield threshold. Existing observed
Runtime policies remain explicit experimental controls.

* One source of execution state

The existing service queues, worker assignments, budget grant/waiter ownership
and Actor turn already carry the scheduling state. ABI32 reads those facts only
at an existing native harvest boundary. Public Gambit =thread-state= predicates
distinguish running, waiting and terminated threads. Critically, a waiting
thread whose =thread-state-waiting-for= is a =processor?= is runnable; a mailbox,
condition variable or timer wait is externally suspended. Known service/budget
control mutexes are treated as eligible, because the observer releases them
before invoking the Scheme scheduler. Arbitrary application mutex waits are
not treated as runnable.

| Existing harvest state | Action |
|------------------------+--------|
| Short completion ready | Collect directly |
| No completion ready | Preserve the existing single Scheme pass, without scanning phases or thread states |
| Bulk completion ready; no short job or Actor source | Collect directly |
| Bulk ready; short queued, selected/owned, or natively runnable | Offer one existing Scheme pass before collecting |
| Bulk ready; all short work externally blocked | Collect directly |

A pass is an execution opportunity, never an execution acknowledgement. Actual
first grant, pending execution, result roots and capacity retirement retain their
existing owners. The safe-span contract remains unchanged: an arbitrary handler
cannot be preempted inside an undeclared operation. Producer-declared work
layouts remain bounded; this policy does not make an entire batch atomic.

* Actor inventory and continuation boundaries

Only a short Actor service registers one probe per service/policy epoch. It
reuses the existing active turn and persistent worker threads, including the
private coordinator that can become runnable after its children reply. Bulk
Actor calls add no observation context. Idle Actor services are ineligible;
close removes the source and clears its cached state. A later short call under
a different policy removes the previous registration before adding the new one.
An old epoch may remain referenced until that call or close; this bounded cold
reference is not a new native root or a completed-result retention policy.

The existing dynamic extent still protects Actor reentry and clears active
state on unwind. During setup or continuation reentry, the coordinator's turn
may not yet be published. Unknown active state conservatively permits one pass;
it cannot grant, acknowledge or retire resources. No retained continuation is
forced to share a new mutable invocation record. Existing budget and work-plan
continuation/exception ownership stays in force.

Source-list spines are immutable. Registration/removal uses the existing budget
mutex; a borrowed source snapshot invokes probes outside service/budget locks.
Service-to-budget lock order is unchanged. No user thunk, Scheme yield or
resource release runs while holding the inventory lock. The selected path
allocates no shadow Runtime context per job or Actor child.

* Typed API and reproducible qualification

=SchemeServiceCyclePolicy::NativeBudget= selects the explicit policy through
=configure_scheme_service_boundary_plan_on=. The native Scheme protocol accepts
mode 17/command 47; command 48 projects the cold two-field inventory snapshot.
=SchemeNativeProgress= exposes whether this policy is enabled and the registered
Actor-source count. =SchemeRuntimeProgress.enabled=false= means shadow context
tracking is disabled; it never means that a Scheme VM is absent.

Build through the existing Cargo/Gerbil native graph with
=GERBIL_DYNAMIC_MODULE_OPT_LEVEL=2=. The existing Rust =scheme_service= bench
selects =--progress-fair-ab --fixed-short-selective --native-budget-cost-ab=.
It compares unobserved ReadyFirst with NativeBudget in the same four live VMs
and image: Tokio two workers, window four, work 32, batch eight, Actor quantum
one, class/feed one and declared work four / maximum span 48. Observation is
off. Five ordered/reversed blocks cover only the existing CPU and mixed loads.
Both arms perform the same cold post-window inventory projections.

Retain whole-file host/image/source identities and every sample privately.
Each window must conserve 8192 orders, 64 short probes, 1088 independently
retired results, exact declared work and first grants. Terminal acceptance
requires four owners joined, zero roots, removed files and quiescent service.
The five-second native meaningful-progress watchdog and 120-second controller
are unchanged. Boundary compiler checks do not prove complete OS quiescence.

The reused joint Tokio/owner/Actor/green-thread model separates native runnable
and external wait, source class, existing grant/waiter ownership and collection.
Directed witnesses include processor-waiting work without a received grant,
blocked-short close/drain, Actor children blocking/resuming, and required
skipped-pass/unsafe-OS-sleep mutations. It creates no second production lease
or waiting queue. Finite model checks do not establish native timing or
universal liveness.

* Remaining client progress boundary

Same-request decomposition locates 97.63% of the candidate CPU scheduled top-ten
total before the current request's submission start (control 94.60%). The worst
candidate scheduled request is 9.109 ms, of which only 0.157 ms is from submission
start to native completion. This cannot be attributed to that request's Scheme
construction, execution or GC. It does not rule out interference from other
requests, OS scheduling or allocation elsewhere.

The existing probe waits for its previous result before the next planned timer
and submission. Thus identical logical work and planned 500-us timestamps do
not mean identical actual arrival traces. =probe_actual_ns= ends at the owner
completion timestamp, not at client observation; =probe_scheduled_ns= adds the
pre-issue lag, which can include previous completion delivery/resumption. The
current fields cannot separate timer wake, Tokio ready wait, synchronous input
preparation/registration and OS wait. Do not rename/remove the negative metric
or claim that the issuer boundary is already an attributed root cause.

The next protocol boundary is planned arrival -> actual issue -> native-ready
-> client-observed, with bounded client preparation/registration kept distinct
from Scheme execution ownership. The actual stream already awaits Tokio
oneshot receivers through a timeout; missing generic cooperative yielding is
not established. Review synchronous pool preparation/validation before the
first registration await and ready-result delivery/resumption under the same
client fairness contract. Extend the existing joint client/owner model and
actual API boundary before another directed experiment; do not add blind
per-result yields or weaken the Scheme budget. The owner spread regression
remains independently open. No new profiler or benchmark matrix is needed to
locate these existing measurement boundaries.
