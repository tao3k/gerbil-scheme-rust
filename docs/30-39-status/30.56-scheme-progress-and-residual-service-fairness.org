#+title: Scheme progress and residual-service joint fairness
#+options: toc:nil num:nil

* Decision from the previous evidence

Report 30.55 rejects both interleaved constructors and snapshot-first refill as
general improvements. Neither callback count nor fair short wake duties express
how much accepted Scheme service remains. This change adds advisory native
progress and a joint short/bulk claim policy; it does not change refill order,
VM count, class execution budgets or any default.

* Two independent ledgers

| Ledger | Charge | Reduction | Authority |
|--------+--------+-----------+-----------|
| Resource | Existing active/work/slot permits at owner claim | Native projection/root retirement only | Admission bounds, lifetime and close drain |
| Service | Declared native units at Scheme submission | Stable Scheme unit IDs; all remaining units at success/exception completion | Advisory destination/claim ranking only |

A completed unit does not free any resource credit or native root. Even zero
remaining service can coexist with held projection roots, outstanding result
ownership and full resource charges. Observation timeout/drop does not retract
accepted native work. Uncommitted Rust payloads can select a different owner;
accepted Scheme values, Actors and continuations remain fixed.

The Scheme ledger serializes report/deduplication, finish and receipt under one
Scheme mutex. No application callback runs under that mutex. A stable unit ID
is counted once even when a multishot continuation resumes after GC. Reporting
on a finished job is inert. Native Actor batches propagate the job context and
report completed item identities, including terminal item failure. Other Scheme
handlers may explicitly use =gerbil-rs-progress-unit!=, or keep their full
conservative charge until completion. If an Actor batch's item count differs
from the declared work charge, automatic partial reports are disabled; execution
and ordinary native types are preserved. Units are logical application work,
not elapsed-time estimates or preemption boundaries.

* Native and public API boundary

=enable_scheme_service_progress_on(owner)= explicitly activates an
idle ABI-v6 owner and verifies the Scheme reply. Configuration requires bounded
native work capacity; active work/producer registration rejects reconfiguration.
Activation is fixed until VM shutdown. This closes a race where a waiting
producer could pass capability validation just before another caller disabled
its receipts. Repeated idle activation is idempotent; active activation fails.
=scheme_service_progress_on(owner)= reads the last cached native-turn receipt,
not a profiler, a new Scheme query or a current OS scheduling state.

ABI v6 adds an optional four-word submit header carrying the frozen declared
charge, and an opt-in completion receipt =[-6, bulk_remaining, short_remaining,
completed_ids...]=. The existing completion command returns the metadata: no
background timer, periodic diagnostic polling or per-unit Rust FFI callback is
introduced. Disabled services keep the existing submit/ready wire formats.
Application payloads and results retain the native type interface.

The owner charges its cached hint conservatively after successful native submit,
then replaces the pair atomically at the next native turn. This includes
submissions since the last receipt without overwriting or summing stale snapshots.
The cached count pair is advisory and may lag Scheme progress. Its separate
=waiting_for_claim= field declares the owner has completed arm/recheck and is
entering native wait; the owner clears it before another host turn and on close.
It excludes active constructors/projectors from bulk opportunity selection, but
is not an OS blocked/runnable measurement or a bound on Scheme execution inside
the native wait. The cache never bypasses capacity,
Actor affinity, the admission/close fence or native lifecycle validation.

* Joint fairness algorithm

** Bulk claim opportunities

=SchemeServiceSupplyAdmission::ProgressFair= requires progress on all registered
owners. A shared source checks the claimant's cached residual service against
other live owners with enough native work/slot and active capacity for the FIFO
head, and a published wait declaration. It allows one head charge of slack. If a lower-service eligible peer exists
beyond that slack, it notifies the peer and returns the claimant's speculative
credits before the owner takes another turn.

Only one such deferral is allowed before the claimant may acquire the next
head. A descheduled, cancelled or closing peer cannot own an exclusive claim or
hold native capacity. The next claim remains runnable even if the notified peer
never executes. Source FIFO, final lifecycle fences, cancellation/deadline and
immutable accepted owner semantics are unchanged. This is an opportunity
protocol, not a global finish barrier or a scheduler time guarantee.

** Short notification duties

=SchemeShortWake::ProgressFair= ranks eligible registered sleepers by the same
residual-service hint. Lower service wins, with existing FIFO order breaking ties.
After two eligible bypasses, a waiter enters a promoted class; promoted waiters
are served in FIFO order before ordinary residual ranking. The threshold is a
promotion rule, not a universal two-grant wait bound when many owners are already
promoted. Ineligible owners accrue no new bypass debt. Resume/claim/close clears
obsolete duties; no native permit or Rust payload is reserved by a wake.

Running owners still claim visible short work before sleeping, even when a peer
was notified. There is no recursive native advance inside selection. Scheme
continues to own class arbitration, green threads, Actors, continuations, waits,
exceptions and GC. Rust only distributes uncommitted cross-instance work.

* Existing model refinement and native obligations

The existing =owner_lifecycle.qnt= adds stable reported-unit sets, a bounded peer
opportunity and short promotion debt. Resource conservation remains the original
invariant. New scenarios cover idempotent progress, zero authority to return
credits, delayed-peer work conservation, low-service short selection, promoted
waiters, timeout/close drain and an intentionally premature credit-release
mutation. The aggregate gate runs the new progress traces and requires a real
invariant counterexample from the mutation. It does not substitute for native
correctness or prove an OS time bound. The existing two-owner domains do not
prove an arbitrary-owner latency/fairness theorem.

Native qualification observes an eight-unit Actor batch with six completed
units while all eight resource credits remain charged. It also executes a
coarser one-unit/eight-item native type contract without partial accounting,
GC/multishot unit replay, Scheme exceptions, construct/project panics, queued
cancellation/expiry, held projections and accepted-work close drain. Progress
mode participates in the existing native service and pool-stream tests.

An initial native run passed the new progress/replay checks but failed a later
old wake scenario because the new fixture left its latch open. Restoring the
latch after the completed partial-progress scenario fixes test-state pollution;
the five-second gate is unchanged. Its failure capture remains private. An
initial Quint command matched non-test action names as well as test runs and
reported uninitialized-state errors; the four deterministic scenarios themselves
passed. That command error is not admitted as a protocol counterexample.

* Directed matched comparison

#+end_example

Both arms use the same four live VMs and native O2 image, two Tokio workers,
8192 real orders and 64 short probes, slot/work limits 4/32, batch eight, quantum
one, native-port wake and three active bulk jobs per owner. Both enable the same
native progress receipts; the control uses =OwnerLocal= plus FIFO =Selective=
wake, and the candidate uses =ProgressFair= for bulk and short duties. Neither
uses =RetirementRefill=. This isolates the joint policy with equal progress
instrumentation; it does not measure progress-instrumentation cost versus the
old disabled default. No matrix or unchanged recapture is added.

Raw output, initial failures, frozen artifacts and full-source hashes stay outside
Git. The binary and native-image identities are recorded before timing. Native
progress retains its five-second watchdog. Short native-completion p99 is the
projection completion clock, not the time a Tokio caller resumes; scheduled-probe
latency is reported separately. GC wall time is not treated as owner CPU time.

Native completion does not include the later Tokio caller resumption. The
scheduled and admission clocks retain their regressions. No promotion is admitted.

Code inspection identifies a distinct eligibility gap: native credits can be
free while a peer is still in an arbitrary constructor/projector. Residual work
and resource eligibility do not constitute a claim-ready handshake. The final
policy therefore additionally requires the peer's existing arm/recheck/native-
wait declaration before offering it a bulk turn. It still falls back after one
opportunity and never reserves native capacity for the peer. This is a protocol
refinement, not a claim that the capture alone proves an OS/GC cause.

The new =progressBusyPeerClaimTest= keeps free peer capacity but no wait
declaration and verifies immediate work conservation. The existing peer-delay
scenario now explicitly parks the peer before granting its opportunity. The
focused model gate discovers all five progress scenarios in both owner domains,
then runs the same 1,000 progress traces and required mutation counterexample.
It passes in 17.76 s. Unchanged model gates are not repeated for this refinement.
