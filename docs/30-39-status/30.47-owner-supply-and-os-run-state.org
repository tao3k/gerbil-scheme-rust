* Instrumentation in the actual owner path

=SchemeServicePhase::Supply= appends a fifth phase, preserving the first four
indices. It encloses the existing owner-local producer step, including capacity
checks and pool directory access. Without explicit observation, the owner reads
no additional phase clocks. No Scheme evaluator or scheduler is replaced.

The Darwin Rust bench adds bounded nominal one-millisecond point observations
of its own four named owner threads. Each row records owner, monotonic query
bounds, kernel run state, cumulative thread CPU in microseconds, flags and
suspend count. It never suspends an owner. Inspection rights, thread-list
storage and the sampling thread retire before native shutdown, including unwind.
Overflow/error counts must be zero. Both diagnostic captures complete forty
samples with zero history loss, zero OS sampling errors/overflow, four joined
owners, zero roots and removed temporary files.

The kernel's =TH_STATE_RUNNING= includes running or queued-to-run: XNU maps
=TH_RUN= to that value, and defines =TH_RUN= as running or on the run queue.
See Apple's [[https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/thread.c][thread-info implementation]] and
[[https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/thread.h][thread-state definition]]. These references explain the API classification;
they are not a claim that an arbitrary upstream revision is the host kernel.
A point observation does not label the time between samples or provide exact
runnable-to-dispatch timestamps. Sampler interference is diagnostic overhead;
performance captures run without this observer or the external stack sampler.

* Blocking evidence versus runnable non-CPU evidence

An own-process five-second stack sample of the unchanged frozen =service-wake=
artifact finds =ServiceProducer::open= under =pthread_mutex_firstfit_lock_wait=: owner refill can actually block on the global admission directory mutex. This
is a real blocking path, not a proof it explains the earlier GC-associated tails.
The external sample completes the workload cleanly; it is not a speed receipt.

The new phase/OS diagnostics separate several cases. These are full phases
that overlap a short request inbox interval; counters and point counts enclose
the full phase and are not clipped to the request overlap:

In the first Submit, kernel cumulative CPU increases only two microseconds
between the first and last enclosed points. In the candidate pooled Wait the
corresponding increase is 29 microseconds; in its pooled Supply it is zero.
These point pairs enclose only part of each full phase and have different CPU
quantization from the phase clock. The full-phase CPU values above remain the
measurement of actual owner execution over the complete enclosing interval.

The GC wall intervals are therefore not 76/110 ms of owner collector execution.
At sampled points the owner is runnable/running with little CPU progress, which
supports off-CPU scheduling delay outside select. It does not establish the
exact dispatch delay, rule out waits between points, identify the competing
thread, or measure collector-only CPU. Enclosing phase CPU includes other native
work; SDK GC CPU remains process scoped and is never summed across owners.
The zero-GC Advance also rules out GC as a universal explanation.

* One protocol candidate, rejected after targeted qualification

A private candidate issued a weak owner epoch at registration after validating
capacity identity under the admission lock. Close invalidated every epoch under
that same lock before directory detach; pre/post-capacity checks used the epoch
and existing wake closure/failure flags. Accepted Scheme work still drained;
no descriptor or VM was retained by the epoch. This removed directory lookup
from resident supply without changing budgets, routing or Scheme execution.

Its unit control passed concurrent directory ownership, explicit close
invalidation and owner-index reuse. Eleven instance unit controls passed.
Every captured candidate workload retired cleanly. Nevertheless removing that
lock did not remove Supply's runnable non-CPU tails or give stable performance.
The candidate source, unit control, manifest, captures and retirement diff are
retained privately; its implementation is withdrawn from the final tree.
No dormant mode, runtime flag or new default remains.

* Decision and remaining gate

Retain the current pool source, its capacity/backpressure protocol, Scheme-owned
execution and production defaults. Ship the trace-consumer correction and
Supply/OS observability. Retire the epoch experiment rather than accepting an
unproven trade-off. No new scheduling model or full thread-count matrix is added.

The remaining causal gap is exact runnable/dispatch transitions and blocking
stacks at individual tails. Point samples now distinguish runnable observations
from persistent select waits, but do not close that gap. A future algorithm
change must explain these measurements and qualify the same-live-VM workload
without hiding negative results. Scheme retains native types, GC, continuations,
Actors, green threads, exceptions and dynamic bindings; Rust distributes work
across instances. No timeout, default or execution capability is weakened.
