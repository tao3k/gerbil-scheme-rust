#+TITLE: Bounded client completion service across native retirement and bulk progress
#+STARTUP: overview

* Evidence and remaining protocol gap

The kernel-arrival-only candidate remains rejected: mixed planned-to-client
p99 improves 84.38%, but CPU total-work/time throughput falls 20.57%, CPU
native p99 grows 45.07% and CPU client p99 grows 416.98%. Its worst CPU window
contains a native-ready-to-client interval of 3.378 ms for request 35, whose
own deadline-resume interval is only 3.625 us. Serial backlog accounts for
95.43% of the top-ten CPU client tails' summed latency. Backlog is propagated
delay, not a cause or an excuse to remove those requests from the metric.

The previous generic client-turn driver already offers a signalled short
future a poll before each bulk wait. That opportunity does not guarantee
consumption of a published result: Tokio's pinned oneshot Future polls its
cooperative task budget before reading readiness. Bulk and short sub-futures
in one task share that budget. A ready transport and a cooperative deferral
are different from an unfinished native job. This mechanism is verifiable in
local Tokio 1.53.1 source and a real exhausted-budget control. It is a possible
protocol gap, not proof that it caused the previous OS/client tail.

* Joint protocol at the actual API

ProgressSchemeTicket::wait_observed_ready is an explicit alternative to the
unchanged wait_observed method. A poll first tries to take exactly one final
Rust oneshot value. A successfully published value can complete before
cooperative deferral. This is a bounded transport operation, not an unbounded
Future or handler running under unconstrained. Empty/closed transport follows
the normal receiver poll, registration and error path. The claim event still
provides an early wake and a single recheck; claim is not a final task value.

The existing InstanceClientProgressDriver provides the service opportunity
before each bulk registration/receive. It drives the same serial short source,
including each original timer and the following native wait. Only the final
receiver's ready read has the new treatment. Timers, bounded admission, bulk
MPSC receive and arbitrary application work retain normal cooperation. A
native completion arriving during one ready bulk turn remains due at the
next service boundary; an indivisible user poll and actual OS scheduling are
still outside the logical opportunity guarantee. No periodic yield or new
threshold is introduced, and no native owner waits for a client acknowledgement.

The diagnostic ready_without_budget bit means an actual already-published
value was taken when the current task had no cooperative budget. It does not
restore the task budget or count an OS resumption. False does not prove that
cooperation was irrelevant elsewhere. A capture with zero such events cannot
claim that this particular fast path explains its performance improvement.
The bit is captured only in the explicit observed ready receive; conventional
receive remains false. Claim and publication traces keep their existing clocks.

Native ownership remains owner-local: before claim, dropping the pending guard
cancels bounded Rust input; after claim, timeout or dropped observation cannot
release native credit or roots. Projection/retirement and owner refill remain
independent of client consumption. Exceptions are task values, and successful
Rust results are not discarded due to separate timing errors. Scheme retains
its complete Actor, green-thread, continuation, GC and exception semantics;
Rust only distributes across the fixed independent instances.

* Reused joint model and native controls

The existing delivery/client-turn section gains a client cooperative-availability
state and explicit completion-service selection. It reuses the same replies,
claim wake debt, ready bulk queues, producer ownership and native capacity.
A ready final result can be observed with exhausted cooperation while bulk
receive remains deferred. Claim-only progress cannot fabricate completion.
Cancel/close still drains the registered producers and native roots. The
model is finite safety/opportunity evidence, not an OS latency guarantee.

invariant. The first Rust focused-test filter matched zero tests; it is not
counted as a test pass. The final filter targets the actual progress_wait

Actual Scheme controls use the new API for native success/exception, preclaim
cancel/timeout and claimed timeout; the last still holds owner capacity until
