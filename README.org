#+title: gerbil-scheme-rust
#+options: toc:nil num:nil

In-process Gerbil Scheme FFI and AOT build support for Rust. Scheme owns its
numeric tower, object identity and GC; Rust gets explicit, lifetime-bound
handles and whole-value transfer APIs.

This is a standalone bridge, not an application runtime or parser.
Marlin, POO Flow, Orgize, graph execution and application policy remain
downstream concerns.

* Hybrid compilation and execution hosts

A Rust execution host does not require handwritten Rust replacements for
Scheme-authored algorithms. Prefer existing compiled Scheme/C algorithm exports
through the typed C ABI; build-time Rust IR lowering is a separate facility,
not a substitute for actually reusing those exports.
Rust owns host scheduling, owned transport and lifecycle. Python consumers
install the built library without an SDK or compilation workflow.

This hybrid boundary is intentional, not an exception to the Rust-host
architecture. A compiled Scheme C export can still require a Scheme VM;
VM-independent execution must be qualified for the actual artifact.
Read [[file:docs/hybrid-execution.md][Hybrid compilation and runtime ownership]]
before extending providers, callable values, closure/state support or compiler
lowering. It records current implementations, unresolved capabilities and
why a second handwritten interpreter is not the migration strategy.

* Rust dispatch retains the Scheme runtime

The full Scheme execution path is Rust dispatch -> fixed OS owner -> complete
Gerbil/Gambit runtime -> compiled Scheme. =InstancePool= retains one native VM
per owner; Rust transfers owned native values between the caller and that owner.
Scheme retains GC, closures, continuations, dynamic bindings and cooperative
Actor/green-thread scheduling. Rust dispatch does not schedule Scheme green threads.

A Rust backend is not inherently a "no Scheme VM" backend. The separate
Scheme-to-Rust IR kernels and the ASCENT Python subset example do not qualify
complete Scheme execution. The ledger now defaults to four native Scheme owners;
its installed tests and the previous expander failure are recorded in
[[file:docs/30-39-status/30.10-python-native-owner-integration.org][the integration report]]. They are not a substitute for this native runtime path.
The Owned C ABI declares =NO_VM= or =SCHEME_VM= explicitly; the latter requires
a live fixed-owner VM through every callback/release. The flag itself is not a
runtime lease. The instance API is experimental on Darwin; packaging, portability
and hot unloading have separate gates. Read [[file:docs/instance-runtime.org][the actual API contract]].

The subsequent native module packaging repair passes the installed four-owner
expander, hygienic macro and clean-shutdown gates; see
[[file:docs/30-39-status/30.11-expander-startup-and-dispatch-benchmarks.org][the repair and direct/Tokio/Rayon benchmark matrix]].
The actual =-O2= wheel also passes the exercised Scheme capability gates;
[[file:docs/30-39-status/30.13-progress-supervised-o2-qualification.org][the O0/O2 qualification]] retains noisy and negative results. Quiet-host performance
admission remains pending.

* Runtime and ownership

- =GerbilRuntime= initializes the process-global runtime on one owner thread.
  Strong roots keep Scheme objects alive; handles cannot cross threads.
- Rooted snapshots retain an entire collection or component span with one
  root. Borrowed references cannot outlive that snapshot. Explicit element
  roots remain valid within the runtime lifetime after snapshot release.
- Byte/string/numeric/name buffers own their copied Rust data. Reused
  staging preserves published output when validation fails. No borrowed
  Scheme heap pointer becomes a Rust slice that survives GC.
- AOT and FFI work together: the canonical build produces linked Scheme
  objects; Rust enters those compiled exports through the C ABI.
- The separate =Gerbil= toolchain API explicitly invokes the configured
  interpreter/compiler. It is not a process fallback for in-process calls.
- Tokio controls admission, queues and response tasks. Concurrent Rust
  callers do not establish parallel Scheme execution inside one VM.

Multiple-VM capability does not imply multiple active processors or safe
cross-thread entry. Current CI explicitly SKIPS Scheme multi-processor
qualification because its pinned SDK lacks qualified multiple-threaded-VM
support. A skipped gate is not a pass. Independent-VM experiments remain
separate from the admitted single-owner path.

* Data transfer

| Family | Public transfer and ownership |
|--------+-------------------------------|
| Boolean, fixnum, character, flonum | Validated owned scalar spans, including trusted false/zero |
| String / bytevector | Whole UTF-8/byte transfer; validated owned Rust data and reused output |
| Exact integer | Canonical sign + binary magnitude, no decimal serialization or truncation |
| u16/u32/u64, s8/s16/s32/s64, f32/f64 vectors | Sealed native-layout whole spans with transactional staging |
| Symbol / keyword | Owned bulk names; spelling is not identity; explicit interned/uninterned construction |
| Pair, proper list, generic vector | Strong shallow snapshots and root-bound element references |
| Rational / complex | Whole batch construction; exact or inexact components remain rooted Scheme values |
| Gambit hash table | Explicit eq?/eqv?/equal?, strong keys/values, shallow bulk key/value snapshots |

Rational reduction and complex-to-real normalization follow official Scheme
semantics. Table order is unspecified; duplicate keys follow the selected
equality and last value wins. Weak tables, arbitrary Gerbil HashTable
implementations and deep recursive Rust serialization are not implied.

#+begin_src rust
use gerbil_scheme::{GerbilRuntime, NumberKind, RootedObjectBatch};

fn main() -> Result<(), gerbil_scheme::NativeError> {
    let runtime = GerbilRuntime::initialize()?;
    let numerator = runtime.root_value(runtime.fixnum_value(6)?)?;
    let denominator = runtime.root_value(runtime.fixnum_value(-4)?)?;
    let values = runtime.number_batch(
        NumberKind::Rational, &[(&numerator, &denominator)],
    )?;
    let mut parts = RootedObjectBatch::default();
    values.copy_number_components(NumberKind::Rational, &mut parts)?;
    drop(values);
    // Scheme normalized 6/-4 to -3/2. The snapshot retains both components.
    println!("{:?}", parts.get(0).unwrap().scalar()?);
    Ok(())
}
#+end_src

PER variant/load, rotating inputs and matched ABBA controls. P95/P99 are
exact nearest-rank percentiles of individual requests pooled across all
20 batches, not percentiles of 20 batch means. Time and memory units are
explicit. Observer storage, Scheme heap and shared process RSS are reported
separately from Rust retained capacity.

* Build and validation

Cargo owns Rust packages and dependency resolution. =build.ss= owns Scheme
compilation; the AOT build helper owns compiler discovery, archive production,
provenance and complete link receipts. Bazel owns the cross-language CI graph.
Downstream consumers validate and consume the receipt, without repeating
SDK, compiler or system-library discovery.

Compiler selection follows the configured Gerbil executable and paired SDK.
Ghostscript's unrelated =gsc= is rejected. Explicit =GERBIL_GSC= overrides
remain validated. OpenSSL, zlib and SQLite link receipts are admitted before
generation; missing required libraries fail the producer build.

Use the installed SDK environment and repository's Justfile:

#+begin_src text
just bridge-workspace
just bridge-lint
just bridge-actor-lint
just bridge-regenerate
#+end_src

Regeneration is required after Scheme/build-input changes; fingerprint
validation prevents stale committed SCM from qualifying a new source.
Linux/macOS CI keeps Cargo, single-processor Actor/AOT, Rust concurrency and
=bazel test //:ci= mandatory. SMP is a separately labeled unsupported gate.

The [[file:.github/actions/setup-gerbil/action.yml][shared setup action]] supplies immutable CI SDK prerequisites.
Consumers pin that action to a commit, rather than copying its installer.
The local benchmark workflow does not download or rebuild the installed SDK.
