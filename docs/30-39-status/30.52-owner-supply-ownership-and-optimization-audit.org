* Repository-grounded cost and protocol map

| Site | Code fact | Optimization target | Evidence boundary |
|------+-----------+---------------------+-------------------|
| Short publication | Reserved requests enter a fixed owner's FIFO | Delay owner commitment for independent short inputs | Spare capacity is not proof of owner readiness; published/rooted work must not be stolen |
| ServiceProducer | A boxed acquire future is created per new reservation, even with free credits | Keep pending reservation state with the owner; avoid unnecessary waiters | A saturated pipeline still needs a FIFO waiter |
| StreamJob | An already boxed Job is boxed again to retain one active permit | Retain the permit in the native retirement guard | Cancellation, exceptions and projection must preserve credit/root lifetime |
| Producer open fence | Weak Admission upgrade and global sender lock occur before and after acquisition | Cache registered identity with a close-fenced invalidation token in the opt-in path | Registration must prevent replacement; closing must invalidate at the original fence |
| Shared source | Head inspection, take and post-take inspection lock the source separately | Claim/reprice in fewer shared critical sections | Preserve heterogeneous work charges, readiness barrier and refunds |
| Capacity retirement | Each guard release publishes to the pool-wide watch channel | Coalesce retirement notifications without delaying credit visibility | Version/wait registration and close notification must remain lossless |

Arc cloning does not copy Scheme payloads. It retains cross-thread ownership.
Moving arbitrary native roots into Rust work stealing or replacing transport Arc
with Rc would violate the existing Send/owner contract. Local borrowing, fewer
temporary clones and fewer boxed envelopes are appropriate candidates. Cache-line
padding or weaker atomic orderings are not admitted without evidence. None of
these static costs explains all of a millisecond-scale non-CPU interval.

The priority is ownership and shared coordination first, then a shared short
claim protocol. Thread-count sweeps and another router score adjustment do not
repair early owner commitment. Stateless Rust inputs can remain unassigned until
a ready owner reserves their real credits; actor-affine/session work must remain
pinned. Claiming, cancellation, expiry and close must share a final admission
boundary. Already accepted Scheme jobs retain their owner and drain normally.
This identifies the next protocol work; it does not claim it is implemented here.

* Actual owner-local ownership candidate

The actual pool API now accepts =SchemeServiceSupplyAdmission= explicitly via
=submit_scheme_service_pool_stream_with_admission=. The ordinary API and fixed
owner stream retain =Queued=. No VM, optimization, routing, capacity, wake or
cooperative-budget default changes.

The opt-in =OwnerLocal= candidate starts with two related ownership changes:

1. Pending units and their future are one typed Pending state. A ready active/
   work/slot reservation needs no boxed future. If credits are unavailable, the
   normal asynchronous FIFO path is registered immediately; subsequent polls
   retain its place. A changed shared head cancels/refunds the old reservation.
2. Stream active credit is stored in CapacityPermit's existing native retirement
   guard. The original boxed Job goes directly into Scheme service admission;
   no second StreamJob box/vtable forwarding layer is allocated. Credit remains
   retained until projection or error cleanup returns native work/slot credits.

This removes the wrapper even when the pipeline is saturated and a waiter is
necessary. It does not make the whole request allocation-free: payloads, typed
jobs, result tickets and Scheme allocation remain. Native guards gain an optional
active-credit field in both compiled arms. Immediate attempts can add atomic/
Arc operations before falling back under contention. These are real trade-offs.
No custom unsafe allocator, new dependency, foreign scheduler, Scheme compiler
change or new build system is introduced.

A preliminary ready-only revision was frozen before adding native guard ownership.
Two five-block captures did not show stable CPU throughput/p99 benefit: CPU
throughput changed -0.45% and +2.58%; CPU p99 changed -6.76% and +8.06%. Mixed
throughput changed +0.90%/+0.17%. The first mixed control had a much larger tail;
its 57.1% p99 reduction is not promoted as a repeatable gain. This rejected
performance claim led to the ownership revision, not more repetitions of it.

* Registered identity and close invalidation

Inspection found an existing protocol guarantee: configure rejects capacity
replacement whenever the producer registration permit is held. Registration
also validates the capacity pointer under the admission table lock. A live
producer therefore need not upgrade Weak Admission and lock that whole table
again on every open check merely to establish the same identity.

The final opt-in path caches the registration's wake identity and an
=Arc<AtomicBool>= accepting token. Pool close stores false under the existing
admission mutex, immediately before removing the sender table. Semaphore close,
notifications and callbacks still run after unlocking. Backend readiness and
owner closed/failed flags remain checked before commitment. Deadline and
cancellation checks, native credit reservations and rooted ownership are unchanged.
A close racing after the final successful check drains that accepted work as
before. Only the bool token survives independently; it does not retain Admission,
owner channels, images or native roots. Queued retains its original table checks.

This removes global Admission reference-count writes and table locking from
OwnerLocal's repeated checks by using a registration invariant. It does not
remove shared-source or capacity-notification coordination. The invalidation
point remains in the existing close transition; no duplicate lifecycle model is
needed. The actual native close test covers both strategies simultaneously.
