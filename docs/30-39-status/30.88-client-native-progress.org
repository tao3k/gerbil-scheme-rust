#+TITLE: Planned arrival, native completion and client consumption
#+STARTUP: overview

* Contract and ownership

The opt-in client progress API records process-local monotonic instants for
planned arrival, the boundary before a deadline wait, actual submission attempt,
native completion and client consumption. Consumption means receiving the Rust
result before application processing; it is not the owner projection timestamp.
An optional predecessor observation describes a serial client's dependency.
Issuing means beginning the client attempt, before input preparation/admission;
it is not a claim that an owner has accepted or started the request.

=InstanceArrival::new= records the wait boundary. The caller-controlled path
retains its existing timer and calls =issue=. The explicit =wait_until_due=
path checks eligibility when polled: already-due work proceeds without another
timer; future arrivals await their existing Tokio deadline. Neither path
bypasses capacity, affinity, cancellation or final native entry checks. This
is not a Tokio task-priority promise or arbitrary-code preemption mechanism.

=AsyncInstanceTicket::wait_observed= consumes an =InstanceIssue= and returns
=InstanceObservedResult=, including an =InstanceClientProgress= timeline.
Native task failure is inside the observed result and retains its completion
and consumption instants. Transport closure, observation timeout and invalid
clock/order are outer errors. A timed-out or dropped observer does not release
an accepted task's native roots or credits prematurely; Scheme work drains
through the existing owner protocol. The tokens hold no native resource.
The caller must associate the issue token with the request it actually starts;
timestamps are observations, not security capabilities or cross-process clocks.

Rust only dispatches across fixed owners. The full Scheme VM, Actor/green-thread
execution, GC, exceptions, continuations and original native budgets remain.
Existing API behavior and all production defaults are unchanged.

* Additive client boundaries

Let =P= be the planned arrival, =W= the before-wait boundary, =I= actual issue,
=N= native completion, =C= client consumption and =Cprev= the previous client's
consumption (or =P= for the first request). The API checks =W >= Cprev= when
present and =I >= max(P,W)=, =N >= I=, =C >= N=.

| Component | Exact duration | Interpretation |
|-----------+----------------+----------------|
| Serial backlog | max(Cprev-P,0) | Predecessor already consumed late |
| Client before wait | max(W-max(P,Cprev),0) | Includes client processing and initial task-start delay |
| Deadline/resume | I-max(P,W) | Deadline eligibility to actual client resumption/issue |
| Native-ready latency | N-I | Existing attempt-to-native-completion interval |
| Delivery/consumption | C-N | Ready result awaiting transport/client observation |

Their sum is exactly =C-P=. The existing native construction/pending/projection
partition remains exactly =N-I=. Placement observed after an await can lag
native completion and is not used as a native execution boundary.

Deadline/resume includes OS scheduling and Tokio dispatch; it does not identify
the internal timer wake timestamp or prove runnable versus blocked OS time.
Serial backlog can propagate a previous delivery delay into later requests.
Owner completion spread remains an independent native progress metric. None
of these components alone establishes GC CPU cost or an OS root cause.

* Joint model refinement

Reuse the existing Tokio/fixed-owner/Actor/green-thread model. Planned,
deadline-due, timer-waiting and client-eligible sets refine the existing
submission, native projection, reply publication and client-observed states.
A serial successor becomes eligible only after predecessor consumption, even
if the predecessor is already native-ready. Independent owner work can continue
without that consumption. Waiting for a deadline holds no Tokio polling slot,
native root or capacity permit.

Tracked client arrivals are distinct from untracked bulk supply. Existing
accepted work, root retirement, budget grants and Actor phases retain their
owners. Canceling an unissued arrival removes only client timing state.
Early issue/consumption mutations must fail the existing safety relation.
An initial model failure incorrectly equated a Rust-projected value with root
retirement; the corrected relation permits ready or already-retired results,
matching the existing independent native retirement protocol. Its failure log
is retained rather than relabeled as success.

A subsequent random trace (seed =0x1bbdf=, 38 states) exposed an abstract generic
source accepting a tracked request before its caller issued it. The trace is
retained in machine-readable form. The refined caller workflow applies the
same issue-before-submit condition to tracked direct and asynchronous routes;
untracked bulk/legacy calls retain their original paths. A required bypass
mutation reproduces that invalid workflow. This is a valid-caller composition
contract, not a claim that an observation token changes every legacy admission
API. The actual benchmark creates its issue token before preparing or submitting
the corresponding request. =wait_observed= rejects a native completion timestamp
that predates the supplied issue token; callers remain responsible for correct
association, as stated by the API.

* What the added boundaries establish

Same-request top-ten totals by client-consumed latency have these shares:

| Candidate load | Serial backlog | Before wait | Deadline/resume | Native-ready | Delivery |
|----------------+----------------+-------------+-----------------+--------------+----------|
| CPU | 89.445% | 0.032% | 0.001% | 3.452% | 7.070% |
| Mixed | 30.597% | 0.032% | 40.728% | 14.426% | 14.218% |

The CPU top tail is dominated by serial predecessor backlog, not waiting for
the current request's already-elapsed timer. Removing that timer cannot repair
its predecessor's delivery/resumption delay. Mixed tails span several stages;
a single pre-issue bucket hid that distinction. These are additive same-request
shares; independent component p99 values must never be added to explain total
p99. The data do not identify why any particular OS thread was not running.

Source inspection further bounds delivery: =run_native= stamps native completion
after the job, error rollback and balance check, immediately before the delivery
callback. =ServiceJob::complete= forwards that callback to the Tokio oneshot
sender. Thus =C-N= includes the send/publication interval and client scheduling,
not exclusively Tokio's ready queue. Native resource retirement remains its
own protocol after result delivery. The model already separates native
projection, reply publication and client observation; the current timestamp
receipt does not independently stamp all three events. Do not label all of
this interval a Tokio wakeup or use client consumption to retire roots.

The next algorithm review must treat publication/client resumption and owner
completion fairness as distinct obligations, retaining the existing cooperative
oneshot waits. A bounded completion/registration policy must preserve capacity
ownership, cancellation and accepted-work drain. The failed timer-only fast
path supplies no evidence for disabling cooperative scheduling, changing Scheme
work budgets, or replacing the serial probe with easier traffic. Keep this
experiment explicit and the negative results available; improve the joint
progress protocol before another targeted capture. The historical watchdog
remains unattributed and its original cleanup unverified.
