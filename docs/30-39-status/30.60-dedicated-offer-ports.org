#+title: Dedicated offer ports and owner-side native admission
#+options: toc:nil num:nil

* Decision from the existing evidence

Report [[file:30.59-revocable-offer-native-entry.org][30.59]] establishes real withdrawal before native entry, but retains CPU
throughput -4.44%, mixed bulk p99 +12.45%, mixed admission p99 +717.73% and mixed
scheduled-probe p99 +433.61%. It is not general performance qualification.
The following source-level coupling remained in that implementation:

- Withdrawn mailbox markers still occupied the ordinary request channel.
- Every offer entry/reclaim could fan out producer signals, even when the source
  head price and eligibility had not changed.
- Offers reserved native active/work/request credits before a receiver ran,
  competing with short admission while doing no Scheme work.

The revised experimental ProgressFair policy separates those resources. It adds
no Rust execution scheduler, Scheme translation, SMP change or new default.
Scheme continues to own types, execution, Actors, green threads, continuations,
GC and exceptions inside each fixed-owner complete runtime.

* Resource and ownership protocol

| Resource | Authority and bound | What it does not own |
|----------+---------------------+-----------------------|
| Uncommitted pool source | Existing input count and aggregate declared-work bound | Scheme roots or native credits |
| Dedicated offer port | One Rust offer per destination owner | Ordinary inbox slots; native active/work/request credits |
| Shared short queue | Existing pending/active bounds and wake duties | Bulk offers or their notification storage |
| Ordinary request inbox | Existing bounded lifecycle/native/API messages | Bulk offer markers |
| Native entry and retirement | Actual owner acquires active/work/slot; retains them through projection | Transferable native state |

A live registration-issued weak endpoint still identifies the intended owner;
the data path does not look up an owner index in the pool lifecycle table.
Progress-based selection checks capacity hints but does not reserve them. Source
publication installs a Rust payload in an empty dedicated port, then notifies
only that target. An occupied port leaves the source head unchanged. An ordinary
full inbox cannot block this publication. Each offer still has a fresh identity
and a single Mutex<Option<Payload>>; payload includes only owned Rust input and
an advisory staged-work guard.

A received claim does not bind native ownership. If a ready owner withdraws the
payload, it immediately clears the matching port; old claim Arcs can neither
execute it nor remove a replacement. There is no stale-marker channel backlog.
Withdrawal drops an advisory hint, not native credit, so it does not synthesize
capacity-return notifications to the short queue. The source retains outstanding
offers and producer finality includes them; weak source/target/active links avoid
an offer/source/owner reference cycle.

Only a running owner attempts native acquisition. Failed immediate acquisition
leaves the same offer revocable and available to another ready owner. Successful
acquisition is followed by final lifecycle/deadline validation and the unique
payload take before M::construct can allocate Scheme roots. The staged hint
moves into the existing native permit guard until successful service submission;
native progress is charged before the hint clears. Constructor failure does not
permit migration or retry elsewhere. All entered graphs, continuations, accepted
exceptions and result roots stay on their original runtime until retirement.

Shared short claims and ordinary queued messages get their existing owner turn
before a dedicated bulk offer. That prevents a continuous offer stream from
overtaking ordinary short or lifecycle requests. An empty offer port uses an
atomic negative check; ordinary owners do not take a new empty-port mutex.
The mutex and fresh identity remain authoritative for publish/remove/close.

Native capacity is still shared once work enters. Existing FIFO partial
acquisitions, synchronous constructors/projectors, Scheme execution/GC, the
physical wake pipe and OS scheduling are not isolated or preempted by this
change. It therefore establishes admission/notification separation, not a
wall-clock short-latency guarantee or complete resource partitioning.

* Event-driven source signals and safe waiting

Moving an existing source request into a Rust offer does not create new source
work or change its head price. Only the target port receives that notification.
An entry/reclaim signals producers when the next source price differs or the
source is exhausted. Cancellation/close retain terminal source signals. The
native owner performs any source fanout after its first native call, not between
the ownership fence and construction. Simultaneous terminal observations can
still produce a bounded final fanout; this is not an exact one-signal theorem.

Existing semaphore waiter wakes and immediate capacity publication remain intact.
Projection never postpones returned credit behind a later application projector.
Before native wait the owner arms/coalesces, rechecks ordinary input, shared short
work and its offer port, then waits in Scheme. Publication after the recheck
writes a new wake; publication before it is visible in the port. A credit-blocked
offer also remains in the existing producer acquisition protocol, whose waiter
is woken by resource return. No timeout, cancellation or close requires a new
request to arrive before making progress.

Routing reads only the native residual word and conservative before/after staged
units. It does not load public diagnostic counters while ranking owners. Public
progress snapshots separately expose pending_offer and source_wake_signals;
benchmarks read those receipts outside their timed region. Source signals count
explicit producer signals, not all semaphore callbacks, syscalls or OS wakeups.

* Existing model and validation boundary

The existing owner_lifecycle model is refined in place. It now has explicit
one-per-owner offer slots and Rust-owned offers independent of native credit.
Entry alone charges the existing work/slot/producer ledger and creates roots.
Withdrawal/cancel/close clears the slot; received epochs reject stale claims.
New scenarios cover immediate reuse, short credit while an offer waits, same-price
entry without source fanout, terminal fanout, and resource-return notification
without another publication. Mutations for native credit held by an unentered
offer, retained stale slot and parking past a runnable offer must fail safety.
The original premature-progress-credit counterexample remains required.

The first sampled model failure is retained. Its trace re-admitted an already
offered Rust identity through offerShort because the old model had relied on
native workHeld as its uniqueness guard. Actual Rust code cannot duplicate the
single owned payload. The refinement adds explicit offer-ownership guards to
selection, staging and admission; it does not suppress the invariant. Resource
return transitions also make the existing registered-waiter wake obligation
explicit. Canonical finite source order, two owners and two offer incarnations
do not prove arbitrary-owner fairness or OS scheduling bounds.

Rust controls use real ports, pipes, channels and semaphores. They check ordinary
inbox independence, one-port capacity, stale identity versus replacement, entry
versus withdrawal races, publication versus close races, short native credit
while a bulk offer waits, expiry/cancel/close, and price/EOF notification rules.
The actual native fixture blocks a real target in an earlier constructor and
checks that its later offer holds no extra native credit. Cancellation/reclaim
clears that port before releasing the constructor; a different native owner
executes reclaimed typed Scheme work. The surrounding native contract retains
initialization failures, GC, multishot continuations, exceptions, backpressure,
accepted drain, zero external roots, descriptor return and image-file removal.

One initial native run exits 70 at the unchanged five-second watchdog. Its last
progress event was lost to libtest capture when the process exited. The same
binary's diagnostic no-capture run passes in 13.36 seconds, which does not explain
the original stall or establish an OS cause. Failure-only watchdog output now
bypasses capture so future exit-70 records retain the last real event. Passing
workloads perform no new diagnostic I/O. The failed run and both style-gate
failures remain private; no timeout or assertion is weakened.

* Final receipts and decision

The final implementation passes 42 instance units, warnings-denied Clippy, the
full native Scheme service contract plus both clock controls (13.84 seconds),
and a release benchmark build. The existing refined model gate passes in 27.06
seconds: scenario sets in both finite domains, 1000 sampled traces of 64 steps
at seed 42, and the required premature-credit-release counterexample. The later
entry implementation matches that existing atomic transition; the model is not
rerun unchanged or used instead of native qualification.

The first port prototype and its rejected capture are retained below. The final
revision additionally closes an actual reservation/withdrawal race. Immediate
acquisition and the unique payload take now share one entry critical section.
EntryCredits separately owns partial immediate credits, then converts to the
existing CapacityPermit only for an owned request. Acquisition uses nonblocking
semaphore attempts. Every partial return, waiter callback, application failure
and Scheme call occurs after the entry mutex is released. Active-only rollback
wakes its semaphore waiters without publishing a false native request/work
capacity event; asynchronous acquisition cancellation retains its existing full
publication rule. Common native work/slot attempts are reused rather than adding
a second reservation implementation.

A concurrent withdrawal winner now causes no target native-credit publication.
The race control checks that with real watch receipts. A separate real Notify
waiter probes the entry mutex during partial-credit return and requires it to be
unlocked. These are native-resource protocol controls, not timing assertions or
claims of measured OS latency.

Static review of this changed implementation finds a remaining ownership gap:
target entry reserves native credit before locking the offered payload. A
concurrent source withdrawal can win in between, causing the target to acquire
and return native credits without owning any request. Those speculative returns
still publish capacity events to the shared short facility. The source signal
counter excludes those events, so similar source counts do not eliminate that
path. The capture does not isolate the time spent in it or prove it caused every
regression. The next revision must make payload ownership and immediate credit
acquisition one critical section, with every credit return/callback outside that
section. This is an algorithm change, not an unchanged recapture.
