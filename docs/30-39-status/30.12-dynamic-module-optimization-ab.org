* Target and execution boundary

The acceptance comparison is =-O0= versus =-O2=. =-O1= is a diagnostic
intermediate, not an accepted substitute for the project's optimized build.
The dynamic module builder now defaults to =-O2=; =-O0= must be explicitly
selected for the control. No automatic downgrade or enlarged timeout is used.

These are two different compiler stages:

- The installed =gerbil/gxc-main.ss= describes =gxc -O= as "optimize gerbil
  source". Gerbil continues to produce Scheme/Gambit compiler input.
- =gsc -obj -cc-options "-D___DYNAMIC -O2"= selects C optimization for
  Gambit's generated native module objects. The existing compiler-owned ABI
  options and the existing GCC =-fno-gcse-lm= policy remain in effect.
- Native program startup/linker objects already request =-O2=. The installed
  SDK's configured C default (=FLAGS_OPT=" -O1"= on this machine) does not
  change this project's explicit =-O2= target.

The default Python library has four distinct Scheme VM images on four fixed
OS owner threads, with one active Scheme processor per VM. Tokio and Rayon
only distribute requests to those owners. Scheme owns its continuations,
Actor scheduling, green threads and GC. This is not four VMs sharing one
execution thread, nor four Scheme processors sharing one VM.

The previous 713ms figure was one owner's first expander/module load plus DSL
execution. It was not four calls per 713ms or a steady-state throughput result.
Cold open, first DSL calls, warm expansion and response projection remain
separate measurements. Cold initialization is still a real cost.

* Reproduction

The existing native build entry point accepts
=GERBIL_DYNAMIC_MODULE_OPT_LEVEL=0|1|2|3|s|g= (default =2=). Values outside
that set fail closed. C object names and fingerprints distinguish optimization
levels. =GERBIL_BUILD_CORES= uses the existing native build worker budget,
independently of runtime Scheme owner count.

Build each wheel with the same maturin/native pipeline and unchanged 120s cap.
Install the variants into separate Python environments; do not replace a live
VM's module mappings. The Scheme source, native type protocol and workload
stay identical. No handwritten compiler or Rust macro evaluator is used.

#+begin_src sh
just -- bridge-python-macro-ab /path/to/O0/bin/python --label O0 --require-quiet
just -- bridge-python-macro-ab /path/to/O2/bin/python --label O2 --require-quiet
just -- bridge-python-owner-ab /path/to/O2/bin/python --owners 4 --workers 2 --require-quiet
#+end_src

The macro script checks a hygienic =ledger-sum= use with a caller-side
=foldl= binding. Each owner first evaluates the real DSL. Then each timed
native request parses one expression, creates an expansion context, imports
the original plugin, checks one evaluation result, and performs 32 iterations
of either =core-expand= or =eval-syntax=. Thus the reported batch latency
includes the same context/import/correctness setup; it is not a timer solely
around the internal expansion loop. Python result projection/release is
reported separately. There are two warmup rounds and eight measured rounds,
with reversed operation order on alternating rounds, on all four owners.

The four-process diagnostic order was O0 / O1 / O1 / O0. It cannot establish
that O2 preserves performance. Native per-call deadlines remain five seconds.
The 32 samples per operation/process support only a small diagnostic tail
sample: their empirical p99 is effectively the observed maximum, not a
well-qualified production p99.

* Quiet-host dispatch admission

The dispatch script now observes active Gerbil executables, gxtest, Lean and
other high-CPU processes, rather than treating only compiler executable names
as host contention. =--require-quiet= records the blocking observation and
returns status 75 before opening the pool when the host is already busy.
Per-round observations remain outside the timed native calls. An initially
quiet host can still become contaminated; all round observations must be
reviewed before admitting a result.

The four-owner/two-dispatch-worker quiet-host attempt returned 75. No new
quiet-host direct/Tokio/Rayon comparison or optimum is claimed. The thread,
throughput, native-ready p99 and finite fairness matrix remains defined in
[[file:30.11-expander-startup-and-dispatch-benchmarks.org][30.11]]. Do not stop unrelated native acceptance work to manufacture a quiet
host. Runtime owner count and dispatcher pool size are separate tuning axes.
