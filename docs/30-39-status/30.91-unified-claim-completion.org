#+TITLE: Unified claim progress and native completion observation
#+STARTUP: overview

* Existing boundaries and the new protocol

The rejected completion-only experiment removes an observable claim event and
changes receiver scheduling. Fewer events do not establish lower latency or
better owner fairness. Reuse the existing bounded unassigned queue, placement
channel, final result channel, pending-input cancellation guard and fixed native
owners. No new scheduler, coordinator task, execution lease or queue is added.

=SchemeShortPool::submit_progress= returns =ProgressSchemeTicket= after bounded
Rust queue publication. It does not promise that an owner is selected. A running
owner still acquires all native/active/work credits at actual claim, with the
original affinity and capacity checks. The ticket uses a single observer for
claim and final-result events. =submit= and =submit_queued= keep their existing
contracts; all defaults remain unchanged.

One poll first checks the final receiver. If ready, it returns that typed value
without requiring a placement observation. Otherwise it polls the placement
receiver with the same task waker. A newly observed claim causes one immediate
recheck of final readiness, closing the claim/completion race within that poll.
If still pending, the already registered final receiver owns the next wake
obligation. It never self-wakes to spin, adds a yield, or repeats claim checks
once the intermediate receiver has been consumed.

Claim and completion published before the next task poll can share one runnable
opportunity. This is not a promise of exactly one waker invocation, OS wakeup
or scheduler resumption. The actual Tokio scheduler owns that deduplication.
Claim alone can never return a task value, acknowledge execution completion,
or release a Scheme root/native credit. Owner refill remains independent of
client observation, through the existing per-result service cycle.

* Types, clocks and cancellation

=InstanceProgressResult= retains independent task/timing results in =observed=
and bounded =InstanceClaimProgress= metadata. Claim owner and observation time
are optional: a ready final result can win before the claim receiver is polled.
That observation time is a client poll timestamp, not the physical owner-claim
timestamp or a Tokio-private runnable timestamp. =final_without_claim= records
that particular observation path, not a count of coalesced OS notifications.

The ordinary =AsyncInstanceTicket= layout and =wait_completed= remain unchanged.
The opt-in observation implementation is shared through a monomorphized receive
helper. Native-only callers still poll their original receiver; progress tickets
poll the combined receive future. Bench metadata labels these intervals as
=native-final= or =combined-claim-final=. The latter can include the one-time
claim poll and final recheck, so it is not an isolated raw-oneshot instruction
measurement. The planned/issued/native-ready/client-consumed partition remains
additive and is checked per request. A timing error must never discard an
otherwise successfully owned result.

=wait_completed= specializes the combined future with claim diagnostic recording
disabled at compile time. =wait_observed= explicitly records bounded claim
metadata. Neither adds a per-Scheme-handler callback or changes Scheme budgets.
Both retain the existing pending-input guard throughout the wait. Before claim,
timeout/drop can remove only the Rust payload and return its pending slot.
After claim, that guard is a queue no-op: native graphs, retained rollback and
credits drain on their owner regardless of the client. Close/error uses the
existing final channel, including when the placement sender has already failed.

Queue admission retains its existing deadline, checked at the owner claim fence.
Observation has its own finite result-wait budget. As with the explicit queued
API, no separate timer is added solely to remove an unpolled queued receipt;
owner inspection, observer timeout/drop or close resolves it. The original
placement-returning API retains its prompt placement-wait deadline contract.

* Joint model refinement

The existing Tokio/owner/Actor/green-thread model reuses the same unassigned
source, root/credit ownership, claim transition and final publication. It adds
one receive-registration set and a coalesced client-wake obligation set, distinct
from native-owner notification duties. Multiple ready events for one registered
observer can owe one runnable opportunity. No second Tokio polling slot or
native reservation is created. Registration checks already-visible claim/final
state, so notification before registration cannot strand a ready result.

Directed witnesses cover early claim then pending final output, both events
ready before resumption, final ready before receiver registration, final during
an active poll, cancellation, post-claim observer drop, owner refill before
client consumption, lost-wake mutation and premature-success mutation. Existing
Scheme lifecycle, continuation and ownership cases remain in the same model.
Finite safety checks cannot prove OS fairness, p99 or unconditional liveness.

* Actual native and transport checks

Real oneshot/waker controls check early claim without a result, already-ready
final output, failed claim, receiver closure and waker replacement on repoll.
Native fixed-owner tests exercise unclaimed cancellation/expiry, claimed
projection timeout with retained native credit, typed Scheme output, Scheme
exception and progress-ticket close drain. Existing GC, continuations and full
runtime tests remain enabled. Rust only dispatches across owners; complete
Scheme execution is preserved and this work is independent of SMP.

One native run exposes a separate qualification race: the prior publication
fixture treated returned work/request quotas as proof that its stream producer
registration had retired. The subsequent idle-only progress configuration
correctly rejects non-idle state. The failure has no simultaneous full capacity
snapshot, so the exact rejected capacity bit is not established. The fixture
omitted producer retirement from its quiescence predicate and now reuses the
existing bounded producer-retirement check before reconfiguration. The runtime
idle check, timeout and five-second meaningful-progress watchdog are unchanged.
This observed configuration rejection is not a watchdog attribution; preserve
its failed binary/image/source receipt and do not infer cleanup without a receipt.

* Attribution from the same capture and remaining boundary

Of 640 candidate short requests per load, claim is observed before native-ready
for 630 CPU and 605 mixed requests. Final readiness bypasses the intermediate
claim observation for ten CPU and 35 mixed requests. These path counts prove
that early observation remains possible; they do not count actual Tokio wakes.
All candidate requests initially suspend on the final receiver, while 35 CPU
and eleven mixed control requests find it immediately ready after placement.
Unified observation preserves a useful event but does not preserve the old
receiver scheduling history.

Mixed send duration p99 changes only from 5.791 to 6.375 microseconds. The
send-end to ready-poll-start lower-bound p99 increases from 149.250 to 336.542
microseconds; corresponding send-start upper bounds are 149.458 and 340.000
microseconds. Client-delivery p99 rises from 151.416 to 341.167 microseconds.
These intervals include transport and scheduler effects; they cannot distinguish
OS runnable wait from blocking and cannot establish GC CPU cost. The ten largest
candidate mixed client-total requests spend 81.95% of their summed elapsed time
in serial probe backlog and 9.93% in post-native delivery. These are sums over
those same tail requests, not a decomposition obtained by adding unrelated
percentiles. A late consumer also delays the next serial issue.

The native pending interval remains distinct from client consumption. Coalescing
claim and result readiness in one client observer is correct, but does not grant
an owner a bounded refill opportunity or ensure the client is promptly polled.
The next architectural boundary is the interaction between independent
capacity/owner-refill notifications and client runnable opportunities. Any
further protocol must preserve early claim observation and independently owed
native-owner opportunity, and use the existing joint state rather than treating
client consumption as native completion. The present data does not identify an
OS cause or justify another notification deletion, threshold change or favorable
repeat. The current observed-workload experiment is not production acceptance.
