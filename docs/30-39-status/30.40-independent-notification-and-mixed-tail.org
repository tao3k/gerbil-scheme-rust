* Concrete notification dependency

The coalesced transport first claims =pending=true= and then locks/writes its
pipe. A second publisher can return =Coalesced= while the first publisher is
paused before its write, leaving the native reader without a new byte. This is
not demonstrated root loss: the first publisher still owes a notification. It
is a latency dependency on that publisher's progress and legacy writer mutex.
A coalesced short receipt alone cannot identify whether its outstanding byte
was already written. The old model explicitly separates publication and delivery.

The actual real-pipe fault control injects a claimed-but-unwritten notification.
Coalescing leaves the pipe unreadable. With the old writer mutex still held,
the explicit short notification publishes a byte from another thread within
the unchanged five-second guard; ordinary bulk notification still coalesces.
Eight concurrent publishers deliver all 256 bytes. Actual kernel saturation
returns Full with readable input; closing the reader returns Failed without
SIGPIPE and marks the wake failed. These controls prove the transport property,
not a wall-clock p99 or an OS scheduling guarantee.

* Final actual API

=configure_scheme_service_notification_on(owner, SchemeServiceNotification::ShortIndependent)=
is explicit and leaves =Coalesced= as the default. Enqueue obtains the already
validated =SchemeServiceRequest::short_service= declaration. Those explicitly declared short
publications bypass pending-flag borrowing and the writer mutex, using an atomic
one-byte nonblocking write. Bulk publication retains coalescing. Close also
writes independently when this policy is selected. No source-name or payload
length heuristic classifies requests, and no Scheme object crosses owners.

The shared wake object owns the descriptor until all notifier references drop.
A full pipe already contains an observable wake; errors remain failures.
The existing clear/recheck inbox protocol is unchanged. Concurrent policy changes
may add redundant bytes but cannot remove accepted work. Unobserved requests
read no diagnostic clocks. No Rust green-thread scheduler, SDK patch, native
optimization downgrade or timeout extension is introduced. Scheme retains
Actors, IO/timers, native types, GC, exceptions and multishot continuations.

The unchanged Quint lifecycle model is reused for publication/delivery and root
conservation. It does not model publisher preemption, pipe buffering, kernel
wake timestamps or unconditional liveness. The real descriptor control is a
separate refinement obligation, not a claim that model success fixes latency.

* Disentangling time

Paired publication/write/dequeue timestamps and owner-phase overlap remain
opt-in. Enclosing GC CPU is now retained alongside GC wall time. These full
phase counters are not clipped CPU measurements for the overlapped request.
Old captures lacking GC CPU remain unknown rather than zero. A successful write
records kernel byte acceptance, not the instant the owner resumes user code.

Native select events distinguish timeout, signal and descriptor-ready returns.
An interval after a completed notification write but before native select returns
contains native wait/wake handling and possible OS descheduling. Without kernel
runnable timestamps and descriptor-specific readiness evidence it cannot be
split into isolated kernel delivery, SDK IO scheduling and runnable-thread delay.
Post-construction Scheme service waiting remains a separate cost.

The GC CPU clock scope itself required correction. In the admitted Gambit revision,
[[https://github.com/gambit/gambit/blob/ea114fc3d2f120abbe20393c1f9aeafdd3f8c89f/lib/os_time.c#L807-L822][process time uses getrusage(RUSAGE_SELF)]], and
[[https://github.com/gambit/gambit/blob/ea114fc3d2f120abbe20393c1f9aeafdd3f8c89f/lib/mem.c#L6954-L7065][GC accumulates those process-time deltas across its interval]]. The admitted
archive's os_time object independently confirms argument zero at the getrusage
relocation in process_times. The FFI exposes these SDK values separately from
CLOCK_THREAD_CPUTIME_ID for the owner. GC CPU is therefore process CPU observed
during a VM's GC interval, including other VM/Rust threads; it is not isolated
collector or owner CPU. It must not be summed across owners or subtracted from
GC wall to derive OS delay. Public Rust field documentation now states this
scope. No SDK counter is modified or replaced by a guessed value.

* Final paired GC/notification diagnostics

One final observed pair completed all 40 samples and clean native shutdown.
Every candidate short probe had a real Written receipt (1,280 across both loads),
so candidate tails do not borrow another publisher's pending notification. This
is diagnostic evidence, not a third unobserved throughput acceptance capture.

In candidate slowest-one-percent observations, publication-to-dequeue occupied
70.6% of CPU-load actual latency and 99.2% of mixed-load actual latency. On mixed
load, wait overlapped 91.0%, submit 8.1% and advance 0.1%; native select overlapped
63.8%. All analyzed tails had complete retained history. The corresponding
control mixed coverage was queue 64.8%, wait 49.5%, retire 15.3%, select 40.7%.
These are matched interval overlaps, not subtraction of unrelated p99 values.

- A mixed candidate probe took 28.900 ms. Its notification completed in about
  two microseconds, but it spent 28.516 ms overlapping native wait; the enclosing
  wait used 0.220-ms owner CPU and had zero GC. A timeout requested 0.952 ms and
  returned 14.578 ms after publication; another native select began about
  13.899 ms later. That intervening gap is not select time and cannot be labeled
  collector work. Kernel scheduling versus SDK IO/thread resumption remains
  unseparated; a successful write does not prove which descriptors were selected.
- A second mixed probe took 23.391 ms, with 23.250-ms wait overlap, 0.064-ms
  enclosing owner CPU and zero GC. Its Written receipt preceded a descriptor-ready
  select return about 23.198 ms after publication.
- A separate mixed probe overlapped 10.287 ms of an 11.246-ms advance phase. That
  phase recorded 11.197-ms GC wall, 0.995-ms owner CPU and 1.995-ms SDK GC process
  CPU. The process counter exceeding total owner CPU illustrates the scope issue;
  it does not mean the collector computed for 1.995 ms on this owner. The owner
  phase contains at least about 10.251 ms without owner CPU, but attribution to
  kernel scheduling, collector blocking or another cause is not established.
- A CPU-load submit phase similarly recorded 32.944-ms wall, 1.071-ms owner CPU,
  32.871-ms GC wall and 4.931-ms SDK GC process CPU. The probe overlapped only
  12.135 ms of that phase; full counters are not assigned to the clipped overlap.

The publication dependency is directly repaired and mixed short tails improve
in the two stable captures. Remaining tails are predominantly native wait with
little owner CPU, plus distinct GC-overlapping phases. They are not evidence
that the Scheme computation must be moved to Rust. CPU throughput/fairness
regressions prevent a general performance promotion; further work needs actual
kernel/descriptor or GC blocking evidence rather than another unmeasured default.


* Native verification and retained failures

The final three real-pipe controls passed. The four-VM actual service fixture
passed in 5.66 seconds total with original per-progress deadlines: native types,
GC, same-Actor multishot continuations, exceptions and panic recovery, class
routing, backpressure/abandonment, host wake and close. Four owners joined,
external roots were zero, copied files were removed and descriptors returned.
This is capability/resource acceptance; its wake timings under compiler activity
are not a short-latency performance result.

Initial development failures are retained: the new test used a forbidden parent
glob import; a saturation control incorrectly assumed writing 64 KiB was enough
to observe Full; an unobserved warmup treated null diagnostic entries as wake
failures. Repairs use explicit imports, actual observed capacity within a finite
safety guard, and observation-only receipt checks. The failed warmup produced
no timed samples or verified cleanup and is not admitted as a completed capture.
No gate or performance expectation was weakened to convert a failure to success.
