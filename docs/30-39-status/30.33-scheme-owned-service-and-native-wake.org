#+TITLE: Scheme-Owned Async Service and Native Owner Wake Protocol
#+DATE: 2026-10-21

* Implementation scope

PR #18 continues from =cfbc10c=. Its exact-head CI run
[[https://github.com/tao3k/gerbil-scheme-rust/actions/runs/39565425105][39565425105]] completed successfully: all six active jobs passed; SMP was
explicitly skipped. The new service described here is opt-in and has separate
local/native/performance and subsequent exact-head CI gates.

This implementation removes the requirement that an asynchronous Scheme task
finish before its host owner can accept another request. The task is a real
Scheme computation, with its own Scheme objects, exceptions, Actor state and
continuations. Gerbil still compiles through Gambit C with the existing =-O2=
chain. No Scheme computation is translated into Rust.

Rust owns cross-instance admission, native conversion/projection, slot/work
permits and owned result channels. Scheme owns the pending queue, worker
selection, Actor execution, timers, native event wait and completion signaling.
A requested Actor lane is an application destination, not a Rust green-thread
scheduling policy. The existing ordinary entry remains synchronous; opting into
a service does not silently convert unrelated native calls into async jobs.

* Actual Rust API

An unsafe =IsolatedProgram::with_scheme_service= descriptor admits one build-owned
rooted unary command export implementing =make-gerbil-rs-service-endpoint=.
It is resolved before SDK initialization and held as a private function pointer.
It cannot also be the ordinary entry, a public additional export or a finalizer.
The ordinary safe =NativeSession::call_export= lookup does not expose it. This
keeps lifecycle/root commands from bypassing the service's admission protocol.

=InstanceDispatcher::submit_scheme_service_backpressured_on= accepts a
=SchemeServiceRequest=. Its constructor builds a native =NativeRoot= on the
fixed owner, and its projector returns only a =Send= owned Rust value. Temporary
Scheme roots remain non-Send. =NumericServiceBatch= reuses the actual existing
native bulk constructor and bounded batch projector; it is not a second codec.
There is no JSON payload boundary or VM-less fallback.

Each request declares work units. The shared owner slot/work reservation is
held through Scheme completion, result projection and native root balance.
A delivery timeout or abandoned receiver does not cancel accepted Scheme work,
free its pending graph, or return its capacity early. Arbitrary custom Rust
constructors/projectors retain the existing callback obligations; work units
are declarations, not predictions of CPU or heap use.

Independent requests may use any available Scheme service worker on their owner.
A stateful session or retained delimited continuation requests a stable
=SchemeServiceLane=. Rust validates that address against the initialized worker
count; Scheme keeps it on the corresponding persistent Actor and preserves its
serial mailbox order. Scheme state is never moved across heaps or Actors.
Application continuations keep their application-owned delimiters; no
continuation may escape a foreign frame or finalize the owning VM.

The native continuation oracle resumes the same captured payload twice across
separate host returns and GC, checks Scheme current-thread identity and dynamic
bindings, and checks balanced =dynamic-wind=. An owner alone is not sufficient
Actor affinity; this native check is separate from the finite ownership model.

* Versioned native command boundary

The private rooted unary payload is a native vector containing an s64 header
and, where required, a native Scheme payload. It is protocol metadata, not the
public Rust representation of application data.

| Operation | Header/data | Ownership and result |
|-----------+-------------+----------------------|
| 0 open | read fd, write fd, accepted-task limit | Success =[0,1,workers,limit]=; version/count/limit checked before readiness |
| 1 submit | explicit lane or -1, native payload | Store a strong job graph, return a positive opaque owner-local identity |
| 2 take | job identity | Require done, remove table entry, return a temporary rooted result or caught Scheme failure |
| 3 ready | none | Scheme yield, then ready identities; result graphs remain strong until take |
| 4 wait | real host producer deadline in microseconds, or zero | Scheme condition-variable/port wait; zero means no timer |
| 7 prepare-close | none | Stop service admission and invoke the Scheme application drain hook |
| 5 drain/close | none | Join accepted Scheme work, clear results, join workers/watcher, close ports and application resources |

The reusable endpoint tracks partially opened application resources. Its hooks
initialize, prepare and close application-owned services entirely in Scheme.
Preparation/close is idempotent. The order qualification adds separate declared
reference/observation exports; these are fixtures, not public service commands.

* Wake protocol and backpressure

Each opted-in owner has its own pipe. The read side stays owned by the native
owner while Scheme holds its input-port duplicate. Scheme also owns an output
port used to wake and join its watcher during close. Host writers are
nonblocking; one pending atomic flag coalesces notifications. A full pipe is
already a readable wake source. Standard descriptors remain untouched, including
when the host intentionally left them closed. Descriptor RAII, close-on-exec
flags and the existing Rust 1.85 requirement are retained.

Enqueue and notification are distinct publication steps. After processing a
native completion/request, the owner clears the host pending flag and rechecks
the inbox before entering Scheme's wait. Enqueues before that clear remain in
the inbox; later enqueues publish another pipe byte. Scheme's watcher and job
completion paths signal the same Scheme condition variable. Ready jobs or a
retained host notification prevent sleep. There is no Rust idle polling timer,
forced yield loop or release of work credits merely because Scheme is waiting.
A real existing producer admission deadline may supply a timeout to Scheme's
condition-variable wait; it does not schedule Scheme task timers.

Normal close publishes the host close fence and wake, drains already-enqueued
host requests, then prepares the Scheme application and drains accepted jobs.
No new submission can cross the fence. Task errors are terminal task outcomes;
peers continue. Construction errors before Scheme admission reject only that
request. Rust projection panics unwind temporary roots and use the existing
retained-root rollback. Protocol/transport errors fail remaining requests and
attempt Scheme drain. Unverified quiescence produces a failed shutdown receipt
and quarantined heap/code, never a successful SDK cleanup claim.

A native Scheme table roots pending inputs and completed results. Taking a
result transfers protection to a temporary external native root until projection
finishes. External root-ledger count zero while tasks are pending therefore does
not mean the service/VM is absent: the internal graph is strong. The acceptance
test forces GC while real handlers are blocked, then verifies their results.
All four owners reach zero external roots, joined children, removed copied image
files and returned pipe/port descriptor counts after normal drain. This does
not claim general RSS convergence or a newly qualified image-unload policy.

* Reused model and native gates

The existing =specs/owner_lifecycle.qnt= is extended, not duplicated. It adds
pending/ready service jobs, logical service-root protection, an inbox and
notification publication/park/recheck state. Logical protection spans the
internal job table and the temporary root during take/projection. Existing
completion releases capacity only after projection; observation timeout does
not. Existing close/code-quarantine boundaries are retained. The model starts after
successful owner admission: native initialization rollback, GC, Actor semantics
and successful joins remain obligations requiring executable checks.

The existing Rust model gate passes 27 scenarios in each of two finite domains,
1,000 sampled runs per domain up to 64 steps, and nine expected safety mutation
counterexamples including missing-root protection and parking without an inbox
recheck. This is finite safety evidence, not an OS scheduling/liveness proof.

The native service target checks partial application-open failure, a fully
opened service initialization exception, private lifecycle access, same-Actor
multishot continuations, forced GC, Scheme errors including a false exception
value, Rust construction/projection panics, real batch error/recovery, abandoned
and timed-out receivers, repeated short requests while long tasks remain latched,
full slot/work admission timeout, and prepare/drain/close with descriptors returned.
The existing native capacity, dispatcher-fault and producer targets remain
separate regression gates. Five-second native progress/observation gates are
unchanged. Model success is not substituted for these native checks.

* Directed comparison contract

One pair uses the same four VMs, native image, two Tokio workers, four request
slots, work budget 32, batch eight, quantum one, four Scheme service workers,
and four Actor workers per batch. Both arms reuse the same native constructor,
order handler and bounded projector. The control calls a synchronous reference;
the candidate uses the actual asynchronous service API. Both arms enable the
same wake/service infrastructure. This isolates the new async execution boundary;
it is not an end-to-end comparison against the old default Python backend.

Each full sample uses 8,192 48-line orders and 64 four-line short probes at the
same nominal 500-microsecond schedule. CPU and mixed inputs are unchanged;
mixed handlers still perform the real one-millisecond Scheme wait. Ten samples
per arm/load alternate AB/BA. VM state identities remain fixed throughout.

Work 32 is explicit and identical in both arms, not a default change. Work eight
would permit only one batch of eight per owner; freeing those credits on sleep
would break the retention bound. These results must not be spliced into the
older work-eight baseline as if only implementation changed.

Native owner completion clocks define bulk throughput and service p99. Short
latency includes its actual admission start through native completion; scheduled
latency is also retained. Pending-before-projection spans include Scheme work,
queueing/waits and owner interleaving, not pure CPU execution. Fairness retains
per-owner progress at first owner finish, finish spread, Actor progress and probe
overlap; faster bulk completion can reduce overlap without proving starvation.
Startup is outside the timed samples and separately observed. No thread/VM/QoS
matrix or automatic policy/default promotion is introduced.
