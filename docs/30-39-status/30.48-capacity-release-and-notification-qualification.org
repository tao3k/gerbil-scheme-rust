#+title: Capacity release and notification qualification
#+date: 2026-10-22

* Decision and evidence boundary

Retain Watch admission notifications and all defaults. A new ArmedNotify
prototype reduced a component CPU cost but regressed CPU-workload throughput
in both unobserved captures. It was withdrawn, including its API, tests and
benchmark mode. The retained change measures the previously unobserved capacity
release boundary and calibrates optional OS/thread-CPU observation.

This does not close exact kernel scheduling attribution or establish a p99 fix.
Rust still distributes across independent fixed-owner Scheme runtimes; native
Scheme types, GC, continuations, Actors and exceptions remain intact. No SMP,
Scheme-to-Rust translation, SDK change or default change is involved.

* Actual blocking and the missing boundary

An own-process stack sample reached =CapacityPermit::drop= through Tokio
Watch BigNotify into a pthread mutex wait. Producer-open mutex contention is
separate; the earlier epoch-fence experiment remains rejected (report 30.47).

Retire enclosed projection/completion, but the retained permit destructor ran
after that observation closure. Release now encloses slot/work return and host
notification after projection. Existing five phase indices remain unchanged;
Release is sixth. Observation remains opt-in, with no new clocks when disabled.

The prototype replaced only the host capacity-generation event transport.
An armed Notify future was created before scanning, including cancellation,
close and generation-swap handling. Native service, quotas and supply bounds
were unchanged. Protocol tests passed; that did not predict performance.

* Directed same-VM, same-load comparison

Each capture reused the same four live VMs between arms, with two Tokio threads,
native O2, native typed payloads, 8192 orders of 48 lines in batches of eight,
and 64 four-line short probes with nominal 500 us spacing. Each owner had four
request slots, work budget 32, and at most three active service jobs. Pooled
staging was bounded at 128 callbacks / 1024 work units; feed one, coalesced wake
and progress-aware routing were identical. Native wake readback was NativePort
on all four owners. Original request/progress limits were unchanged.

Watch is A, ArmedNotify is B. Both unobserved captures contain 40 samples and
clean four-owner shutdown, zero roots and removed files. Diagnostic sampling
is a separate capture, not pooled into performance claims.

Unobserved CPU throughput fell 30.94% and 24.62%. Mixed p99 changed in opposite
directions. The observed CPU result has the opposite sign: instrumentation and
host variability preclude a general performance conclusion from that capture.
The prototype is rejected, without changing defaults or discarding negatives.

Release mean CPU per call fell from 714 to 445 ns for CPU load and 749 to
494 ns for mixed load in the diagnostic capture. Mean Release wall time was
1.69 -> 1.56 us and 1.36 -> 1.30 us; no Release GC delta occurred. An overlapping
Watch Release span reached 0.720 ms wall versus 0.010 ms CPU. This is a genuine
blocking path, but these observations do not explain the much larger native
wait/GC-wall tails or justify adopting the transport change.

* Wall time, CPU time and OS attribution

Thread CPU is measured separately from wall time. GC wall duration overlaps
these enclosing owner intervals. SDK GC CPU accounting is process-scoped;
never sum it across owners or subtract it from wall to infer collector-only CPU.
RUNNING point samples include running/runnable states and cannot distinguish
on-core execution from time waiting for dispatch.

The retained observed smoke ran eight controls before warmup on the same four
initialized owners. Four concurrent 20 ms sleeps used 0.007--0.015 ms thread
CPU over 20.37--26.92 ms wall. Four CPU-demanding Rust loops each consumed
20.005--20.012 ms CPU over 41.10--55.84 ms wall. GC wall and collection counters
were bitwise unchanged. The controls demonstrate non-CPU wall time without GC;
they do not measure exact runnable wait or replace native Scheme workloads.

A System Trace attached only to the owned benchmark PID reached its five-second
collection limit but hung finalizing. The recorder was stopped at its 90-second
watchdog; the benchmark independently completed 40 samples and clean shutdown.
The incomplete trace was retained privately. Read-only export failed with
=Document Missing Template Error= (exit 10). No usable exact kernel scheduling
data was recovered, and the failed trace is not a profiler acceptance result.

Consequently routing/supply changes cannot yet be justified by an asserted
kernel runnable-wait duration. The next targeted attribution gate is usable
per-owner running/runnable/blocked intervals correlated with native wait and
Release spans; keep real blocking and descheduling distinct. Do not repeat the
unchanged failed capture or tune routes from sparse point states alone.
