* Updated build admission

The user authorized a longer build when the compiler has genuine progress.
The earlier 120-second timeouts in [[file:30.12-dynamic-module-optimization-ab.org][30.12]] remain historical failures under
that earlier rule. They are not rewritten as successful builds. The current

* Observed cause and minimal change

The SDK declares =___SINGLE_HOST= with an unlimited =___SINGLE_HOST_LIMIT=.
Gambit's generated =contract~10.o1.c= declares 5034 labels. The earlier native
sample found all 801 recorded samples under GCC's =pass_reload::execute=,
with LRA live-range, constraint and spill work. That sample locates an
expensive compiler stage; it does not prove that every slow module has the
same cause, or quantify the separate effect of host contention.

The extended attempt exposes compiler-written =.ira=, =.reload=, =.i= and
=.s= progress through the existing native process monitor. Completed O2
objects advanced from 91 to 99, 123, 129, 138, 148 and 151. One observed
=contract~10= reload dump grew from approximately 0.5MB to 222MB, and the
compiler subsequently completed its 1,238,552-byte object. A later sample
attempt found that compiler process already gone; its object existed. This
is evidence of finite compilation for that previously interrupted module.

The fixed 120-second wall cutoff therefore interrupted real compilation.
It was insufficient evidence for a runtime deadlock. Existing host activity
and compilation diagnostics affect wall time; this is not a quiet-host build
speed comparison.

The minimal source change adds =GERBIL_BUILD_OBJECT_PROGRESS=1= to the
existing native build helper. It requests allocation dumps and temporary
compiler products after computing the code-generation input fingerprint.
It does not enable broader GSC verbosity, invalidate previously matching
optimized objects, change Scheme compilation, or substitute a compiler.
Only compiler-written growth generates progress events; polling does not.
The existing native process helper removes owned diagnostic products after
each compile. Interrupted attempts may leave their diagnostic files behind.

Dynamic C optimization stays at =-O2=. The existing =-fno-gcse-lm= policy
is unchanged; no additional optimization subpass was disabled. The SDK's
C-host partitioning limits were inspected but not changed. Gambit's
[[https://github.com/gambit/gambit/blob/v4.9.8/include/gambit.h.in][upstream header]] documents that C-host choice separately from VM/thread ownership.
The observed generated parts had no label count above the installed
=___OPTIMIZED_MODULE_LIMIT=20000= threshold.

* Runtime and comparison boundary

The actual Python API enters four independent Scheme VM images on four fixed
OS owners. Rust direct/Tokio/Rayon modes distribute tasks to those owners;
Scheme retains its macro expansion, interpreter, GC, continuations and Actor
scheduler. Runtime operation deadlines and result/error semantics are unchanged.

The O0 control is the wheel recorded in 30.12, with exactly the same Scheme
macro fixture and runtime request protocol. Native compiler diagnostics are
not part of timed Python execution. The O2 wheel is tested in its own Python
environment. Each macro comparison uses a new process, all four owners,
identical hygienic source, iteration count, warmups and measured work count.
The process order is balanced as O0 / O2 / O2 / O0.

A completed comparison on a busy host is observational. It cannot establish
performance preservation or an optimum. All per-round negative and noisy
results must remain. Native-ready batch tails exclude Python projection;
32 batch samples per operation are diagnostic tails, not a qualified
production p99. The direct/Tokio/Rayon thread sweep requires explicit quiet
host admission, including compiler, Gerbil, Lean and other high-CPU activity.

* Native diagnostic verification

The owned diagnostics scope passed all 14 tests, including actual GCC
byte-for-byte parity between O2 objects compiled with and without allocation
observability, cleanup, real-byte event forwarding, stalled-file suppression,
partial/nonblocking writes and child stdio isolation. The native parity test

=--include-ignored= invocation also selected an existing linker test without

or ignored-test requirement was weakened. Strict helper Clippy is recorded
separately in the accompanying receipts.
