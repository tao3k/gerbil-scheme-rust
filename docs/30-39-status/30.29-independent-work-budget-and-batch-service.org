The observed gap is structural: four request slots at batch eight can hold 32
bulk items per owner, while four slots at batch one hold only four. Internal
Scheme yields do not let a short Rust queue entry enter the active native call.
This refinement separates request count from declared work and measures the
remaining indivisible service turn. No thread/VM matrix is added.

* Admission protocol

=configure_owner_budgets(slots, Some(work))= creates independent per-owner bounds.
The slot count must fit the existing native queue; work must be positive and fit
the semaphore counter. =configure_owner_capacity(slots)= retains slot-only behavior.
No capacity mechanism is enabled by default, and existing Python mode selection
is unchanged.

Every native numeric batch method, including synchronous, asynchronous and
profiled methods, charges its actual item count. Generic native and byte methods
charge one unit; applications can explicitly declare a different weight with
=submit_native_weighted_backpressured_on=. A declared work unit is not an inferred
CPU cost, byte count, GC cost or prediction of an arbitrary Scheme program.
An indivisible batch larger than the enabled work budget is rejected, never
silently split or left waiting for an impossible reservation.

Backpressured admission acquires work before a request slot under one finite
shared deadline. Every waiting path uses this order; no waiter holds a slot while
waiting for work. Tokio can partially allocate a multi-unit reservation. Cancelling
or timing out before acceptance returns that partial allocation. Immediate methods
try both resources without waiting and retain =QueueFull= behavior.

Both resources travel with the accepted native request through actual execution,
result delivery and abandoned-reply rollback. Receiver timeout does not release
either resource. Quiescent reconfiguration checks both resources; stale generation
identity cannot enqueue into a replacement budget. Closing wakes waiters on both
resources and drains already accepted Scheme work. Semaphore close, permit release,
request destruction and foreign wakers stay outside the admission mutex.

FIFO weighted admission can delay a small request behind a large reservation.
The pool bounds reserved/accepted work, not the total number of external caller
futures. The existing flow driver also bounds pending reservations per owner and
invocation. Neither mechanism establishes an arbitrary-client latency SLO or a
starvation theorem.

* Scheme service boundary

A numeric batch remains one complete native turn, with unchanged whole-batch
exception acknowledgement/drain and Actor/green-thread scheduling. Scheme retains
macros, arbitrary procedures/types, continuations, dynamic-wind and GC. Rust
only handles cross-instance admission, dispatch and lifetime. The SDK, native
compiler path and Scheme source are unchanged.

The observed owner service span is entry to native completion:

#+begin_example
service = native construction + Scheme execution/scheduling/GC
        + native result projection + root retirement/balance checking
#+end_example

Final receiver delivery and capacity return follow that marker. The profiled API
also records API-entry-to-owner-entry and Scheme-entry-to-return spans, plus GC
counter deltas. Diagnostics between markers and OS preemption remain included;
these are wall-clock observations, not pure CPU attribution.

With work eight, a batch cannot exceed eight declared items and the owner cannot
hold more than eight reserved/accepted item units at once. This bounds the work
count, not arbitrary handler duration. A temporal bound additionally requires
application bounds on each handler, GC and host scheduling. No hard preemption,
forced continuation migration, weakened exception semantics or hidden timeout
increase is introduced. Scheme-internal yields cannot shorten the Rust queue's
non-preemptible service turn.

* Directed same-VM experiment

Only one AB/BA pair is run: four native VMs, two Tokio workers, request slots four,
batch eight, work budget 32 versus eight. Both arms use the same opt-in profiled
native batch API and the identical independent invoice oracle. Historical
unprofiled rates are not directly comparable to this new executable.

Each full sample uses 8,192 bulk orders of 48 lines and 64 short four-line probes
at a nominal 500-microsecond interval. The probe producer is closed-loop and keeps
its original scheduled timestamps after a delayed result. Report both scheduled
p99 and actual-entry-to-delivery p99; nominal wake lateness includes inherited
lateness and runtime scheduling, not pure Tokio/OS wake cost. Per-row subtraction
is done before taking quantiles. No quantiles from different rows are subtracted.

Bulk inputs are generated outside timing; payload cloning, native work, result
projection and the independent oracle remain inside elapsed time. Probe fixture
construction/cloning is inside its admission span. Each arm warms 256 orders;
five forward/reverse blocks yield ten measured samples per arm. Reconfiguration
requires all slot and work credits to return; native VM identities are unchanged.
Each owner exercises a real bad eight-item Scheme turn and subsequent recovery.
The five-second startup/progress/observation gates remain unchanged.

* Native and finite-model controls

The real =owner_capacity= and =owner_dispatch_faults= targets pass. Weighted controls
cover zero/oversized charge rejection, item charging on old batch APIs, exhausted
work with free request slots, partial multi-unit cancellation, admission timeout,
receiver timeout retaining both resources, panic recovery and close waking a
partially allocated waiter. The existing controls retain forced-GC multi-shot
continuations across FFI, dynamic-wind and clean four-owner joins with zero roots
and removed copied files. Injected panic diagnostics remain in the external log.

The existing =owner_lifecycle.qnt= is extended rather than replaced. Job 1 has
weight eight, the other jobs weight one. Full work reservations before slot
acquisition are represented separately from slot reservations and accepted work.
Both finite domains pass 19 scenarios, 1,000 sampled traces of at most 64 steps,
and the six existing mutation counterexamples. Tokio's partial allocation and
waker mechanics remain native/code checks, not model conclusions. No new symbolic,
unbounded safety or liveness theorem is claimed.

* Matched results and retained negatives

Two complete cohorts use the same frozen executable and native image. Each has
40 samples, four result summaries, four real Scheme fault/recovery controls and a
clean four-owner shutdown with zero roots and removed files. No failed performance
capture is discarded. Host snapshots show concurrent compiler activity; these are
shared-host paired observations, not a quiet-host certification. The A cohort
also has a 79.691 ms CPU batch service outlier. No production default is promoted.

All times below are milliseconds. Throughput is bulk orders per second; each arm
has ten samples. The complete-workload rate also includes the fixed probe schedule
and is retained separately in the external captures.

** Service durations and handoff cost

| Cohort/load | Bulk service p99 32 -> 8 | Observed bulk service max 32 -> 8 | Bulk Scheme span p99 32 -> 8 |
|-------------+--------------------------+----------------------------------+-----------------------------|
| A / CPU | 0.900 -> 1.037 | 4.892 -> 79.691 | 0.198 -> 0.476 |
| A / mixed | 8.433 -> 6.167 | 25.818 -> 32.146 | 7.748 -> 5.637 |
| B / CPU | 0.439 -> 0.428 | 1.488 -> 1.175 | 0.298 -> 0.073 |
| B / mixed | 3.341 -> 3.367 | 7.880 -> 10.387 | 3.252 -> 3.244 |

In mixed cohort B the bulk service p99 is essentially unchanged while actual-entry
probe p99 approximately halves. The primary improvement in that cohort is reduced
waiting, not faster execution/GC. The observed maxima are finite receipts only;
none is an enforced wall-clock bound.

There is a measurable pipeline cost. Reconstruct each owner's entry/completion
intervals for both bulk batches and probes. Restrict to the common bulk-active
window, from the latest first bulk entry to the earliest last bulk completion.
The gaps outside these native service intervals include result delivery, credit
return, queue/handoff and host scheduling. They are not pure Tokio time or an
OS-idle counter. Probe-only tails after bulk completion are excluded.

| Cohort/load | Median outside-service gap fraction, work 32 -> 8 |
|-------------+----------------------------------------------------|
| A / CPU | 9.57% -> 32.69% |
| A / mixed | 0.90% -> 13.23% |
| B / CPU | 4.92% -> 25.30% |
| B / mixed | 0.18% -> 2.74% |

With work eight, a full eight-item batch exhausts the work credits. Another full
batch cannot enter the owner queue until real completion returns credits and its
Rust producer resumes. The common-window gaps increase in both cohorts. This
identifies a pipeline/handoff cost consistent with the CPU throughput loss; the
shared host prevents assigning all of it to Tokio scheduling alone. It would be
incorrect to claim that merely shrinking the budget solves the full performance
problem, or to hide the loss by altering the default.

|-------------+-------------------------------------------------------+------------------------------------------------|
| A / CPU | 848 -> 624 of 2048 | 35 -> 64 of 64 |

| B / mixed | 1752 -> 1648 of 2048 | 56 -> 64 of 64 |

All short probes complete before bulk finishes in the mixed candidate samples.
Bulk-owner progress is not uniformly better: mixed cohort B regresses, and CPU
cohort A also regresses. The Scheme Actor peer minimum is zero in mixed samples
in both cohorts; the CPU minima are zero in A and one in B. No internal Actor
fairness improvement or starvation-freedom result is claimed.

The protocol is implemented and natively exercised. The performance policy stays
explicit and unpromoted. The next architecture boundary is maintaining bounded
Scheme-native service work while avoiding a Rust replenishment gap after every
full turn. It must preserve whole-turn exception/drain, continuation ownership
and Scheme scheduling. More Rust dispatch threads or a larger blind batch do not
remove the measured service boundary. This report does not claim that future
refinement has already been implemented or accepted.
