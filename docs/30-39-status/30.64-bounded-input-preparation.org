#+title: Bounded Rust input preparation and ready-result retirement priority
#+options: toc:nil num:nil

* Decision and scope

[[file:30.63-native-owner-service-cycle.org][30.63]] retains the NativeCycle negative results. Its input opportunity may
construct a fresh Scheme bulk payload between two already-harvested results.
This experiment separates Rust input acquisition from native construction and
compares the previous NativeCycle directly with PreparedCycle on the same VMs.
Snapshot remains the default. This is an explicit experimental policy, not a
replacement for the complete Scheme runtime or its native scheduler.

Rust distributes independent work across fixed owners. Each owner keeps a
complete Gerbil/Gambit runtime, native types, Actor/green-thread scheduling,
continuations, exceptions and GC. Stateful work remains affine. The native build
remains Cargo, the package's Gerbil build, Gambit C and the selected C optimizer.

#+begin_src rust
dispatcher
    .configure_scheme_service_completion_on(owner, SchemeServiceCompletion::PreparedCycle)?
    .wait(timeout)?;
// Submit through the existing typed service stream/pool APIs.
#+end_src

* Ownership and precedence

| State | Rust input and credits | Scheme authority | Transition |
|-------+------------------------+------------------+------------|
| Source staged | Existing bounded source and work accounting | No new graph | Existing producer acquisition or revocable offer |
| Prepared | At most one owned input per owner; existing active/slot/work credits | No native session or new root | Recheck cancellation, deadline and owner close |
| Offer pending | Existing one-slot offer port; payload stays withdrawable | No native graph | Claim and entry fence only after snapshot retirement |
| Ready snapshot | Existing linear token and independently rooted result slots | Complete native result graphs | Project and release each result separately |
| Entry frontier | Prepared input passes final lifecycle check | Construct through existing SchemeServiceRequest | Native ownership becomes fixed |
| Entered | Credits span execution, native root retirement and projection | Scheme schedules actual work | Existing completion protocol |

PreparedCycle adds native policy mode 4, advertised by service ABI 10. Native
batch take and slot transfer are the same protocol as ABI 9. The native receipt
is validated before the owner publishes its Rust policy flags; unsupported
images cannot silently select this mode.

Within a harvested snapshot, ready results take precedence over new typed
Scheme construction. Each result's root and credits still return independently.
A bounded preparation opportunity may acquire one Rust input after a retirement;
subsequent opportunities cannot grow that slot. The full snapshot retires before
the prepared input enters Scheme. Producer preparation has no Image or
NativeSession argument. Synchronous native producers have no preparation hook.

The ordinary inbox preserves its FIFO head. Typed Scheme submissions and control
messages remain deferred during this snapshot; ordinary native owner callbacks
retain their existing semantics. Explicit application callbacks can themselves
enter Scheme, so this is not a general prohibition on arbitrary FFI callbacks.
The multi-feed shortcut cannot put fresh bulk construction ahead of collection
in PreparedCycle. Short routing, Scheme class budgets and scheduling remain the
existing mechanisms; this experiment makes no preemption guarantee.

Pending peer offers stay in their existing revocable port during retirement.
Preparation neither claims them nor reserves their target credits. After the
snapshot, the original offer entry fence still checks withdrawal, cancellation,
deadline, close, active credit and native capacity together. There is no second
offer queue or duplicated capacity registry.

A prepared producer input reuses its existing credits. Cancellation, expiry and
close are checked again immediately before native construction. Rejection
returns both partial/native and stream credits through the existing rejection
path. The producer registration prevents replacement of that owner's capacity
identity. Close/error drains native graphs before releasing any credit retained
for failed native result transfer; prepared input itself owns no Scheme graph.

Bounds are on input count and declared work through existing stream/source
configuration, plus one prepared input per owner. Arbitrary application-owned
Rust payload bytes have no new aggregate heap-byte bound. Native construction
and projection retain their existing byte quotas; do not infer a whole-process
memory bound from the one-slot preparation rule.

* Executable protocol checks

The new native contract holds three real Scheme Actor batches at a common ready
frontier and leaves a fourth Rust input in the producer. It verifies:

- only three constructors run while the first three results retire;
- the prepared input uses the returned existing slot/work and active credits;
- GC during a held projector sees only the batch root and current result root;
- continuing constructs the fourth input after all three results retire;
- cancellation, deadline expiry and owner close reject the fourth input without
  invoking its Scheme constructor;
- non-close paths return all slot/work and producer-registration credits;
- all four cases join with zero native roots and removed instance files.

These run alongside existing native GC, multi-shot continuation affinity,
exceptions, false/void, quota, failed-slot transfer, backpressure and close-drain
controls. An actual native failure remains a failure regardless of model status.
The native progress watchdog remains five seconds. The performance controller
remains 120 seconds.

The existing owner lifecycle/shared-resource model is extended with a prepared
reservation, not replaced. Prepared input is a subset of held reservations,
disjoint from native roots, and bounded to one per owner. Entry waits until that
owner's harvested slots are empty; cancel/close discard the reservation. The
required unsafe-overtake counterexample checks that this precedence rule is
observable. Existing offer, capacity, premature-credit and stale-ack controls
remain in the same model. Finite scenarios/sampling do not prove unbounded
liveness, scheduler timing, native correctness or performance.

* What the existing evidence says to change next

The one-slot Rust preparation boundary solves pre-entry cancellation/root
ownership and prevents native bulk construction between harvested projections.
It does not restore the original overlap of supply and native execution. After
snapshot retirement the prepared request enters, then the ordinary owner loop
collects again. The measured increase in harvest batches is consistent with
smaller completion groups and additional cycle boundaries; the capture does
not isolate the CPU cost of each boundary.

Offline analysis of the same captured stage arrays adds no workload rerun:

| Load | Stage | NativeCycle p50/p99 (us) | PreparedCycle p50/p99 (us) |
|------+-------+--------------------------+--------------------------|
| cpu | Bulk construction | 2.458/411.417 | 2.542/414.042 |
| cpu | Bulk projection/retirement | 6.084/26.042 | 6.042/29.458 |
| mixed | Bulk construction | 2.542/458.208 | 2.583/453.209 |
| mixed | Bulk projection/retirement | 6.167/16.625 | 6.209/18.834 |

These wall intervals include possible allocation, GC and descheduling. There is
no same-spike runnable/blocked evidence here; pooled quantiles cannot be
subtracted into a causal OS-wait or GC CPU duration. Process GC CPU and owner
thread CPU retain their separate scopes.

The next architectural work should retain the root-free/withdrawable pre-entry
boundary while amortizing native construction and harvest transitions within
one bounded owner service cycle. The typed batch interface and its exact
root/credit ownership need to be established before implementation: ready
retirement frontier, lifecycle recheck, capacity-authorized native entry,
Scheme-owned execution, then completion. An optimized native type/batch
constructor must preserve generic typed requests, exception behavior and
continuations; it cannot move the Scheme scheduler into Rust. Increasing a
wake threshold or staged-window default would not establish this protocol.

This capture rejects the current prepared-entry implementation as a performance
promotion. It does not identify a unique OS/GC cause or justify another full
matrix. The next candidate needs a concrete reduction in native transitions
and typed construction work, followed by one targeted matched comparison.
