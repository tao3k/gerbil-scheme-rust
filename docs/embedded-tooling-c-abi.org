#+TITLE: Embedded Gerbil Package Operations
#+LANGUAGE: en

* API and ownership

Enable the opt-in =package-tools= Cargo feature on =gerbil-scheme=. The existing
=GerbilRuntime= owns the one-shot, thread-affine VM. No second tooling session,
frontend subprocess wrapper or consumer-owned scheduler is introduced.

| API | Official operation |
|-----+--------------------|
| configure_package_paths | Bind one immutable package prefix and standard library search path |
| build_package | Load the package build.ss and call its main with compile |
| clean_package | Invoke the package-owned build.ss clean action through the same C ABI owner |
| run_package_main | Call the actual build.ss main with ordinary checked arguments |
| test_package | Call :gerbil/tools/gxtest main with explicit test selection |
| stage_package_program | Stage the existing compiler-owned complete AOT manifest |
| build_package_cancellable / clean_package_cancellable / test_package_cancellable | Reject before entry or retain the entered result through return |

The safe API checks the live owner thread. =gerbil-scheme-sys= validates borrowed
UTF-8 spans and arrays, copies C strings for the call and retains every borrow
until return. Bridge-owned C exports invoke Scheme using Gambit's C interface.
These are not hypothetical official C symbols named gerbil_build or gerbil_test.
The Scheme adapter calls existing Gerbil procedures; it does not replace
PackageSpec, the compiler, the test harness or the package's build language.

* Admitted image

The build owner stages compiler, expander, core and GxTest metadata using the
existing program manifest and archive builder. The minimal conversion image
is insufficient. The generated-SCM provenance check runs before choosing the
tooling archive. Regeneration remains =just bridge-regenerate=; checks and
source hashes are never disabled or edited by hand.

The C bridge admits package operations only when initialization used the
matching default tooling linker. A different downstream linked program does
not gain that capability merely by initializing a VM. The package-tools image
can coexist with the external-program Cargo feature; an explicitly initialized
external graph still fails its tooling-image identity check.

The paired installation is supplied through Gambit's setup parameters,
including gambitdir and gambitdir_map. Child gsc processes receive Gambit's
standard relocation options too. This follows the existing package-owned
toolchain mapping and the [[https://github.com/gambit/gambit/blob/master/lib/main.c][Gambit setup contract]].
One-time image bootstrap and real C compiler/linker processes remain distinct
from direct public build/test invocation.

* Package context and host state

Each call scopes its directory, expander context and standard Gerbil paths.
Prefix binding is immutable for the tooling owner's lifetime. Standard
GERBIL_PATH, GERBIL_LOADPATH, GAMBOPT and GERBIL_BUILD_CORES values are restored
on return, including failures. Missing values are removed using Gerbil's
single-argument setenv; passing false as the value is not equivalent.

Build capacity is resolved from the executing host's cpu-count. A stale CI
core value or a build-host CPU count embedded in a reusable driver is not
execution authority. build.ss retains module, pkg-config and compiler policy.

The C boundary saves host descriptors and signals, installs the actual
Gambit child notification handler for package work and restores host state
before publishing its result. This is trusted, exclusive build-host tooling;
it does not isolate arbitrary package code from unrelated host threads.
Do not run unrelated subprocess or environment access concurrently with an
entered package operation. Tokio coordination must not migrate the affine VM.

* Exceptions, cancellation and completion

All Scheme argument materialization and package work must be inside the
exception boundary. A foreign helper's namespace must agree with its Gerbil
extern declaration. Testing exposed an uncaught argument-helper failure that
escaped C entry; the adapter now contains it before returning a package code.
Transport status and the package result remain distinct. On transport refusal,
the caller's result output stays unchanged.

The caller-owned cancellation flag is monotonic for the call's lifetime. The
acquire load is the entry fence. CancelledBeforeEntry performs no Scheme work.
After that fence, Completed retains both the actual code and the cancellation
observation. Cancellation neither rolls back artifacts nor interrupts arbitrary
Scheme code. A dropped outer waiter cannot release the owner or acknowledge
cleanup while foreign work is pending.

A zero result alone does not admit a build or test batch. Consumers must check
expected artifacts and the complete nonempty case/module inventory. GxTest's
own discovery, assertions and failure code remain authoritative. Its repeated
suite objects can retain subtests; do not infer fresh source evaluation from a
new expander context. Freeze source/dependency inputs and use a new build host
for a different source cut.

* Executable evidence

Clippy. The existing test-child isolation convention supervises actual output,
15-second total time and five-second idle time. Failure cleanup cannot become
a passing natural-exit receipt. The Tokio supervisor uses available host cores.

The fixture exercises actual compilation and artifacts, same-process owner
identity, passing and failing official tests, a failed path, immutable prefix,
pre-entry cancellation, cancellation after a real entered test, subsequent
owner use, program staging, actual build.ss arguments, malformed UTF-8,
post-close refusal and natural VM/process shutdown. The first complete local
execution naturally exits in 2.11 seconds with 12 workers. Strict lint and
cross-platform CI are separate receipts; this fixture does not qualify the
complete MRR package or establish a performance distribution.

Initial setup failures, missing child relocation, environment-restoration
failure, escaped FFI failure and an Apple linker bus error are retained in the

or CPU capacity are relaxed to convert those failures into acceptance.

* Compiler-owned function layout

The qualification actor image has 8,364 generated labels, below the existing
20,000-label generic GCC threshold, but still produced one expensive host C
function. The cancelled owner jobs were waiting in that compiler, not in a
failed Rust or Scheme assertion. The compiler-owned staging manifest now admits
the optional per-module host_layout values compiler-default and
separate-procedures; unknown values reject. Only the qualification actor module
selects separate-procedures, using Gambit's supported SINGLE_HOST_LIMIT=1.
Other modules retain their existing policy. Resolved options participate in
the existing object fingerprint, so changing layout recompiles that object and
an identical repeat reuses it. Optimization, ABI, actual host CPU capacity and
watchdogs are unchanged. No consumer CI linker flags or compiler environment
switches implement this policy.

The complete local one-processor actor entry naturally finished all nine cases
in a cold 11m30s invocation, including checksum, fault-control and final cleanup
observations. This is separate from remote CI and from package-tools C ABI qualification.

* Host environment survives native shutdown

The first Darwin CI run completes all foreign calls and returns from VM cleanup,
then receives SIGSEGV. Local allocator churn after cleanup reproduces the defect:
the crash is in platform_strlen called by Rust vars_os, reading the overwritten
0x5555555555555550 pointer. This is a concrete use-after-free counterexample;
the previous natural-exit fixture did not establish environment lifetime.

Gambit's [[https://github.com/gambit/gambit/blob/master/lib/os_shell.c][shell environment implementation]] can extend the process environment
pointer table, then free that table during cleanup without replacing environ.
Restoring variable values alone is insufficient. The bridge now captures a deep
host-owned copy before shutdown and installs it immediately after native cleanup.
The surviving table and strings transfer to the host process environment's
lifetime. Snapshot failure refuses cleanup acknowledgement. This is finalization
work, not a request-path allocation or a new environment-variable control.

The strengthened test retains the whole environment, performs ordinary host
allocations after VM teardown and checks exact preservation without printing
potentially sensitive values. It keeps natural exit and the original deadlines.
A separate MallocScribble diagnostic reaches a child compiler failure earlier
and is retained as inconclusive for this focused post-shutdown counterexample.

* One compiler environment for process and embedded owners

The complete MRR build exposed Homebrew GCC reading Nix SDK headers through
ambient CPATH. The former command entry already excluded unrelated compiler
settings, but the C ABI owner had not reused that projection. The existing
shared tool_environment source now owns that single projection. The AOT process
builder and opt-in tooling VM both consume it. The VM applies it before setup
and restores the original values after teardown; there is no compiler command
spawn or consumer-owned environment policy on this path. Explicit downstream
program initialization retains its original environment.

The complete fixture receives a CPATH containing a deliberately rejecting
stdio.h and an invalid inherited SDKROOT. Actual Scheme compilation must pass,
and the exact original host environment must be restored after shutdown.
The real MRR failure remains in ignored cache; passing the focused poison
counterexample does not replace full consumer acceptance.

* Compiled consumers and real work observation

The complete fixture now requires nonempty SSI and module/runtime/macro object
files and imports the compiled package by its declared identity. Its runtime
procedure and exported macro are checked by official GxTest. A source-relative
import alone could bypass the package artifacts and is insufficient evidence.

The complete MRR inventory exposed a missing observation path at grammar
preparation. Test calls now scope the official expander import/evaluation
callbacks and observe runtime loader entry/return, delegating to the captured
original operations and restoring them on every unwind. These are actual work
events; no timer output or deadline extension is involved. Consumers may forward
their producer's existing Parser trace through normal test process configuration.

* Darwin program-image packaging

A retained Apple linker crash reports stack exhaustion in markLive while Rust's
executable dead-strip traversal walks the complete Scheme graph. The exact
snapshot later replays successfully; that replay does not erase the crash or
establish a deterministic failure. The package now reuses existing program-image
link assembly to package the opt-in Darwin tooling graph as one shared image.
Rust links its C ABI instead of traversing the graph again as executable atoms.
Linux retains the existing archive path. No caller RUSTFLAGS, linker replacement,
stack enlargement, dependency update or weaker test gate implements this boundary.

The shared image has a package-owned absolute install identity in its build
output. It is qualified for that persistent build host and paired Gerbil
installation, not arbitrary relocation. Its code mapping lasts for the host
process lifetime. GerbilRuntime remains the single affine VM owner; this is
packaging, not another VM, a new scheduler or a security isolation boundary.
The complete local fixture naturally exits in 4.00 seconds with 12 workers,
under the original 15-second wall / five-second idle gate, and strict runtime
and AOT-owner Clippy pass. The OpenSSL dependency is selected by standard
pkg-config configuration matching the Gerbil package; a concurrent host keg
change is recorded separately from the linker recursion failure.

* Package cleanup is a Scheme action

=clean_package= and its checked C export =gerbil_scheme_rust_package_clean=
invoke the package's ordinary =build.ss clean= on the existing VM owner. This
matches the action to which official GxPkg delegates current-package cleanup,
without launching the build script as another process. Cleanup requires an
explicitly bound package prefix; the generic main entry enforces the same
precondition for the clean action before loading package code.

The root build.ss retains standard PackageSpec cleanup and then delegates
remaining module sidecars to =scheme/package-clean.ss=. That Scheme module
reads its declared namespace from the package identity and removes only the
namespace under the selected library prefix. Traversal includes hidden outputs,
excludes dot/parent entries and uses lstat semantics to unlink symbolic links
without following them. Errors propagate as package failure; repeated clean is
idempotent. Cargo remains the owner of its OUT_DIR and compiled tooling image.
Explicit caller-owned staging directories have their separate lifetime. Package
cleanup does not unload the live VM or establish a fresh source cut.

Rust transports the typed action and result. It does not enumerate SSI/object
files, infer cleanup from timestamps or use generated-file existence to decide
whether the action should run. Build-product, clean-product and staging assertions
now live in actual Scheme =t/*-test.ss= fixtures. Rust copies those source inputs
and checks only invocation status, process identity, cancellation and host lifetime.

The real sequence builds a module and macro, checks their compiled products in
GxTest, refuses a cancelled clean before entry, cleans, verifies that the generated
namespace is gone, repeats clean, rebuilds and imports the compiled module.
Hidden outputs and a link to another package exercise the traversal boundary;
source inputs and the other package remain. Missing directories, unbound prefixes,
malformed UTF-8 and calls after final close must refuse. Success, failure and
cancellation still require natural exit under the original gates. A syntax error
in the first native fixture and its failed transcript remain in ignored cache;
that failed run is not counted as acceptance.

The final local clean-action fixture naturally exits in 2.95 seconds with 12
workers; strict Clippy passes. The complete AOT owner entry also passes 29 library
and 19 input/protocol tests; its seven existing opt-in scenarios remain unchanged.
The initial source-fingerprint fixture failure was repaired by including and
independently mutating the real cleanup source, preserving the previous runtime
input invalidation checks.

Darwin CI at the preceding implementation revision completed the real C ABI test

hit its 30-minute limit while preparing the distinct Clippy graph. Execution and

separation. The cancelled whole job remains unqualified despite its passed test.
