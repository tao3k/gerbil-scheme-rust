#+TITLE: Native Wait Attribution and Explicit Owner OS Policy
#+DATE: 2026-10-21

* Scope and decision

Continue PR #18 from =ce9a2af= using the existing Rust owner-capacity bench.
The preceding accepted native constructor and owner producer remain unchanged.
This change adds bounded, opt-in native observations and one explicit Darwin
OS-policy experiment. It does not claim a repaired Scheme scheduler or change
library defaults, queue budgets, backend selection, SDK sources or optimization.

The final mixed-service tails spend median 99.48--99.77% of their matched turn
inside observed native =select= intervals. These intervals include kernel wait
and delivery back to user space. This is stronger evidence than inferring a
cause from low CPU time, but still does not separate timer coalescing, kernel
wake delivery and runnable-thread scheduling latency.

Explicit =USER_INITIATED= owner QoS helps throughput in the source-identical
final captures. Earlier captures regress CPU throughput, and one regresses
mixed throughput too. It is not promoted to a default or presented as a general fix.

* Observation contract

Only the private qualification image defines the hidden =select= observer.
The SDK archive's select reference binds locally; neither a process-wide dyld
interposer nor an SDK patch is used. The forwarding target is resolved once
with =pthread_once= and =RTLD_NEXT=. All original arguments, timeout mutation,
return status and errno semantics are retained. Other images/processes are not
configured. The normal library adapter contains none of this observer.

Recording is enabled only on the fixed owner through an ordinary native typed
call. Each image has a fixed 4,096-row buffer (128 KiB) and a trivial thread-local
recording flag. There are no TLS destructors, escaping Scheme pointers or host
callbacks registered outside the image. A hidden image constructor binds the
observer to the qualification Scheme graph without starting a VM. Ordinary
linked qualification graphs use an inert callback until an image binds it.

Each sample records real Scheme =thread-sleep! 0.001= intervals and native
select intervals on =CLOCK_MONOTONIC=. The native trace distinguishes timeout,
signal interruption, descriptor readiness and error. Rust verifies zero lost
rows/errors, monotonic intervals, expected per-owner Scheme wait counts and
actual SDK select observations. Full mixed samples contain 1,171 Scheme waits:
293, 293, 292 and 293 for the four owners. Pure CPU samples have no such waits.
Trace configuration, snapshot projection and QoS changes occur outside timing.

Matched tail attribution groups each owner's observed sleeps by the original
batch's known wait count. It intersects native select intervals with that
batch's wait span and divides the covered time by that same turn's measured
service time. Select intervals cannot overlap on an owner, and covered time
must not exceed Scheme time or service time. No subtraction of unrelated p99s
is used. Residual time includes Scheme work/scheduling and possible OS
preemption outside the observed syscall; it is not a pure CPU measurement.

* Same-VM experiment

The exclusive =--qos-ab= pair uses the native owner producer and single-entry
Scheme constructor in both arms. Four unchanged Scheme VMs, two Tokio workers,
work budget eight, request slots four, batch eight and quantum one are fixed.
Each sample executes 8,192 48-line orders and 64 scheduled four-line probes.
Ten samples per arm/load alternate AB/BA. No additional thread-count matrix is
introduced. Both arms have identical trace settings and native type projection.

The control uses each owner's original requested class/relative priority.
The candidate explicitly requests Darwin =QOS_CLASS_USER_INITIATED=. Native
receipts show =DEFAULT (21) -> USER_INITIATED (25) -> DEFAULT (21)=. Restoration
is checked after every sample, including exact original class equality. An
unspecified original class is rejected rather than inventing restoration.
Only these task-owned OS threads are configured; Scheme still owns Actor and
green-thread scheduling. Other processes are neither paused nor reconfigured.

The local host had concurrent compiler activity. These are matched diagnostic
captures, not quiet-host performance acceptance, and no comparison to older
quiet captures is claimed. Their variation is retained.

* Retained preliminary and negative evidence

The initial forwarding observer's pipeline capture completes all real native
checks but has much lower throughput than the previous quiet baseline. Its
control/candidate Scheme wait p99 is 11.879/13.522 ms; native select p99 is
10.905/12.091 ms. This capture lacks the final select-status classification and
exact QoS restoration receipts and is not substituted for the final captures.

The preliminary QoS capture has CPU throughput +25.39%, but mixed throughput
8,958 -> 8,553 orders/s (-4.53%) and mixed service p99 14.350 -> 16.146 ms.
That direction differs from final mixed results and must not be discarded.
Preliminary sources/receipts remain distinct from the final frozen source/image.
Smoke figures are correctness controls, never throughput acceptance.

Before the final lint extraction, two complete same-image captures retained
CPU throughput -7.80%/-10.15% and mixed throughput +4.98%/+21.59%. CPU service p99
worsens in both, A mixed minimum progress declines 1936 -> 1928, and CPU finish
spread worsens in both. Their portable receipts are =wait-final-a.jsonl=,

benchmark executable, not the final source-identical artifact. Extracting the
untimed policy/setup helpers resolves strict function-size lint (119 then 101
lines); failed lint receipts remain separate. No allow/suppression is introduced.
The final rebuilt source is rerun below its own frozen identity; prior captures
are not relabeled or discarded.

* Consequences for further optimization

The measured mixed critical path is occupied by native OS wait intervals.
Optimizing only Rust refill allocation, numeric projection or Scheme arithmetic
cannot remove that occupied time. Raising OS priority alone is not sufficient,
as the preliminary mixed regression and final CPU regressions show.

The current host owner pump observes new host work only after a complete
synchronous Scheme batch returns. A pending Scheme wait therefore holds that
foreign-entry boundary even when its CPU demand is tiny. Reducing the gap
between completed batches is useful for CPU throughput but cannot itself make
that entry interruptible or eliminate OS timer overshoot.

The next architectural candidate must keep asynchronous execution and wake
ownership in Scheme. An explicit Scheme service can retain pending Actors and
continuations while accepting independent native typed submissions. That needs
separate bounded accepted-work, runnable-work and retained-result accounting,
owner-local roots, close/error drain and real wake integration. It must not move
Scheme continuation scheduling to Tokio, fuse original batches silently, spin
on timers, or allow a host callback to outlive its image. This protocol is not
implemented or admitted by this diagnostic change. Reuse and extend the existing
owner protocol model when those transitions are actually added; model success
must still be followed by native validation.

The immediate admission decision is to retain the existing producer/constructor
baseline and expose the diagnostic experiment only. No SDK timer patch, OS-policy
default change or Scheme capability reduction is justified by these captures.
