#+TITLE: Indexed ready-owner delivery and independent native refill
#+STARTUP: overview

* Evidence and protocol responsibility

The unified claim/final observer preserves early claim observation, but its
qualified observed workload rejects performance: mixed client-total p99 worsens
28.59% while native short p99 changes only +0.53%. Mixed post-send to ready-poll
bounds increase, and serial probe backlog amplifies a late client observation.
The prior experiment does not prove OS blocking, GC CPU cost or a specific Tokio
queue cause. Repeating unchanged samples cannot identify that cause.

FIFO bulk delivery introduces a separate architectural dependency: a completed
result from one owner cannot reach its caller until an earlier input assigned
to another owner completes. This dependency is unnecessary for stateless pool
work. It can bunch client work, but its contribution to the previous tail is a
hypothesis until matched A/B; it is not established by the old timing evidence.

=submit_scheme_service_pool_ready_stream= is an explicit alternative over the
same pool source, validation, registrations, native quotas and revocable offers.
It returns =SchemeServiceReadyStream<R>= with =SchemeServiceReadyResult<R>=:
original input =sequence=, actual optional =owner=, independent task =result=,
and =native_completed=. Successful output has an actual fixed owner. Pre-entry
rejection can have no owner. Public defaults and the existing FIFO API remain
unchanged. Callers requiring input order must reconstruct it explicitly.

* Three independent progress responsibilities

1. Native completion projects the typed result and balances transient roots.
   Existing per-result native/work/stream retirement and refill retain their
   original linear ownership. No client acknowledgement gates an owner refill.
2. Result publication moves one indexed Rust result into its actual owner's
   ready queue. Each staged input has one consuming reply sender; aggregate
   unread result count cannot exceed the original bounded input count. A single
   owner may execute all inputs, so each bounded channel permits that count.
   Channel allocation is incremental; the logical bound is aggregate, while
   per-owner channel metadata and allocation overhead must be measured.
3. Client receive polls queues from a rotating cursor and consumes at most one
   ready result. A continuously ready owner is visited within the participating
   owner count of successful receives. Empty owners do not stall the rotation.
   This is opportunity fairness per client receive, not OS time fairness or a
   guaranteed Tokio resumption deadline. Normal Tokio cooperative accounting is
   preserved. No explicit yield, periodic timer or new executor is introduced.

The sender never awaits a client or a new native slot to publish an already
completed result. A channel-capacity failure cannot occur under one publication
per original input; a closed/invalid destination reports failed delivery and
uses the existing owner-local native retained rollback. Ordinary oneshot results
use the original send path through the same typed reply boundary. Rust result
queues are not extra Scheme roots or execution leases. Application-retained
values keep their existing explicit ownership contract.

* Wait, cancellation and close boundaries

All empty owner receivers register the current task waker during one pending
poll. Already-ready channels are checked before suspension; replacing a task
waker reaches each polled receiver. Tokio channel/waker/cooperative-budget
semantics remain trusted transport primitives, exercised by real controls.
Short requests keep their unified claim/final observer, including its early
claim opportunity. They do not share the bulk result queue or its input index.

Ready-stream observation timeout leaves unread identities and queues intact,
allowing a later receive. This differs explicitly from consuming a FIFO ticket
before waiting. Inner task errors retain their sequence and native timestamp.
Unexpected final sender closure reports =Closed= once rather than silently
ending with missing identities. Stream drop/cancel wakes existing producers and
rejects uncommitted Rust input. Accepted Scheme graphs drain on their owner;
closed result receivers cannot free native roots early. Producer registration
retires after native drain independently of unread Rust results.

The API does not preempt a native projector or arbitrary Scheme computation.
An indivisible constructor/projector remains part of its owner service turn;
Scheme Actor/green-thread execution and continuation/exception rules are unchanged.
This work changes result delivery across instances, not Scheme execution or SMP.

* Model and actual API controls

Reuse =specs/owner_lifecycle.qnt= and its existing Tokio/owner/Actor/green-thread
state. Publication appends the same completed identity to its owner result queue;
ready receive rotates owners and records the expected versus chosen owner.
Safety checks bound occupancy, prohibit duplicate/consumed identities, preserve
wake debt for an armed consumer and distinguish native retirement from result
consumption. Existing short-claim and native ownership transitions stay intact.
Directed cases include refill before consumption, early wake, drop with native
drain, head-of-line bypass, owner rotation, and explicit lost-wake/unfair-pick
mutations. Finite safety checks do not establish wall-clock fairness or p99.

Real transport controls exercise ready bypass, rotation with an owner backlog,
latest-waker registration, timeout followed by receive, missing sender closure,
dropped receiver and invalid owner identity. Native controls hold the first
input in a real projector: the other owner retires its producer and all native
credits before its unread results are consumed, then those later identities
arrive before input zero. The held graph keeps its native credit across client
timeout. Construction/Scheme/projection failures retain their input identities;
staged cancellation/drop reuses the normal producer drain. Complete native GC,
continuation, exception and teardown controls remain enabled.

* Targeted performance contract

Use the standard O2 Cargo/native graph and actual Rust bench:
=--progress-fair-ab --fixed-short-selective --ready-owner-ab=.
Both arms use the same four live VMs/image, Tokio two workers, window four,
work 32, bulk batch eight, Actor quantum one, NativeBudget, AfterRetirement,
original client timers, same unified short observer and short trace mode.
Only FIFO bulk result collection versus indexed ready-owner collection varies.
The candidate restores input order in a bounded Rust vector for the existing
independent oracle; that storage and indexing cost remains inside its timing.
Native input, result count and logical Scheme work are unchanged. No matrix
expansion or default promotion is allowed.

This compares observed workloads. Empty compiler boundaries qualify only those
boundaries, not continuous host isolation. Preserve failed/unqualified captures
and evaluate total-work/time, paired throughput, native/client p99 and owner
completion spread separately. Performance acceptance is required before commit
or push. Passing a finite model or native lifecycle suite cannot substitute.
