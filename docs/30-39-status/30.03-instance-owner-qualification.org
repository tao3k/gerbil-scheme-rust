Rust owns OS threads, task admission, queues and scalar result delivery.
Scheme owns its heap, closures, continuations, dynamic bindings, exceptions
and computation. No Scheme computation is translated into Rust in this lane.
The existing Gerbil compiler graph produces Scheme-to-C native objects through
=gerbil-scheme-aot-build=. The test does not introduce a second build system.

* Existing FFI and the instance boundary

The bridge's production =GerbilRuntime= remains owner-affine and one-shot.
Its C setup entry points are =gerbil_scheme_rust_runtime_init_program= and
=gerbil_scheme_rust_runtime_init_program_single_processor=, with
=gerbil_scheme_rust_runtime_cleanup= for teardown. This change does not remove
those guards or admit a production executor.

The existing =instance-probe= feature supplies private Darwin dynamic library
images. Each image carries separate statically linked native runtime state;
its =gerbil_instance_probe_init/cleanup/batch/marker/state= exports are loaded
by the existing diagnostic loader. The new scalar =lifecycle= export exercises
Scheme state without exposing Scheme pointers to Rust. Each instance now sets
=parallelism_level= to one and rejects setup if the actual processor count is
not one. Each image remains =!Send= and =!Sync= and stays on its fixed Rust owner.

Distinct GSTATE addresses and Scheme markers are asserted. This is an
independent runtime image experiment, not several VM records sharing one
GSTATE. Process memory, signals and timers are still shared resources. Separate
Scheme heaps do not imply process-level fault isolation.

* Executed lifecycle checks

The native executable completed all of the following:

- Initialize two fixed owners and verify one actual processor per instance.
- Reject duplicate initialization while the instance is live.
- Capture a 65,536-element Scheme vector in a continuation; return a scalar
  to Rust while only the saved Scheme continuation retains that vector.
- Allocate fresh vectors and explicitly collect eight times on each later
  resume entry. Check every captured payload element after collection.
- Restore the same continuation twice through separate foreign calls, with
  exact independent owner results. The test's shift/reset delimiter is
  expressed in Scheme =call/cc=; Rust stores no continuation or Scheme object.
- Check Scheme thread identity and captured dynamic parameter bindings during
  resumption, and restored outer bindings at subsequent foreign entry.
- Check balanced =dynamic-wind= entry/exit counts through multi-shot resumption
  and a caught Scheme exception.
- Clear the saved root and collect; destroy the first instance and join its
  owner while the second retains its continuation. Resume that continuation,
  collect again and run another native batch before destroying the survivor.
- Confirm completed cleanup rejects repeated cleanup, reinitialization and
  later Scheme batch entry. The finalized checks execute C guards only.
- Prove four owners have entered Scheme concurrently using the existing
  synchronous Scheme-to-host rendezvous. A host queue alone is not accepted
  as proof of simultaneous Scheme entry.

A five-second observer watchdog advances only after real owner responses,
completed batches or joins. A stalled run exits 70 and reports cleanup as
unverified. The existing startup and foreign-response gates remain five
seconds. Scheme execution is not protected by a shared host mutex; setup and
cleanup transitions in the existing pool are serialized for process hooks.

* Equal-load A/B

A uses one fixed owner and one native instance. B uses four fixed owners with
four private instances. Both use the same image and Scheme checksum algorithm,
the same total jobs, rounds and expected checksum. B partitions those jobs;
it does not reduce total arithmetic work. Every native batch performs GC
before computation. Both pools remain initialized during measurement.

Each of six loads runs ten ABBA blocks, giving 20 complete samples per variant
and 240 checked samples overall. The median averages the two middle samples.
Measured time includes host admission, foreign calls, per-instance GC,
computation and result validation; initialization is recorded separately.
A batch enters Scheme once in A and once per owner in B. This is a coarse
batch boundary, not a foreign call for every arithmetic step.

* Remaining admission limits

The result supports continuing the fixed-owner, isolated runtime image approach
on the selected Darwin SDK without replacing Scheme semantics. It does not
admit the public production runtime as a parallel executor. No hot unload,
in-process crash containment, signal/timer coexistence under all events,
initialization-failure rollback, leak freedom, sanitizer acceptance, portability
or remote CI result follows. The checks cover the specific delimited Scheme
resumption pattern above; arbitrary continuations escaping foreign frames or
moving between owners are not admitted.

Scheme roots, continuations and native pointers remain local to an instance.
Only explicitly owned host values may cross queues. Any later public executor
must preserve this boundary and qualify its resource and failure contracts.
