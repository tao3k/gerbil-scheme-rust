* Actual library protocol

The opt-in =submit_numeric_batch_stream_backpressured= and profiled counterpart
register a bounded sequence of explicitly independent original numeric batches
on a fixed native owner. The owner advances one complete native call at a time.
It checks its inbox at every foreign-return boundary. Scheme still owns evaluation,
Actors, green threads, continuations and GC; the Rust owner pump does not schedule
Scheme threads, reenter an active Scheme call or translate Scheme into Rust.

| Resource | Bound and meaning |
|----------+-------------------|
| Native request slots | Existing configured bound, four in this qualifier; each actual turn separately acquires a slot |
| Native work credits | Existing declared item budget, eight in both arms; includes partial reservations and accepted work |
| Producer registration | One cursor per owner, including an acquired registration not yet queued |
| Staged Rust input | At most native queue capacity batches per cursor, 128 here, and aggregate existing input-byte limit |
| Completed Rust rows | Aggregate existing output-byte limit; no native Scheme roots are exported |

Registration is not blanket native acceptance of all staged work. Every original
batch separately acquires the same work-then-slot permit pair and crosses the
existing admission/close fence. The native call uses the same =run_native= execution,
exception catch, retained-root rollback and balance check as ordinary requests.
The turn's owned result is placed in a bounded Rust accumulator before returning
its native credits. The final cursor reply retains only owned numeric Rust data.

The producer preserves its input order. Ordinary queued requests retain their FIFO
order; independent producer turns may interleave between them. Stateful/dependent
multi-call work uses the ordinary owner-pinned APIs. No generic call or batch is
silently split, fused or made reorderable by the new API.

A queued short work reservation shares FIFO semaphore credits with the producer.
The producer does not reserve its following batch while the current Scheme call
is active. At the boundary it returns credits, checks the inbox and attempts the
next original turn. Already queued short reservations participate first. The
work bound constrains native reserved/accepted units, not all external caller
futures or a universal multi-client latency SLO. Arbitrary Scheme handlers still
have no automatic wall-clock service bound.

** Waiting, deadlines and retirement

Semaphore-only acquisition is polled on the fixed owner without entering a Tokio
runtime. If blocked, its waker posts a bounded inbox notification. The owner waits
on its inbox until notification or the real deadline; there is no periodic polling,
spin loop or artificial progress heartbeat. Tokio still handles cross-instance
submission/collection and occasional cursor registration boundaries.

The admission duration starts when the async API executes and bounds registration
and the start of every unadmitted turn. Entered Scheme work drains without host
preemption, even after receiver timeout/abandonment. Individual Scheme failures
retain complete whole-batch acknowledgement/drain and do not cancel later explicitly
independent batches. Rejected turns have no native completion clock.

Close rejects unadmitted staged turns and closes both credit resources and producer
registration. A waiting external registration future holds no owner-channel sender.
Owners can therefore exit without waiting for Tokio to repoll those futures.
Quiescent reconfiguration also waits for producer registration to retire. Wakers,
semaphore returns, failed queue payloads and cursor destruction run outside the
admission mutex. The default and non-Tokio paths remain available.

* Directed same-VM experiment

One pair only: caller replenishment versus the native owner producer. Both arms
use four identical VM states, two Tokio workers, request slots four, item budget
eight, batch eight and Scheme cooperative quantum one. Both use the existing native
profiled batch implementation and the same independent invoice oracle.

Each full sample has 8,192 independent 48-line bulk orders and 64 four-line probes
at a nominal 500-microsecond interval. The control makes 1,024 batch admissions;
the candidate makes eight cursor registrations, two per owner, still executing
all 1,024 original Scheme calls. No handler work, batch count or native type
construction/projection is removed. Payload cloning, candidate grouping/reindexing,
result collection and independent Rust verification are included in sample time.

A 256-order warmup precedes each arm. Five forward/reverse blocks give ten samples
per arm. The probes use the same closed-loop API in both arms and retain their
original scheduled timestamps. Scheduled latency includes inherited wake lateness;
actual-entry latency is also reported. Per-turn bulk dispatch starts at its first
credit attempt, after caller/cursor backlog waiting, so it is not total bulk latency.
All native offsets from sample release are retained separately.

Reconfiguration waits for slots, work and producer metadata to return; the VM state
identities are unchanged across arms. The five-second startup/progress/observation
gates are unchanged. The host has concurrent work; these paired receipts do not
certify quiet-host performance or independent open-loop arrivals.

CPU cost per completed order. Probe tails and owner progress remain separate
observations alongside throughput.
