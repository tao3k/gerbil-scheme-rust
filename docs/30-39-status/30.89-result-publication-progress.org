#+TITLE: Result publication, client consumption and owner progress
#+STARTUP: overview

* Protocol and ownership

The previous owner cycle publishes a projected reply before returning that
result's native/stream credits. A client may resume while its completed result
still occupies admission capacity. This is distinct from Scheme execution,
client timer eligibility and a serial client's predecessor dependency.

The explicit =SchemeCompletionPublication::AfterRetirement= policy returns each
successfully taken result's stream and native credits after projection/root
balance and before its oneshot publication. =Immediate= remains the default.
The policy is captured once per owner harvest; changing it does not reorder an
already captured harvest. No whole batch is retained, no extra lease is added,
and existing per-result owner refill opportunities remain. A result is never
held for another arbitrary projector. Rust dispatches across fixed owners; the
complete Scheme VM, Actor/green-thread scheduling and native budgets remain.

Slot-transfer failure keeps native and stream credits for the existing owner
drain. A projector exception rolls back its retained allocations before reply
publication. A dropped receiver uses the original failed-send rollback on the
same owner before its next native entry, even if admission has been notified.
Successful application-retained values have independent release authority;
returning execution credits must not release those values. A capacity waiter
may prepare/enqueue work but cannot enter this owner's Scheme VM concurrently.

* Separate result validity from observation validity

=wait_observed= now returns independent inner =result= and =progress= results.
An invalid issue/native timestamp association reports invalid timing without
discarding an already returned value. This corrects the outer-error description
in 30.88: a successful retained value must remain available for explicit release
even when its observation metadata is invalid. Only transport closure and the
observation timeout remain outer errors. The native test deliberately supplies
a late issue token, receives the retained value and explicitly releases it.

* Observable boundaries

=SchemeServiceRequest::completion_trace= optionally supplies a bounded
=SchemeCompletionTrace=. No native value, permit or scheduling authority is
stored in this diagnostic object. The actual API records native-ready time,
credit return, oneshot send start/end and whether the receiver accepted it.
=wait_observed= polls the existing Tokio oneshot future and records the final
ready poll's start/end and count of preceding pending polls. It preserves the
original future, waker and Tokio cooperative behavior.

A sender can still be returning while a receiver consumes the result. Therefore
send-end is not ordered before the receiver's ready poll or consumption. Given
send interval =[S0,S1]= and final ready-poll start =Q=, a conservative interval
for send-to-poll delay is =[max(Q-S1,0),max(Q-S0,0)]=. An overlapping poll is
explicitly marked as racing. A first poll that is already ready does not prove
a Tokio wake occurred. These process timestamps do not isolate OS runnable
waiting from actual blocking or instrument Tokio's private runnable queue.

Native-ready, publication, final ready poll and consumption remain distinct.
The existing five-part planned-to-consumed partition is retained, including
serial predecessor backlog. Owner finish spread is measured independently;
client consumption is not required to free the completed native result.
After-retirement =Release= is nested inside =Retire= observation: those inclusive
phase totals must not be added as an exclusive time partition.

* Same-request attribution and next protocol boundary

Candidate send p99 is 5.67 microseconds for CPU and 7.50 for mixed. Its native
ready-to-send p99 is 2.88 and 2.79 microseconds, including the deliberately
moved credit return. Send-to-final-poll delay bounds at pooled p99 are
1.907708--1.907750 milliseconds for CPU and 0.761875--0.764375 for mixed.
Those marginal percentiles are not an additive decomposition of another p99.
One mixed candidate poll overlaps send; 89 CPU and 96 mixed candidate results
are already ready on their first poll. None proves an isolated Tokio or OS
cause. The sender interval itself cannot explain the millisecond delivery tail.

For the ten largest candidate native-ready latencies in this same capture,
before-entry and pending intervals account for 24.90% and 73.88% of CPU total,
30.08% and 69.12% of mixed total. Construction and projection together account
for 1.23% and 0.80%. Pending includes the existing Scheme execution/waiting
boundary; it does not isolate GC CPU or OS blocking. Reducing result copies
or construction alone cannot explain most of these particular native tails.

For the ten largest candidate planned-to-consumed latencies, serial predecessor
backlog accounts for 95.65% of CPU total and 87.34% of mixed total. These are
same-request sums, not independently added percentile shares. Serial backlog
propagates earlier completion/delivery delays; it is not current-request owner
execution. Keep planned-client and native-ready performance contracts distinct.

The source boundary to investigate next is the existing capacity transaction:
=CapacityPermit::drop= returns active/work/slot credits and invokes the shared
=CapacityEvents::publish= path, while reply publication wakes the receiver and
the owner service cycle independently replenishes work. That path currently
signals watch subscribers, capacity waiters and eligible pooled short work.
The model already separates resource return, notification owed, delivered wake
and owner progress. Reuse those states to reason about which consumer actually
needs notification and when an owner gets its next service opportunity; do not
add another lease, make client acknowledgement own native capacity, or hold a
completed result behind another projector. Notification fanout is a concrete
source dependency, not a proven explanation for every measured tail. This run
rules out treating send order alone as the complete fairness solution.
