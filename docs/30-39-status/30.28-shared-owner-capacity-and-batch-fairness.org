* Implemented pool protocol

=InstanceDispatcher::configure_owner_capacity(limit)= enables request credits for
every owner and every dispatcher clone. It must run immediately after pool startup,
before the first unbounded dispatcher admission. Later changes require all old
credits to be available. Existing pools remain unbounded by this optional mechanism
unless explicitly configured; native queues retain their original bounds. The
configured limit must be positive and no larger than the native queue capacity.

Each synchronous/native/asynchronous/byte request participates once configured.
Immediate APIs use a nonblocking reservation and retain =QueueFull= rejection.
=submit_native_backpressured_on= awaits the same owner's FIFO semaphore with a
finite budget. =submit_numeric_batch_backpressured= validates and executes the
existing native Scheme Actor batch through the same capacity gate. Neither API
retries rejection, enlarges a queue or alters observation/close deadlines.

An owned semaphore permit moves into the accepted =Request=, then stays on its
fixed owner through native execution, response delivery and abandoned-reply root
rollback. Receiving/dropping/timing out a reply does not return that permit. A
never-admitted reservation returns on cancellation/rejection. Native failure and
Rust task panic follow the original typed error/root handling. Capacity is a
request-lifetime bound, not root-retirement or code-unload authority; retained
Scheme objects and image/code leases preserve their separate ownership contracts.

Admission and close keep the same short Rust-only mutex. Close removes sender
identities under that fence, then closes old semaphores outside it. Reconfiguration
also retires old semaphore identities outside the lock. Reserved enqueue checks
both the current owner and semaphore identity, rejecting stale reservations after
close/reconfiguration. Failed-request destruction occurs outside the mutex, since
it can release a credit and invoke a waiting caller's waker. Scheme never executes
under the admission mutex.

The opt-in =owner_flow_backpressured= driver permits at most one pending capacity
reservation per owner per invocation. This prevents that producer from placing its
whole backlog ahead of a cooperating producer. Previously accepted native tickets
can still execute concurrently across distinct owners. It creates no per-request
Tokio tasks. Generic admission futures are wrapped in the original common deadline;
a permanently pending callback cannot outlive that budget. Ready synchronous
admission keeps the existing API without this additional admission timer. A
synchronously blocking callback or stuck native call is not preempted by Rust.

Zero/expired capacity waits reject even if a permit is immediately available.
Timeout after actual native acceptance remains observation failure, never native
cancellation or an early credit return. This preserves Scheme continuations and
cleanup behavior rather than cutting execution at a Rust deadline.

* Reused model and independent native controls

Extend =specs/owner_lifecycle.qnt=, not a new runtime model. Its shared held set is
exactly reservations plus accepted work not yet completed, bounded per assigned
owner. Observation timeout preserves that set; native completion returns accepted
credit; closed reservations cannot become new native work. Configuration requires
quiescence. Both finite domains pass sixteen deterministic scenarios and 1,000
sampled traces of at most 64 transitions each. Six deliberate mutations produce
required safety counterexamples, including timeout returning native credit early.
These are bounded safety checks, not FIFO implementation or starvation proofs.
Historical symbolic results are not transferred to the extended state.

The real native =owner_capacity= test independently checks:

- shared rejection across dispatcher clones, synchronous/native/byte entry paths;
- timeout/drop before and after admission, zero budget and permanently pending
  admission-future expiry;
- held capacity after an accepted response timeout and during a blocked owner;
- FIFO waiters, cancellation, Rust panic and idle-only reconfiguration;
- all four owners capturing and resuming continuations twice across FFI returns,
  forced GC and the existing dynamic-wind oracle through backpressured calls;
- close waking pending reservations, draining accepted work and clean four-owner
  joins, zero native roots and removal of private files.

The existing =owner_dispatch_faults= control still passes the synchronous/grouped
and completion-driver panic/conservation/continuation paths. The actual eight-item
Scheme batch error and recovery run on every owner before each performance cohort.
The native Scheme image is unchanged; these are Rust admission protocol changes.

Strict core lint passes both with and without Tokio, and support/qualification
source/lint gates remain separate. An extra core-only library-test invocation with
=external-program= fails to link =gerbil_scheme_rust_root_release_raw= because that
mode expects an application-owned native provider. Its failed log is retained;

the qualification crate that owns the real image. This invocation mismatch does
not replace the independent native controls or the installed/default CI gates.

* Architectural interpretation and remaining boundary

Request slots and work budgets are different resources. Four request slots at
batch eight can represent 32 bulk items on an owner; four slots at batch one
represent four. The second pair intentionally evaluates batch policy under a
fixed request limit. It is not an equal queued-work-budget comparison. Arbitrary
Scheme execution cost cannot be inferred from item count, either.

Scheme Actor yields schedule inside the current native batch. The Rust owner
queue cannot enter another call until that turn returns. Larger batches can
improve throughput while delaying short work behind longer native turns. Neither
additional Tokio/Rayon workers nor receiver cancellation changes this boundary.
A root-level follow-up must separate queue-slot credits from declared work/service
budgets and qualify Scheme-owned bounded/cooperative turns. It must preserve
exception draining, dynamic bindings, continuation/GC state and owner affinity;
arbitrary Scheme calls cannot be silently split or migrated.

Pool credits close the cross-clone native-capacity gap; cooperating flows bound
pending reservations. They do not provide adversarial per-client fairness, bound
all host-owned input/result memory, migrate stateful calls, preempt arbitrary
Scheme or integrate new Python dispatcher modes. The existing Python defaults
remain unchanged, and no installed-Python performance claim is made. The generic
backpressured =NativeSession= API preserves full Scheme operation capability;
the numeric Actor batch remains one explicit specialization.

All raw failures, samples and binaries remain outside Git with evidence-relative
filenames. No universal performance/default promotion or industrial-readiness
claim follows from these controls.

* Decisions from the final pairs

The mixed capacity pair supports the pool-level direction. Scheduled probe p99
changes 527.854 -> 76.581 ms in C and 394.539 -> 124.056 ms in D. Entry-to-delivery
p99 also improves, 20.931 -> 4.478 and 10.977 -> 8.237 ms, so this is not just
moving native wait into an unmeasured upstream queue. Admission p99 rises
0.025 -> 3.059 and 0.018 -> 4.268 ms as intended backpressure; those costs remain
inside the complete latency. Bulk rates are 20,331 -> 20,309 and 20,449 -> 19,050
orders/s, retaining the roughly flat/-6.8% throughput trade-off.

All 64 candidate probes finish while bulk work is still active; baseline minimums
are 58/60. By the final probe, candidate bulk work has completed at least 996/1,186
items, so the finite run shows progress for both producers. Owner completion
minimums change 1,989 -> 2,019 and 2,006 -> 2,015 out of 2,048 offered items. This
is not adversarial fairness, an equal-share theorem or an industrial p99 gate.

CPU capacity results do not establish a stable tail gain: C scheduled p99
17.502 -> 50.614 ms regresses, whereas D changes 8.662 -> 1.898 ms. CPU bulk
throughput loses about 5-6% in both. Repeated occurrences of the same capacity-four
single-item configuration in the other pair also vary; these tables must not be
collapsed into one fixed speedup. No default or optimal-capacity claim is made.

Batch eight improves bulk throughput in both final cohorts: CPU 327,578 -> 596,925
and 318,746 -> 584,697 orders/s; mixed 18,591 -> 24,090 and 20,580 -> 24,050.
However, mixed scheduled probe p99 regresses 179.819 -> 499.250 ms and
304.611 -> 526.364 ms. Entry-to-delivery also regresses 8.728 -> 22.143 and
17.400 -> 23.203 ms. CPU D has another clear negative, 2.037 -> 112.899 ms.
The CPU complete-workload rates remain near 253k orders/s despite much higher
bulk-only rates because the scheduled probe workload remains part of completion.
Neither bulk-only gains nor reduced overlap are a complete-workload speedup.

The request-credit/work-budget mismatch and non-preemptive native turn are now
concrete blockers to adopting batch eight for latency-sensitive traffic. The mixed batch-eight summary's within-batch Actor peer minimum is zero in both
final cohorts; larger batches do not prove stronger internal fairness. Keep batching explicit and unpromoted. The next
architectural refinement should introduce declared work/service budgets separate
from request slots and Scheme-owned cooperative turn boundaries, preserving full
Scheme semantics. Merely adding Rust threads cannot shorten an already-entered
native turn.

Final source-policy tests, strict core/support/bench/native-target lints, the
extended lifecycle gate and both real native fault targets pass. The non-Tokio
feature route also passes strict core lint. Native controls include a permanently
pending admission future returning within its configured budget. No installed
Python wheel, long-memory soak, open-loop SLO or new hot-unload acceptance is
claimed for this source. New exact-head remote CI remains a separate gate.
