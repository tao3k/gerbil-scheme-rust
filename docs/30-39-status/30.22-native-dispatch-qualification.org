* Decision and scope

The industrial acceptance work now includes executable native startup, contention, overload, in-flight close and deadline-recovery gates. These finite local passes do not establish complete industrial readiness. The default four VM owners, two Rust dispatch workers, stateless Tokio dispatcher, session direct dispatcher and window 128 remain unchanged. The adopted 10.10x owner-resident payload baseline remains historical working evidence; the new matrix changes workload/probe parameters and is not a replacement capture or a multiplicative speedup.

Scheme keeps its native Gerbil/Gambit/C O2 compilation, macros, GC, closures, continuations and Actor/green-thread scheduling. Rust only admits, distributes and observes jobs on fixed owners. All 53 non-source native runtime/package resources are byte-identical to the previous qualified O2 wheel. * Implementation and source-gate closure

The Python runtime facade now separates library methods, value methods, input conversion and linked execution into responsibility-owned modules. Deep relative imports and the Rayon glob import are removed. A typed =DispatchRuntime= owns the Tokio runtime, returns supervised task handles, and remains under the existing host shutdown lifecycle. Pipeline admission, collection and ordered publication are distinct helpers; the JoinSet still observes every accepted future.

Public maintainer startup/grouping functions use =PythonInstanceRequest= and =ModuleBundleRequest=. Resource namespace selection uses indexed path-ancestor membership instead of loop-local load-path scans. No source policy, allow-list, severity, deadline or compiler optimization was weakened. The strict ASP source gate now passes, as do both unit tests, all 31 integration tests, full formatting and strict release Clippy for instance-only and linked-only feature profiles. Linked-only lint is not an installed linked-wheel runtime acceptance result. Two older root-binding source contracts are updated to distinguish unconditional FFI from optional Tokio dispatch and the default SDK policy from explicit single-processor initialization. Negative controls reject an unconditional processor override or a changed default entry; runtime source is unchanged by this test repair.

Shutdown now checks the closed flag while holding the Rayon pool creation lock and the registry insertion lock. This prevents late pool recreation or metadata publication after retirement. These were code-audit hazards: the finite pre-fix controls did not reproduce a failure. The rebuilt artifact passes the strengthened close test, which checks OS thread retirement before a second idempotent close can mask late recreation.

Direct and Tokio batches now check the original group budget before admitting additional work, matching the existing Rayon/pipeline admission checks. Error cleanup and draining still occur after observation timeout; five seconds is not a hard bound on total API return or forced termination of Scheme.

* Stateful native session API

#+begin_src python
session = library.session(owner)
payload = session.value(read_only_data)
roots = session.call_many(
    [("actors", payload, 1)] * count,
    dispatch="tokio", admission_window=16,
)
rows = library.project_many(roots, release=True)
payload.close()
#+end_src

Supported pinned modes are =direct=, =tokio=, =rayon= and =rayon-blocking=. Native references stay on their actual owner, preserve identity, and execute within each batch in input order. Tokio admits ordered native asynchronous tickets before supervising replies. Rayon submits the ordered stream on its pool; the blocking reference occupies a pool worker while waiting. Concurrent batches may interleave and are not transactions. Defaults are unchanged.

The experimental =tokio-pipeline= remains stateless-only and rejects pinned use before any Scheme state write. There is no fallback. The routing suite checks real ordered Scheme writes and rejection without side effects, in addition to type identity, GC, exceptions, foreign handles and continuations.

* Matched resident-data performance protocol

Each configuration uses the same live VMs, same read-only native input graph per owner, same 128 logical requests x 32 Actor items, same native results, and quantum one. Initial VM setup and graph preparation are reported outside warm timing. CPU cases use 512 pairs per item. Wait-mix cases use 48 pairs and one-millisecond cooperative Scheme waits; they are not production network-I/O tests.

All four treatments are warmed before timing. Sixteen measured rounds use a four-treatment Williams rotation: each mode occupies every position and each directed adjacent pair occurs once per four-round cycle. The first matrix had equal counts but incomplete position balance; it was retained locally and superseded by this complete rerun. Added observations report per-owner client completion and Darwin thread rows. The final matrix uses the rebuilt shutdown-guard artifact. Earlier pre-guard captures remain separate local observations and are not pooled into its results.

Main p99 is the nearest-rank p99 of 16 complete batch responses, including bulk projection/release; it is not 128 independent request-arrival samples per batch. Four short probes per owner are offered at fixed 20 ms intervals in each arm, including call, projection and release. The complete cohort drains before the next arm. Every owner finishes 64 probes per mode; Actor work finishes eight items per Scheme worker in every result. Equal finite counts do not prove starvation freedom, and faster arms can finish before later probes arrive.

Comparisons are paired within one configuration. Owner/worker-count configurations use separate processes and are not paired proof of an optimal count or linear VM scaling. Host observations are retained locally; this is not dedicated-host performance certification. Primary tracing is off. No own build or lint ran during final captures.

* Positive observations, negative results and admission

- 4 VMs / 1 worker, wait mix, rayon-blocking: paired throughput ratio versus direct 0.306, descriptive bootstrap interval [0.279,0.426], faster in 0 / 16 pairs.
- 4 VMs / 2 workers, wait mix, rayon-blocking: paired throughput ratio versus direct 0.568, descriptive bootstrap interval [0.531,0.772], faster in 1 / 16 pairs.

The final four-VM/four-worker CPU run favors Tokio versus direct: median paired throughput ratio 1.222, descriptive interval [1.012,1.391], faster in 12 / 16 pairs. Its short p99 is 130.2 ms versus direct 209.3 ms. The blocking reference also favors throughput in this CPU capture (ratio 1.326, interval [1.041,1.812], 12 / 16 faster). These CPU wins did not recur consistently across the earlier pre-guard matrix. Host variation and changed shutdown guards prevent attributing their magnitude to the guards or promoting a default from this run.

A separate pre-guard four-VM/four-worker wait-mix capture showed a Tokio regression: paired median throughput ratio 0.853, descriptive interval [0.716,0.971], and short p99 418.3 ms versus direct 199.9 ms. The final guarded capture has ratio 1.033 with interval [0.880,1.214]. Both observations are retained; neither proves that shutdown guards change scheduling performance.

Blocking the finite Rust workers can limit simultaneous owner-stream progress. Other scheduler ratios remain workload- and configuration-dependent; no universal winner is admitted. Earlier pilot and pre-guard results are retained locally rather than merged into the final sample set.

The bootstrap intervals describe these finite paired observations, not population guarantees; p99 differences do not inherit those throughput intervals. No scheduler, window or worker default is promoted. Rayon-blocking remains an explicit reference path, with its capacity cost stated. Treat compute-heavy, cooperative-wait and projection-heavy workloads separately before tuning.
