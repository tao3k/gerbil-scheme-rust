* Actual library protocol

=submit_scheme_service_pool_stream= takes a count/work-bounded set of explicitly
independent stateless Rust messages and =SchemeServicePoolStreamConfig=:

- Unique owner indices are sorted before acquiring the existing one-producer
  registrations, avoiding registration-order cycles between competing streams.
- Declarations are frozen once and all destination capabilities, native capacity
  epochs, work bounds and active limits are validated before publication.
- A readiness barrier prevents partial registration from executing any input.
  The result handle doubles as the registration-future cancellation guard.
- Requests retain input-order result positions in one shared Rust FIFO. An owner
  obtains private active and ordinary work/slot credits before claiming work
  through the existing final owner/close/capacity fence. Native values never move.
- If a competing owner changes the head's declared charge, speculative credits
  are refunded before repricing. Empty/head-charge transitions notify producers;
  equal-charge claims avoid an unconditional wake-all per request.
- Cancellation, absolute deadline or participating-owner failure/close rejects
  remaining uncommitted work. Accepted tasks drain through the original native
  service, projection, root balance and capacity retirement.
- Fully consumed handles retain weak cancellation signals. Unconsumed application
  outputs retain their normal resource ownership. Count/work limits do not claim
  an exact bound on arbitrary generic Rust payload bytes.

=ReselectProgress= retains short-class pending-count priority, then considers
native occupied request slots before the router's total/batch ledger. It sees
resident producer reservations and retirement without maintaining a second load
ledger. These approximate observations do not prove that an owner is OS-runnable
or predict its task duration. Class quotas remain per router. Existing =Pinned=
and =Reselect= behavior and every native wake/feed/budget default are preserved.

* Native and finite protocol checks

The existing four-VM fixture now exercises:

- Busy-owner bypass with heterogeneous native work charges, exact result identity
  and fixed construct/project owner identity.
- A direct resident producer invisible to the old short ledger: the old router
  selects owner zero while progress-aware reselection selects the empty peer.

  the readiness barrier, and already-acquired registrations are returned.
- Multi-owner active bounds, cancellation and expiry; accepted graphs drain and
  uncommitted messages receive typed errors without leaking work/slot credits.
- Native GC, Scheme exceptions, constructor/project panic and independent recovery
  through the pooled path, plus existing multishot continuation and reuse cases.
- Pool-source close with accepted and staged work; four joins, zero roots,
  successful finalization, removed copied images and the existing FD checks.

The original observer test failed once because its returned observation preceded
its own capacity-guard retirement. It now waits for the same exact expected

=poolStep= extends the existing QNT lifecycle model, with bounded =poolStaged=,
a registration barrier and atomic owner claim. Accepted ownership, roots, work,
slots, active-window and close invariants remain. Unregistered application-owned
Rust inputs may outlive native join while their host future is unpolled; they
hold no native credits or Scheme roots and cannot be claimed after close. The
first new random run exposed an assertion that incorrectly conflated those inputs
with native resources. Its counterexample is retained and the distinction has an
explicit scenario. The missing-barrier mutation remains a required failing
control. Finite safety is separate from native acceptance and performance.

Control retains four fixed groups of 32 callbacks and 256 work units per owner.
Candidate uses one shared group of 128 callbacks and 1024 work units. Both
retain each original Scheme constructor, handler, projection and FIFO result
position. Control refills each fixed owner after its own group drains; candidate
refills after the shared group drains. This measures the complete supply
algorithm, not an isolated mutex improvement or an equal peak-memory claim.

Setup/warmup and compilation are outside timed samples. Each capture reuses the
same native VMs/image across arms. No other task is paused. Host activity is not
controlled, so these are matched local observations, not a quiet-host or portable
latency certificate. No Python/GIL throughput claim follows from this Rust bench.

A short opportunistic sample need not use all four owners. The initial smoke
failed an older all-owners-used assertion; that binary/source and failed output

progress for any unused owner. Finish spread covers participating owners and

results do not establish intra-VM Actor fairness or uniform OS scheduling.

* Residual tail diagnostic and decision

A separate instrumented 40-sample capture also closed cleanly. CPU throughput is
32708.45 -> 44018.77 orders/s and actual short p99 is 53.162 -> 41.383 ms. Mixed
throughput is 15218.36 -> 16906.21, but short p99 regresses 8.193 -> 21.519 ms and
scheduled p99 regresses 98.691 -> 237.914 ms. The diagnostic's mixed finish spread
improves 148.718 -> 55.528 ms and minimum owner progress 79.688% -> 98.718%.
Instrumentation changes execution; this capture neither replaces the unobserved
negatives nor proves an unobserved mixed-tail regression.

For the seven largest actual short latencies among each arm/load's 640 probes,
matched-request median publication-to-dequeue/actual fractions are 98.01%/99.85%
for CPU control/candidate and 99.49%/99.85% for mixed. The corresponding median
Wait-overlap/queue fractions exceed 99.90% in every group. Median post-construction
pending times in these same tail groups are 2.555/0.048 ms CPU and 0.035/0.034 ms
mixed. No entry history was lost. This locates a substantial residual before owner
entry, not predominantly in these requests' own construction or projection.

Summed Wait wall time over four owners and ten samples is 9360.40 -> 7661.42 ms
CPU and 18020.26 -> 17990.39 ms mixed. Those overlapping phase sums are not elapsed
time or isolated OS delay: native green execution, waiting, GC and descheduling
can occur inside the phase. SDK GC CPU remains process-scoped; do not sum it as
per-VM CPU or subtract it from owner wall time to infer OS overhead. Capacity
progress cannot by itself distinguish a promptly runnable owner from a delayed
native wait boundary. That remaining distinction needs native wake/readiness and
scheduling evidence, not a phase boolean, wider watchdog or Scheme replacement.

The pool-level supply algorithm is qualified as an explicit throughput/balance
option. Short p99 stability, universal fairness and industrial latency acceptance
remain open. Defaults are not promoted. No additional thread/load matrix is added.
