#+title: Native service input construction and retirement-bounded pipeline
#+options: toc:nil num:nil

* Baseline and decision

The predecessor commit =1e6c6ac= has all six supported CI checks successful in
[[https://github.com/tao3k/gerbil-scheme-rust/actions/runs/39888042508][run 39888042508]]; the separate unsupported SMP job is skipped.
[[file:30.64-bounded-input-preparation.org][30.64]] implements the root-free preparation boundary but retains its CPU
throughput and tail regressions. This follow-up compares that PreparedCycle
with an explicit PipelineCycle using the same current native image and VMs.

The existing numeric batch constructor already constructs a complete Actor
batch natively. Reimplementing it in Rust would duplicate the native mechanism.
The remaining avoidable work is constructing the service header/envelope in
separate foreign calls and returning to collection after each fresh submission.

The actual library now combines the native numeric payload, service header and
envelope in one foreign construction entry, then replenishes the owner from
retired-request opportunities before the next collection. Rust distributes
work across complete owner runtimes. Scheme owns execution, Actors/green
threads, continuations, exceptions and GC. Snapshot remains the default; neither
optimization moves Scheme scheduling into Rust or introduces SMP.

* One bounded owner cycle

| Boundary | Ownership and ordering |
|----------+------------------------|
| Prepare | At most one owned Rust input per owner, using existing source/active/slot/work budgets; no Image, NativeSession or new Scheme root |
| Harvest | One existing native batch transfer acquires the ready token and result slots |
| Retire | Each projection clears its slot/root and returns its own native/stream credits |
| Ready frontier | All harvested slots retire and the batch guard drops before any new typed Scheme construction |
| Refill | At most one attempt per retired result; actual capacity and work admission authorize each new request independently |
| Native entry | Recheck cancellation, deadline and close for each prepared input; construct and submit on the same fixed owner |
| Next collection | Collect after the bounded refill, rather than unconditionally after every single new input |

The refill opportunities count retired requests, not work units. They do not
replace the independent work semaphore: a newly priced large job still needs
its full charge. The opportunity budget is local to this cycle and unused
opportunities disappear; they cannot accumulate across future turns. No new
window, timeout, fill timer, capacity registry or default is introduced.

Ordinary inbox FIFO/control messages stop refill. A successfully claimed shared
short request is deferred to the ordinary owner turn and also stops refill.
Native lifecycle messages are not overtaken. A prepared producer input is still
rechecked immediately before entry. Pending peer offers stay in the original
revocable port during ready retirement and use the original claim/entry fence
only at refill. Construction/entry uses existing native error handling; a failed
result transfer retains the original drain credits until native close.

The bound limits refill attempts and prepared inputs, not elapsed constructor
time. Generic application constructors can perform arbitrary native work;
Scheme cooperative scheduling and its existing work budgets remain authoritative.
There is no preemption guarantee or unbounded starvation-freedom claim.

* Typed construction API and native ABI

#+begin_src rust
dispatcher
    .configure_scheme_service_completion_on(owner, SchemeServiceCompletion::PipelineCycle)?
    .wait(timeout)?;
// Existing typed stream/pool submission APIs remain the entry path.
#+end_src

Service ABI 11 advertises policy mode 5. Selection checks both service version
and the optional image-local =gerbil_scheme_rust_numeric_service_create= symbol
before changing native policy or Rust owner flags. Production and qualification
export lists include this symbol. Isolated instances without Tokio keep the
corresponding module, field, initializer and type alias feature-gated.

=SchemeServiceRequest::construct_service= receives an opaque
=SchemeServiceInput= context. Its default calls the existing arbitrary
=construct= method and wraps that payload with the stable admission metadata.
Thus custom Scheme values, affine requests, exceptions and continuations retain
the existing path. Composition wrappers =Checked= and =RoutedRequest= forward
this optional construction capability while preserving their snapped declarations.

The built-in =NumericServiceBatch= uses =SchemeServiceInput::numeric_batch=.
Under PreparedCycle this constructs the original payload then its header and
envelope. Under PipelineCycle one synchronous native call constructs all three,
with only the final parent receiving an external strong root. Both paths share
the same native numeric payload builder, layouts and byte-copy operations.
No Rust pointer survives that synchronous copy. Generic requests need not opt in.
A custom override must preserve its normal constructor semantics; it is not a
license to change the declared lane, class, work charge or application payload.

The native constructor checks kind, row count, quantum and service-header shape.
Rust validates sealed numeric layouts and cumulative input charge before entry:
payload charge plus the service-header elements and outer-vector references.
It uses the same total charge as the ordinary wrapper path, with checked size
arithmetic. A quota rejection cannot silently fall back to an uncharged route.
There is no JSON transport, Rust translation of Scheme, or substitute scheduler.

* One matched A/B

One frozen capture exits 0 in 6.534 seconds. Both arms use four identical live
VMs and the same native image, Tokio two Rust workers, ProgressFair bulk supply,
Selective short routing, NativePort wake, slot/work budgets 4/32, three active
bulk batches, batch size eight and Scheme quantum/feed/native budget one.
Each sample has 8192 real orders and 64 short requests. Five alternating AB/BA
blocks yield ten samples per arm/load, 40 samples total. Observation is Off.
Own builds/models/profilers/pollers are finished during capture; other tasks
are untouched. No expanded thread/runtime matrix or default change is made.

The benchmark's numeric bulk request delegates to the actual public construction
API in both arms. Its bulk construction interval now covers the complete service
envelope in both arms; short native-payload timing keeps its existing scope.
Do not compare these stage absolutes with older captures as if scope were
unchanged. The ordinary generic path remains exercised by the native controls.

All samples satisfy workload identity, actual native policy readback, four owner
participation, 1088 retired results per sample and offer publications equal to
withdrawals plus entries. Every sample ends with zero owned token, claimed slot,
queued ready result and pending opportunity. Final cleanup joins all four,
reports roots [0,0,0,0], quiescent services and removed image files. This is not
an RSS soak or proof that every SDK mapping unloads.

Construction medians improve, while construction p99 worsens in both loads.
CPU short pending p99 rises 4.55%, short construction p99 rises 7.32%, and short
overlap falls. Mixed throughput falls 2.42%. These negatives are retained even
though native short p99 and owner finish spread improve in both loads and CPU
throughput rises 12.24%. The large mixed bulk-p99 ratio is an observed pooled
tail, not a guarantee of the same improvement in another run.

Decision: retain PipelineCycle as an explicit experiment, NOT a default promotion.
The CPU throughput gain and reduced cycle count support this architecture over
per-input collect transitions. They do not establish a uniform workload win.
The next optimization should address remaining constructor tail and supply/
retirement interaction without sacrificing the native execution pipeline, not
increase a wake/window threshold or repeat the entire matrix. This combined
candidate does not independently identify construction versus refill causality.

Stage wall time can include allocation, GC and descheduling. No same-spike OS
runnable/blocked evidence is collected, and pooled quantiles cannot be subtracted
into causal waits. Process GC CPU and owner thread CPU retain separate scopes.
CPU utilization increases alone are not classified as performance regression.
