#+TITLE: Scheme execution progress and completion retirement
#+OPTIONS: toc:2

* Existing evidence and causal limits

The rejected ready-first comparison is preserved in
[[file:30.82-scheme-ready-service-cycle.org]]. Its paired CPU throughput improved
7.55%, while mixed throughput fell5.73%, actual short p99 rose7.68%, bulk p99
rose25.71% and owner finish spread rose8.07%. This is not performance admission.

Source inspection separates the mechanisms. CPU handlers perform arithmetic
before publishing their graphs, so immediate retirement can promptly return
capacity. Mixed handlers suspend through Scheme before arithmetic. After a
harvest, the owner can prepare and construct more native inputs before returning
to existing Scheme jobs. Ready custody and an execution opportunity therefore
represent different obligations. The previous counters establish a small
change in boundary decisions, not a unique quantitative OS/GC attribution.

A completion can also be exceptional and carry no successful declared-work
credit. The previous bounded-ready-backlog argument still bounds graph custody,
but the arrival of a new ready graph does not prove useful logical execution.
A finite backlog draining eventually is weaker than timely service under refill.

The short probe issues requests sequentially against scheduled release times.
Scheduled p99 includes accumulated client lateness. Actual latency still has the
existing additive before-entry, native-construction, pending and projection
components. Pending includes execution, suspension, GC and retirement; it is not
Scheme CPU time. Neither differences of p99 values nor scheduler-pass counts
separate those costs causally.

The same-request additive audit of the already captured mixed ready-first
arm puts72.42% of the ten largest actual latencies in pending,26.85% before
entry,0.57% in construction and0.16% in projection. These shares describe those
specific requests, not all requests or differences between quantiles. They
exclude projection CPU cost as the dominant measured component of those ten
short-request tails; they do not distinguish Scheme suspension from OS waiting.
Across640 short requests the owner assignment counts were180/154/158/148;
concentration alone does not explain the execution and completion delay.

* Three independent progress contracts

| Progress | Authority | What it cannot acknowledge |
|----------+-----------+----------------------------|
| Admission and construction | Existing bounded Rust offer, owner reservation and native input entry | A Scheme receiving grant or finished execution |
| Successful logical execution | Scheme work accounting, including the live lease accumulator | Root retirement, capacity return, CPU time or partial exceptional work |
| Completion retirement | Scheme ready token and each result's projection/clear | Another request's first grant or successful logical work |

The new explicit =ProgressFair= service-cycle policy observes execution only at
an existing native harvest boundary. Immutable handler plans, continuation
activations, class arbitration, declared maximum spans and the existing work
epoch remain authoritative. No new handler poll, timer, outer lease or Rust
executor is introduced. The established shared wake policy remains unchanged.

| Boundary state | Action |
|----------------+--------|
| No ready graph | Existing single Scheme pass, recheck, then ordinary native wait if still empty |
| Ready graph and logical execution advanced | Direct bounded harvest |
| Ready graph, unfinished accepted work, no execution advance | Existing single Scheme pass, then bounded harvest regardless of whether work advanced |
| Only terminal graphs remain | Direct harvest, including exception-only results |

The observation is updated after the pass and before harvest. A pass offers an
opportunity; it never fabricates work credit or waits for an arbitrary handler.
There is at most one explicit pass per harvest, never a new second yield. A
native outstanding-job counter changes at accepted submission and terminal
publication, not at every Actor handler. Both comparison arms maintain the
same counter. There is no table scan or per-harvest queue allocation to count
unfinished jobs.

This policy does not promise preemption, a wall-clock service bound or per-class
starvation freedom from aggregate execution credit. Existing Scheme class
arbitration and first-grant obligations remain separate. In particular, bulk
progress is not proof that a short request ran. Performance and per-owner
receipts must establish whether this boundary rule is useful.

The old continuation lease policy uses its own =cycle= internal tag. The new
ready-first boundary policy now uses =ready-cycle=, avoiding a local name
collision that previously redirected the old lease policy to registered layout
execution. The ready-first A/B still selects the registered layout explicitly.
This compatibility repair requires native replay and Actor qualification too.

* Ownership and validation

The actual API is =configure_scheme_service_boundary_plan_on= with explicit
=SchemeServiceCyclePolicy::ProgressFair=; default selection is unchanged.
=SchemeServiceCycleProgress= gains the policy flag and stalled-ready pass count.
Counters are observations, not routing authority. Decoder checks retain signed
range, flag, cardinality and active/total-pass conservation.

No service mutex is held across scheduling. The existing service-to-budget
lock order, receiving-thread first grant, stale-epoch continuation fences,
multishot successful credit and exceptional unwind are retained. Each result
keeps independent native root and capacity retirement. Cancellation and timeout
after entry retain Scheme ownership until drain; closing does not depend on a
future caller to acknowledge execution.

The existing Runtime model is extended with monotonic ghost execution credit
and last boundary observation. Only =compute= advances this ghost credit;
readiness, grant, harvest and projection do not. Directed controls distinguish
a stalled exceptional completion with another unfinished job, one bounded pass,
terminal-only drain and a skipped-pass mutation. The ghost receipt represents
logical progress, not a new runtime activation allocation or OS CPU clock.
Existing cancellation, timeout, close, replay, registration and ready-token
controls remain separate evidence.

A native control holds a real Scheme continuation on a latch, publishes an
exceptional result, verifies exactly one stalled-ready pass without invented
work, resumes and drains the continuation, then verifies that a terminal-only
exception drains without an idle scheduling pass.

* Direction after the negative result

Do not promote aggregate logical execution credit as the scheduler's sole
readiness predicate. Unfinished work can be suspended on external readiness;
bulk execution can advance while a short job still waits. The next protocol
must distinguish at least runnable Scheme work, lease registration/acquisition,
external suspension/resumption and ready completion custody, using the existing
Runtime model's blocked/runnable states and existing Scheme lifecycle events.
A returned completion slot must not by itself authorize a claim that another
class progressed. Native construction and retirement must consume the same
owner service-cycle opportunity contract.

Selection should move at those state transitions, retaining the uncontended
specialized plan. No new per-handler polling, sleep threshold, outer lease or
Rust green-thread scheduler is justified. Preserve the single native boundary,
continuation reentry/exception fences, independent roots and admission credit.
This direction is not implemented or performance-qualified by the failed
aggregate-credit experiment. Further A/B requires an actual protocol change,
not another capture of this image or another yield threshold.
