#+TITLE: Local native Scheme O0/O2 and owner dispatch measurements
#+STARTUP: overview

* Execution and scope

The user explicitly authorized immediate local execution without a quiet-host gate.
No automation, rebuild, process suspension or runtime source change was used.
Existing verified O0/O2 wheels and native Scheme types were reused. Rust only
distributes requests across independent fixed-owner Scheme runtimes. Scheme
retains macro expansion, Actors, green threads, GC, exceptions and continuations.
JSONL files are benchmark receipts; runtime values use the native type API.

Host observations remain in every raw capture. A successful process exit means
the workload, result checks and cleanup completed; it does not override a
REJECTED_HOST_BUSY observation or establish quiet-host non-regression. The old
negative observations and timeout receipts remain unchanged.

* Observed results and remaining admission boundary

All 22 processes completed with exit 0: four macro captures and 18 topology/load
captures, covering 72 dispatch-mode cells and 1152 measured dispatch rounds.
The measured dispatch work contains 147456 native requests and 4718592 Actor
work items. All result, live-VM identity, GC and clean-shutdown checks in the
benchmark entry points completed. No Scheme/Rust execution code was changed.

- Both O2 macro processes have higher expansion throughput and lower API p99
  than both O0 processes in this sequence. The prior pure-expansion regression
  was not reproduced here; pooled O2 throughput is 14.6% higher and API p99 is
  12.5% lower. This is not quiet-host statistical non-regression acceptance.
- The highest observed projected throughput is 3981.6 Actor items/s for CPU
  (four VMs, four configured Rust workers, direct) and 4939.3 items/s for mixed
  (four VMs, four Rust workers, Rayon blocking). These are selected observations,
  not a qualified optimum. The four/four processes have 13 measured OS threads
  on a 12-logical-CPU host, a thread-count oversubscription control. Idle pool
  threads are included; this does not prove 13 threads were simultaneously runnable.
- Direct submits to owner queues without using the Tokio/Rayon dispatch pool.
  With four owners its CPU throughput nevertheless changes substantially across
  configured worker cells: 4200, 2568 and 6389 native Actor items/s. These are
  separate processes at different times, and pool configuration also changes
  process state. This control variation prevents attributing cross-cell changes
  solely to Rust worker count. Topology selection requires balanced repetitions
  with those direct controls; do not change defaults from this grid.
- At the default four VMs/two Rust workers, mixed-load Rayon projected median
  throughput is 3038.4 items/s versus direct 2749.8, and pooled projected p99 is
  1727.6 ms versus 2361.9 ms. However, its paired-round throughput ratio interval
  includes 1.0. CPU Rayon has a worse projected p99 than direct (2770.7 versus
  2384.4 ms), and its paired-round median throughput ratio is approximately 1.0.
  Neither observation establishes a universal scheduler advantage.
- Keep the two-VM/two-worker mixed Tokio negative result: projected p99 is
  7644.9 ms, versus direct 5279.0 ms. Native operation deadlines were unchanged;
  this projected bulk-response metric includes queueing and projection.

* Dispatch topology measurements

Each cell starts a fresh O2 process and retains the same live VM identities
across direct, Tokio, Rayon admission and Rayon blocking. Modes are warmed
first and compared in balanced order for 16 measured rounds. Each round uses
128 requests, 32 Actor items per request, quantum 1 and four Scheme Actor
workers. Each mode has 2048 native-ready samples per cell. CPU and mixed
cooperative-wait workloads retain the same computation and native result checks.
Rates count completed Actor work items, not newly created Actor instances;
the four Scheme Actor workers persist for the life of each VM service.

Native-ready clocks reset at each 128-request admission window. Projected
response is measured from bulk API start through ordered projection/release;
it is not independently arriving or streaming request latency. Final coverage
alone is not fairness. Owner pending gaps and intervening completion gaps,
Actor-worker gaps and rank displacement are retained in summary.json.

* Limits and raw evidence

The topology grid is a finite comparison, not a global optimum. Rayon blocking
has a different in-flight admission limit from Rayon admission; preserve it
as a separate control. Fewer intervening completions under blocking admission
can reflect reduced concurrency rather than better scheduler fairness.
GC and cleanup checks complete in each successful
process. They do not establish long-duration leak freedom or repeat the full
continuation/exception acceptance suite, which remains separately recorded.
