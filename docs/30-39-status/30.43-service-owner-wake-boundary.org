* Scope and admission decision

Continue the native service from [[file:30.42-capacity-reserved-owner-reselection.org][capacity-reserved owner reselection]].
Four independent Scheme VMs remain on their fixed OS owners. Rust admits and
distributes requests across instances; Scheme retains native types, Actors,
green threads, continuations, exception handling and GC. The Scheme/C build
remains O2. No SMP, JSON transport, default, timeout or thread matrix changes.

This iteration separates three claims: the existing reselection lifecycle
contract, a version-observation synchronization repair, and a targeted OS
scheduling experiment. Neither the repair nor the experiment closes general
throughput/tail/fairness acceptance. Historical negative captures remain valid.

* Version-only capacity observation

The pool capacity event uses =watch::Sender<()>=. Its payload carries no value
that admission needs. Tokio 1.53.1 =borrow_and_update()= takes the payload read
lock; native owners' =send_replace()= takes the corresponding write lock.
Reselection now calls =mark_unchanged()=, which observes the version without
borrowing payload data. This removes an unnecessary reader/writer dependency.
It is not evidence that this lock caused the above native select tails.

The ordering remains mark, scan live capacity, then await a version change.
A return before marking is visible to the subsequent real-capacity scan; a
return after marking remains a changed version even if delivery precedes await
registration. The test exercises both windows with actual semaphores. FIFO class
heads, capacity-object epoch fencing, cancellation, close and publication
ownership remain unchanged. This refines the same existing model protocol;
there is no new model or claim of OS liveness/latency from finite model checks.

* Architectural consequence and remaining gate

Credit availability describes admission ownership, not whether an owner is
running or when it will resume. A short queue in Scheme cannot prioritize a
request that has not reached Scheme. QoS, queue scoring, GC accounting and
native completion notification address different boundaries; combining them
under one latency claim obscures the actual missing evidence.

The next algorithmic candidate must reduce host-refill-dependent empty pipeline
transitions through bounded owner-resident service production, while preserving
short admission, Scheme cooperative execution and native result/root retirement.
It must reuse existing producer/capacity machinery rather than invent an
independent runtime. This is a candidate, not an implemented or validated fix in
this iteration. It requires an explicit source-of-work/output bound, cancellation
and close protocol, and a same-VM comparison against the current service.

Do not revive the rejected wait-phase boolean hint, infer readiness from free
credits, add polling sleeps/spinning, raise watchdogs, or promote OS priority.
The version protocol and directed native lifecycle checks are closed here;
the throughput/p99/fairness objective remains open. Preserve the negative rows
as the starting control for the next actual algorithm change.
