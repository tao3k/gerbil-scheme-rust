#+title: Signed vectors and identifier ownership qualification

* Scope and baseline

Parent commit: =0a034f0958c4bc839f10c5ee123d9889958a7afa=.
The admitted =scheme/utf8.ss= encoder is unchanged. Generated SCM is
regenerated through the existing build owner; byte identity is not claimed.
This is bridge conversion qualification, not Org parsing performance,
Scheme parsing parallelism, or SMP admission. No kernel or installed SDK
changes are included.

* Official-source implementation and ownership

Signed =s8/s16/s32/s64vector= use the existing sealed native-element
whole-span protocol with the official Gambit representation macros.
Negative values are not converted through unsigned arithmetic or text.
Rust initializes staging, validates type and extent, and publishes only
after successful whole-copy. Old output remains usable on errors.

Identifier packets use the installed Gerbil runtime exports
=string->symbol=, =string->keyword=, =string->uninterned-symbol=,
=symbol->string= and =keyword->string=. The last constructor is important:
=make-symbol= is not used to infer fresh identity. Name equality is not
Scheme identity. An owner-bound =is_identical= operation delegates to
official =eq?=, including references into rooted snapshots.

A private strongly rooted packet holds a complete set of name snapshots,
family tags and a conservative four-byte-per-character capacity bound.
One bulk transfer encodes all selected names into caller-owned storage.
There is no per-name Rust-to-Scheme entry, retained Scheme heap pointer,
JSON conversion, or stable-text cache. Changing rows are encoded on every
request. The existing SIMD UTF-8 validator admits the combined Rust String;
offsets and tags are validated before replacing published output.
Names remain owned and usable after source/packet release and Scheme GC.
Identity remains in rooted Scheme objects, never in copied spellings.

There are two preparation/transfer entries per complete name packet, plus
its one root release. The eight-single-name control performs each sequence
eight times. At source level, a vector input creates three packet containers
(names vector, tag bytevector, packet vector); the eight single-name calls
create those three plus a wrapping vector each time: 32 containers versus
three. Both still perform eight official name conversions and encode all
eight names. This explains the eliminated entry/registry/container work,
not measured allocator bytes or a causal GC duration. No forced GC or
capacity shrink is added to the timed path.

The capacity bound intentionally avoids a second encoding/counting pass.
It can reserve more than the resulting UTF-8 byte length. Both published
and staging capacity are reported, not hidden by shrinking after timing.
ASCII eight-name control/bulk retain 2,776 / 1,264 Rust bytes; reverse-prefix
retain 3,032 / 1,520 bytes. These include storage headers. Signed s64 spans
retain 256 / 512 payload bytes: the bulk protocol costs one additional
transactional span rather than pretending zero-copy ownership.
These are explicit capacity counts, not allocator metadata or per-mode RSS.

* Correctness and regression guards

Signed tests exercise empty, singleton, three-element and 1,024-element
vectors, MIN/-1/0/1/MAX, reused capacity, indexed snapshots, parent release,
GC, and transactional failure. Identifier tests cover empty names, NUL,
ASCII/BMP/supplementary/combining text, mixed kinds, changing shape,
unsupported elements, root release, short capacity, wrong count and
unchanged published output. Repeated interned symbols compare identical;
two equally named uninterned symbols compare distinct after parent release
and GC. The missing-root gensym sentinel must never become a legal symbol.

The dev-only AST guard rejects foreign entries inside Rust element loops
and scalar substitution. It permits owned-data validation loops.
Uninterned construction and identity checks were added after timed matrices;
they do not change timed copy paths and receive final correctness checks.
Rational, complex and hash-table serialization remain explicit open
representation/ownership work, not inferred from these results.

* Scheduling experiment

The separate full Tokio experiment compares default self-tuning global
queue polling with a CPU-budget interval, using identical adaptive host
thread counts, bounded admission and a single Scheme owner. It changes
poll frequency, not channels, Scheme concurrency, or the kernel.

Official Tokio 1.53.1 =runtime/builder.rs:1154-1189= documents the
fairness/synchronization tradeoff and the self-tuning multithread default.
=runtime/scheduler/multi_thread/worker.rs:1341-1368= routes external wakes
through remote injection, while =worker.rs:1420-1427= locks shared state
and pushes a task. A combined wake-to-resume duration does not isolate
mutex wait. This candidate tests the scheduler polling mechanism; no
specific lock-duration reduction is claimed.

The complete seven-corpus, three-load matrix ran 840 batches, 31,080,000
requests, with 20 batches per variant/scenario. The candidate failed
86 of 189 paired-median metric gates. It is rejected and the scheduler
source is restored exactly to the parent version. The benchmark's zero exit
is diagnostic completion, NOT acceptance: its explicit completion marker
is =candidate_all_gates_pass=false=.

Both variants use 12 threads on this host (selected from machine capacity),
24 closed-loop callers, a 12-request bounded queue and one Scheme owner.
Both runtimes coexist and share one owner; this controls setup but is not
a deployment-RSS comparison. Observer rows alone retain 2,560,000 /
25,600,000 / 256,000,000 bytes PER variant across the three loads. At
100,000 requests the two retained variants cost 512 MB decimal before
scratch and runtime memory. Shared peak RSS reached about 634.5 MB;
it is neither isolated candidate RSS nor production queue memory.
CPU/GC per-service observers were disabled identically in both variants;
their zero fields do NOT establish zero GC or zero owner CPU cost.
