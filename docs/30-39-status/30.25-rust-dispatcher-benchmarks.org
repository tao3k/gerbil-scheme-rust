* Reproduction and workload

Run =just bridge-owner-dispatch-benchmark --test= for smoke and
=just bridge-owner-dispatch-benchmark= for the full release-profile matrix.
Redirect standard output and standard error to separate external files. The
bench directory's English README defines the complete boundaries and schema.

Each owner cohort retains exactly the same live Scheme VM state identities across
all cases. One/four native owners each retain four Scheme Actor workers. Direct
uses no additional dispatcher workers; Tokio and Rayon separately use one, two
and four. Each case creates only its own executor, verifies worker-start hooks,
warms on 128 orders, measures, then verifies matching exit-hook identities before
the next case. Setup/retirement are reported outside sample timing. Exit hooks
are not process-wide thread sampling or a Rayon OS-thread join receipt; native
owner joins are separately required at final close.

Tokio tasks submit through the real asynchronous native batch API and await
oneshot delivery without blocking a worker. Rayon performs indexed parallel
submission, then the caller waits on native tickets. The distinct blocking-Rayon
variant is not in this matrix. Parallel stateless submissions do not promise
stateful session enqueue ordering.

Each full sample has 1,024 orders of 48 invoice lines. Windows release 128 orders
with identical owner routes and batch size one or 32; cooperative quantum is one.
Mixed inputs request a 1 ms Scheme green-thread wait every seventh order. Five
rotating forward/reverse blocks produce ten samples per case. All returned totals
and Actor metadata are validated; no phase diagnostics are enabled. Input corpus
generation is outside timing; input cloning, dispatch, native conversion,
execution, projection, retirement and Rust validation remain inside.

* Native capability gate repair

After the matched dispatcher runs, the existing =instance_resources --smoke=
gate failed after its complete native type check. Its panic hook hid unexpected
assertions along with injected Rust panics. Restoring the previous hook for
unexpected panics exposed the exact cause: the reuse test expected the historical
=Native { operation: "native root", code: 0 }= instead of the current explicit
=InstanceError::Scheme= diagnostic. The Scheme source intentionally raises
="injected Scheme task failure"= after GC inside =dynamic-wind=; the native API
consumes that error diagnostic. This was a stale test expectation, not a newly
observed loss of continuations or a reason to downgrade typed error reporting.
Both original failed captures remain outside Git and receive no complete native
acceptance. The repair requires the correct typed exception and injected message;
a generic zero root, unrelated Scheme error or timeout cannot satisfy it. Only
intentional injected Rust panics increment the test's panic counter.

The unchanged six-epoch/128-job gate now passes under =instance-dispatch= with
720 successful tasks, 42 injected Scheme failures and six injected Rust panics.
This short reuse shape injects faults only on owner zero; the dispatcher controls
separately require real Scheme failure/recovery on every owner for all seven
mode/worker configurations. All four owners pass capture, two resumptions across
FFI returns, forced GC, dynamic bindings and multi-shot =dynamic-wind= checks.
Native type checks include nine numeric and four scalar families, Unicode, NUL,
mixed vectors, NaN payloads and signed zero. The post-GC tail live values are
both 4,376,864 raw SDK units. A positive Scheme retention control detects and
then clears 134,219,264 raw units despite zero external roots. All four owners
join with zero roots and removed files; FDs/threads return to baseline. Four
base images remain under the unchanged retention policy and post-close RSS is
nonzero. This bounded gate is not a replacement for the earlier one-hour memory
qualification, arbitrary unload or zero-residue proof. CI now runs this native
capability smoke in addition to the dispatcher smoke and strict Rust lint.

* Fairness and negative conclusions

Least owner progress is the minimum number of completed orders among owners when
the first owner finishes its complete window share. The offered per-owner count
is 128 / owners. A single owner's value 128 is necessarily trivial. At batch 32,
a value zero can mean that another owner has not returned its first batch yet;
it does not establish no internal Scheme progress or starvation. Per-owner p99
vectors and complete sample clocks are retained in the external captures.

For four-owner C, single-item CPU direct has minimum progress 0/32, versus
14/32 for Tokio one worker and 9/32 for Rayon one worker; their throughput and
response tails must also be considered. Single-item mixed direct has 21/32,
Tokio two has 16/32 and Rayon four has 17/32. These burst progress observations
are not a proof of long-running fairness or cross-session service guarantees.
Batch-32 CPU Actor peer minimum is seven throughout C. Mixed Actor peer minimum
is two except four-owner Tokio two, where it is one. In B, four-owner CPU Tokio
two and Rayon four reach six instead of seven. These regressions are retained.

No dispatcher dominates throughput, native tail, delivery tail and fairness:

- Four-owner C CPU batch 32: direct 557,899 orders/s, Tokio four 452,455 and
  Rayon four 517,815. Additional Rust workers do not multiply native VM capacity.
- Four-owner C mixed batch 32: Tokio one has native p99 9.446 ms and delivery
  p99 24.301 ms versus direct 5.357 / 7.073 ms. Rayon two has lower observed
  tails (3.333 / 3.578 ms) but slightly lower throughput than direct. This is
  a cohort observation, not a default-promotion decision.
- B's four-owner CPU batch-32 Rayon one native p99 is 19.270 ms versus direct
  2.944 ms; B's single-item Rayon two delivery p99 is 48.902 ms. C does not
  reproduce those magnitudes, so negative B results remain separate.

Production defaults remain unchanged. The competing-probe =QueueFull= failure,
Python/GIL costs, resident Scheme input placement, arbitrary mutable sessions,
long-term memory growth and general module unloading remain separate gates.
This benchmark has no competing probes and does not repair global admission or
prove zero RSS. Further optimization requires a repeated workload-specific
bottleneck, followed by the same semantic and native acceptance controls.
