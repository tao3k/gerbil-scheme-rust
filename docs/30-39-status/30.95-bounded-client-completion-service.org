* Joint protocol at the actual API

ProgressSchemeTicket::wait_observed_ready is an explicit alternative to the
unchanged wait_observed method. A poll first tries to take exactly one final
Rust oneshot value. A successfully published value can complete before
cooperative deferral. This is a bounded transport operation, not an unbounded
Future or handler running under unconstrained. Empty/closed transport follows
the normal receiver poll, registration and error path. The claim event still
provides an early wake and a single recheck; claim is not a final task value.

The existing InstanceClientProgressDriver provides the service opportunity
before each bulk registration/receive. It drives the same serial short source,
including each original timer and the following native wait. Only the final
receiver's ready read has the new treatment. Timers, bounded admission, bulk
MPSC receive and arbitrary application work retain normal cooperation. A
native completion arriving during one ready bulk turn remains due at the
next service boundary; an indivisible user poll and actual OS scheduling are
still outside the logical opportunity guarantee. No periodic yield or new
threshold is introduced, and no native owner waits for a client acknowledgement.

The diagnostic ready_without_budget bit means an actual already-published
value was taken when the current task had no cooperative budget. It does not
restore the task budget or count an OS resumption. False does not prove that
cooperation was irrelevant elsewhere. A capture with zero such events cannot
claim that this particular fast path explains its performance improvement.
The bit is captured only in the explicit observed ready receive; conventional
receive remains false. Claim and publication traces keep their existing clocks.

Native ownership remains owner-local: before claim, dropping the pending guard
cancels bounded Rust input; after claim, timeout or dropped observation cannot
release native credit or roots. Projection/retirement and owner refill remain
independent of client consumption. Exceptions are task values, and successful
Rust results are not discarded due to separate timing errors. Scheme retains
its complete Actor, green-thread, continuation, GC and exception semantics;
Rust only distributes across the fixed independent instances.

* Incremental source publication without the preparation/registration barrier

** Joint progress and ownership contract

=pipeline_scheme_service_pool_ready_stream= is an explicit opt-in API. It reuses
the existing =Shared= source, =ServiceProducer=, ready-owner channels, capacity
reservation and first-native-entry fence. There is no new task, OS thread,
Scheme scheduler, native lease or source queue. Existing whole-source APIs keep
their registration barrier; their semantics and defaults are unchanged.

The source has two monotonic states: open input and sealed input. Temporarily
empty open input cannot retire a producer registration. Sealed input may still
contain valid published requests; producers leave only after its requests and
offers are depleted and their accepted work retires. Failure seals the source,
preserves the first error, drains unentered requests and prevents late
publication. Publication and failure serialize under the existing request lock;
notifications and application rejection run outside that lock. Publishing wakes
on an empty-to-nonempty transition; sealing and rejecting also wake installed
producers so terminal progress cannot depend on another payload publication.

A preparation window derives from the aggregate configured active count, capped
by source input count. The benchmark therefore uses twelve request envelopes
(four owners times three active slots), with the original eight orders per
envelope. This is an existing capacity boundary, not a new tuning threshold.
Client recovery is offered at a window boundary, not at every item. Declared
work is checked cumulatively across all windows, independent of native work
credits; the existing queue-count limit bounds the entire source and its result
transport. Caller-owned payload bytes and CPU cost still require application
bounds. No callback is preempted or allowed to enter Scheme during preparation.

The existing structured progress driver services producer registration alongside
window preparation, and the caller's existing driver services client recovery.
A blocked later registration cannot prevent publishing to installed producers.
Every bounded window is validated, indexed with its stable global positions and
atomically appended before notification. The final window is followed by seal
and a client-recovery opportunity while outstanding registration completes.
Native progress and root/credit retirement remain independent of bulk result
consumption. This is source preparation/supply overlap, not a guarantee of OS
resumption latency or Scheme handler preemption.

This changes the failure contract of this new API: valid prefixes can enter
Scheme before later input validation or registration completes. Later errors
can therefore follow native side effects. There is no all-or-nothing batch
promise. Cancellation, unwind or partial registration failure uses an armed
source guard created before registration is polled; it cancels, seals, rejects
unentered work and wakes installed producers even before the returned stream
has their weak signal list. Already accepted Scheme work keeps its owner and
drains normally. A single absolute deadline covers all phases.
