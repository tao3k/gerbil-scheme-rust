* Workload and measurement

One fixed-owner Scheme VM runs the original Mailbox business path with four
existing Scheme workers and three transfer frames. The load is one million
planned messages at 1,000,000 messages/s for one second. A separate 1,000/s,
one-second warmup is excluded. A message is the original four-line typed
order, real handler execution and independent result verification. It is
neither an empty ring hop nor an HTTP request. Rust enters the native service
once per measured arm, not once per message.

Latency is the ORIGINAL planned timestamp to real source consumption, including
source debt and worker verification. Histogram buckets report the upper bound
at 1 microsecond resolution. Throughput equals completed messages divided by
elapsed source-cycle seconds. Whole native-call time is reported separately.
Peak backlog is planned-due minus really consumed; it is not Mailbox depth or
an Actor-count limit. Independent maxima must not be treated as one request.

The first three rows retain the same 7F source basis. The two retained control
runs use the same image and reader hashes. Their timing difference is not a
code-optimization gain or regression and has no established machine/GC cause.
The 6D duration/startup/workload differs and is not a direct scaling comparison.
The 12-VM 10.141 ms workload is also a different profile and is not a direct
competitor to this single-VM record.

Zero rejection and clean shutdown do not waive 4,853 > 128. The original native
receipt explicitly fails historical p99 and outstanding-window checks; these
literal failures remain in the structured record. Publishing the record does
not promote defaults, relax acceptance or assert that all future runs reproduce
4.513 ms. At the total peak, at least 4,850 requests are unpublished because
only three existing frames can be materialized; this does not prove which
phase caused the debt. Ring saturation results cannot replace this population.
