#+TITLE: Matched Tokio receive batching qualification — rejected
#+DATE: 2026-10-11

* Decision and scope

The official Tokio =blocking_recv_many= candidate was rejected and removed
from the active benchmark implementation. Production encoding and generated
AOT sources remain unchanged against =fc4562c91af0c8ed81840b5ceaaf40712555e0aa=.
No kernel, SDK, SMP requirement, or acceptance threshold was changed.

This measures UTF-8 bridge traffic, not Org parsing. Twelve Tokio workers
and twenty-four closed-loop callers feed a bounded channel of capacity twelve
on this host. There is exactly one Scheme owner. Rust admission concurrency
is not Scheme parsing parallelism. Worker count follows available parallelism;
these observed counts are not a universal scheduling policy.

* Official implementation and hypothesis

The locked dependency is Tokio 1.53.1. Its =sync/mpsc/bounded.rs= documents
=recv_many= at lines 250–274, with async/blocking entry points at lines 319
and 434. The implementation at =sync/mpsc/chan.rs:340–405= drains available
messages and releases channel permits together. It does not wait for a full
batch. The candidate used that API directly, with a reusable FIFO buffer and
immediate per-request oneshot responses, without adding another scheduler.

This can amortize receiving, but also releases admission permits before
buffered requests reach service. Waiting then moves from admission into the
owner's pending buffer. The observed admission improvement and queue-tail
regression are consistent with this mechanism; the measurements alone do not
attribute every scheduling fluctuation to it.

* Matched experiment

Both variants ran in one process against one AOT image, with identical
encoding, clients, concurrency, queue capacity, and instrumentation. Variant
selection was acknowledged outside timed batches. Each variant received
1,000 warmup requests per load outside measurement. Ten ABBA groups produce
twenty measured batches per variant for each corpus/load combination.

Seven character distributions, 1,000 / 10,000 / 100,000 requests per batch,
and two variants give 840 batches and 31,080,000 measured requests. Independent
receipt counting confirms all 42 groups contain twenty batches, all 42
summaries are present, and content error count is zero. All loads completed
before the performance gate intentionally failed with exit 101.

Per-request timestamps separate admission, queue, service, and response.
Quantiles use exact nearest rank. Acceptance checks the median paired ratio
across twenty batches for wall time and P95/P99 of every phase: nine metrics
per corpus/load, 189 decisions. A ratio above one is rejected, with no
post-result tolerance adjustment. Pooled quantiles below are descriptive,
not substitutes for that matched gate. This is closed-loop load, not an
open-loop overload or production latency SLO qualification.

* Reverse-prefix results

Each total wall time covers twenty batches. P95 and P99 are per-request
end-to-end response latency, expressed in milliseconds. Throughput is
measured requests divided by total timed wall seconds.

For reverse-prefix 100,000, paired wall ratio is 0.992661, but paired
response P95/P99 ratios are 1.052088 / 1.088312 and queue P95/P99 ratios
are 1.607008 / 1.589818. A throughput improvement does not offset those
tail regressions under the retained acceptance rule.

Mixed-text 100,000 paired wall ratio is 1.058834 and response P95/P99 ratios
are 1.094650 / 1.465131. Some other distributions improve, but a universal
receive-batching replacement is not supported. Paired medians and ratios of
aggregate wall totals are different statistics and must not be interchanged.

* Memory and retained baseline

The pending-event vector reserves 480 bytes (twelve Event slots) on this
target. The matched harness preallocates it for both variants; only the
candidate uses batched buffering. At 100,000 requests/batch, retained timing
samples reserve 64,000,000 bytes per variant, or 128,000,000 bytes together,
with another 16,000,000-byte quantile sorting scratch allocation. These are
explicit capacity costs, not whole-process RSS measurements or a claim that
production memory improved. Common client/channel/oneshot costs remain.

The experiment demonstrates a queue-tail tradeoff, not an accepted memory
or throughput optimization. No production change is promoted from it.
The active single-receive path has been restored. Future response-allocation
work must preserve ownership, bounded outstanding work, and immediate replies
and undergo the same matched distribution/load gate.
