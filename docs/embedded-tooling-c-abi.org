#+TITLE: Embedded Gerbil Build and Test API Ownership
#+LANGUAGE: en

* Required direction

The public build/test API belongs to gerbil-scheme-rust and invokes Gerbil
through its C ABI in an admitted, thread-affine VM. A Tokio wrapper around
=Command= is process hardening, not an embedded tooling API. MRR and Weaver
consume this upstream capability; neither maintains a second compiler driver.
=build.ss= declares its PackageSpec, modules and pkg-config dependencies.

The tooling image is a build/test capability. Runtime bindings and application
images remain separate; an application does not acquire a compiler merely by
depending on the value/VM bridge.

| Existing owner | Responsibility |
|----------------+----------------|
| gerbil-scheme-build | Typed build/test session and complete tooling capability |
| gerbil-scheme | Safe VM ownership, rooted arguments/results and linked exports |
| gerbil-scheme-sys / ffi | Checked C ABI, exception containment and host-state boundary |
| gerbil-scheme-aot-build | Bootstrap image, compiler closure and canonical native artifacts |
| Scheme build.ss | Existing package declaration and build semantics |
| Tokio | Outer coordination, readiness, backpressure and cancellation |

Tokio tasks must not move a live Gerbil VM across arbitrary worker threads.
Reuse the existing affine owner/instance mechanisms. Serial access to one VM
does not cap native compiler workers or the host scheduler to one CPU.

* Executing-host build capacity

The AOT owner resolves =std::thread::available_parallelism= when constructing
each Gerbil build command and explicitly injects =GERBIL_BUILD_CORES= into that
child. It does not compile a developer machine's CPU count into an artifact or
inherit a stale CI override. Object compilation and the shared Tokio runtime
use the same host-capacity function; an object batch uses at most its number of
jobs. The root =build.ss= uses Gambit's current =##cpu-count= instead of a fixed
single worker. Package declarations remain in =build.ss=.

A real child-process regression starts with an invalid inherited core value,
checks the injected count against the executing host, and checks object-worker
capacity and the one-job bound. This establishes environment propagation, not
whole-build speedup, successful linking, or completion of remote CI. Existing
resource cleanup, cancellation and wall/idle watchdogs remain unchanged.

* Source audit and actual gap

=crates/gerbil-scheme-build/src/lib.rs= currently implements
=GerbilCompiler::compile_to_gambit= with =Command::new(gxc)=.
=src/package_aot.rs= invokes =gxpkg env gxc=. These are not C ABI build calls.
The existing rooted export and program APIs in
=crates/gerbil-scheme/src/runtime/program.rs=, and private instance export tables
in =src/instances/image.rs=, provide reusable ownership mechanisms. They do not
by themselves load a complete Gerbil compiler and test framework.

=scheme/runtime.ss= explicitly links a reduced module graph for value conversion.
Its successful initialization does not establish compiler, expander, std/make,
package metadata or gxtest availability. The current private image constructor
also explicitly qualifies Darwin; no Linux tooling support follows from that.
Do not relabel that diagnostic image as a portable tooling executor.

The selected Gerbil source provides the existing =defbuild-script= semantics and
=:gerbil/tools/gxtest= =main=. The latter returns success/failure, so a bound
entry need not terminate the host process. The build entry must be bound to the
actual package declaration; do not replace it with a new build language, generic
shell arguments or arbitrary caller-provided eval strings.

* Tooling session contract

The proposed C surface uses opaque, owner-checked sessions and typed structures:

#+begin_src c
GerbilStatus gerbil_scheme_rust_tooling_build(
    GerbilToolingSession *, const GerbilBuildRequest *, GerbilBuildReceipt *);
GerbilStatus gerbil_scheme_rust_tooling_test(
    GerbilToolingSession *, const GerbilTestRequest *, GerbilTestReceipt *);
#+end_src

These signatures specify the required boundary; they are not existing exported
symbols. Checked session admission, cancellation observation and close/join are
also required before this surface is production-ready. Reuse the existing status,
root and exception conventions rather than a second foreign-object framework.

An admitted session binds its image/module closure, ABI, package source cut,
rooted entry points and owner generation before accepting an operation. Build
and test requests are distinct typed operations. Paths, test selection, declared
features and artifact expectations are checked fields, not command fragments.
All foreign requests and results use the existing checked value/root boundary.
Raw Scheme words and borrowed Rust buffers must not escape their owner lifetime.

The session invokes the selected Scheme build/test procedure through a bound
C export. Scheme exceptions are caught before returning through C. A return
status is necessary but insufficient: required artifacts, test inventory and
drain evidence must agree. Cancellation requested, cancellation observed, failed
operation and completed operation are distinct. A timed-out foreign call cannot
be declared stopped merely because its Tokio waiter was dropped. Preserve the
live owner/quarantine until the actual foreign call and any backend work finish.

Package-local parameters, current directory, imports and diagnostics need scoped
restoration. Process-global environment or descriptor mutation is not made safe
by a per-session mutex alone. Audit concurrent host users explicitly. Existing
=ffi/host_io.h= creates private startup streams and restores descriptor slots and
signals; its presence is not evidence that every tooling call, callback and
cleanup path has been checked. Do not use shared =F_SETFL= resets as a repair.

Tooling also creates native backend children. The current host I/O adapter
captures and restores SIGCHLD/SIGINT/SIGTERM. Value-conversion tests do not prove
that Gambit child completion and Tokio child notification coexist under those
restored handlers. Admit that signal/child-wait contract explicitly, including
an unrelated host child exiting during VM setup and a compiler child finishing
during cancellation. A single-VM mutex cannot serialize other host processes.

Initial compilation of the tooling image is bootstrap work owned upstream.
That bootstrap, and native C backend compiler/linker children, may use the existing
source-owned process layer. Public steady-state build/test invocation must not
spawn =gerbil=, =gxi= or =gxtest= as a hidden fallback.

* Validation obligations still requiring evidence

1. Admit the full compiler/expander/PackageSpec/gxtest closure and reject a reduced
   or mismatched image before invoking any entry.
2. Invoke actual package build and both passing/failing test suites through C ABI;
   observe the bound Scheme procedures, not a command-based surrogate.
3. Repeat operations on the same live owner; reject cross-owner roots, reentry,
   stale generations and calls after shutdown.
4. Check host descriptor flags, signals, directory/environment and unrelated
   writers during setup, invocation, callbacks, failure and cleanup.
5. Exercise queued cancellation, an entered foreign call, compiler child failure,
   partial diagnostics and shutdown while native work remains active.
6. Keep real host CPU parallelism. Compare complete bootstrap/cold entry and
   repeated warm calls separately; reduced startup overhead is a hypothesis
   until actual paired measurements establish it.
7. Verify complete outputs and natural owner shutdown under the original budgets.
   No final marker, zero exit code or dropped waiter alone qualifies completion.
8. Qualify supported platform images explicitly. A consumer frozen before this
   capability cannot be described as using it; do not change its pin or copy a
   local implementation to hide that boundary.

These are tooling/ABI obligations. Reuse the existing owner lifecycle formal
model; do not create another policy, budget or execution-authority model here.

* Process-path evidence is separate

The Darwin Cargo incident is independently reproducible at the inherited stdio
boundary: a slow reader can receive truncated JSON despite a zero status, or a
nonzero verbose-build refusal. Native Cargo preserves the complete output. Cargo
must remain the native root while the upstream library drives Scheme. The Tokio
process changes retain bootstrap diagnostics and reap failed children; their
tests do not prove that the embedded build/test API already exists.

Existing dependency version/source/checksum pins remain unchanged. Enabling the
already selected Tokio version with workspace =full= features adds required
feature dependencies; it is not a toolchain or package-version upgrade.
