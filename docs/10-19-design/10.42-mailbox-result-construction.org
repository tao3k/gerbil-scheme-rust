* Whole-cycle ownership and recurring work

Source constructs a fresh native input after obtaining an existing free frame,
sends it to its worker, then consumes a real validated reply before clearing roots
and returning capacity. The worker executes the actual order handler, independent
oracle and immutable id/frame reply. Eager replenishment and both standard Mailbox
deliveries remain. The new change is within Actor execution, after arithmetic and
next-rank, not in the optional observation or error-report path.

The original result suffix allocates a zero-filled s64vector[21], fills five
header fields and loops over sixteen SKU totals. That is 21 initial zero values
followed by 21 field writes at the source level. The result is not observable
until complete, but its allocation must remain AFTER next-rank returns: a retained
rank continuation must create another fresh result on each return. Reusing the
accumulator as the returned object or allocating a reusable result before rank
would break that ownership property. Those earlier counterexamples remain valid.

The implementation factors the original checked suffix into one defrules builder.
The ordinary kernel retains it. The native kernel reads the current scalar fields
AFTER rank, checks that all 21 values are fixnums, and uses Gambit's existing
native s64vector constructor. Any non-fixnum uses the original checked builder,
including valid signed64 bignums and original conversion/type/range failures.
No arithmetic, mutable accumulation, checkpoint, handler or oracle is rewritten.
There is no persistent 18-slot state, pooled result, pre-rank allocation or cached
snapshot across continuation returns.

The installed gsc probe emits BEGIN_ALLOC_S64VECTOR(21), twenty-one element
initializers, END_ALLOC_S64VECTOR and the normal heap check. It creates no list
or foreign buffer and fully initializes the object before returning/exposure.
The actual native kernel has that same atomic construction site; the checked
make/fill loop remains only as its generic fallback. Generated source site counts
alone are not used to assert benefit: the declared 1M/5M input/rank/worker bounds
make all successful normal-profile fields fixnums, and complete native profiles
then validate every actual result through the unchanged independent oracle.

* Where the remaining debt resides

The candidate reports source-pending peaks 6744 at 1M and 4000402 at 5M. Reported
due-unconsumed peaks are 6746 and 4000404. They need not occur at the same instant.
The original source accounting gives, at EACH sampling point:

  due - completed = (due - next) + (next - completed)

The last term is bounded by three physical frames. Therefore the two maxima
can differ by at most three even without matching timestamps. The reused QNT
checks this same source/physical-custody partition; it adds no runtime observation.
This is evidence that the roughly four million requests are mostly unpublished
source ordinal debt, NOT four million payload objects inside Actor mailboxes.
It does not rank CPU phases or prove that adding frames would fix capacity.

The new constructor reduces real repeated work, but the remaining complete-cycle
service rate is still roughly 1M/s under a 5M/s plan. To meet 128 at the final
planned 5M arrival requires at least 4999872 actual consumptions by that time,
plus valid pause/recovery and per-request bounds throughout. Zero rejection with
seconds of drain is not production admission. The next structural cost case must
address this full-cycle deficit; changing the benchmark window, offering less
work, increasing queue capacity or attributing it to the machine is not a remedy.

An eligible future handoff direction must remove a recurring request-delivery or
park/wake operation while preserving eager replacement and exact source retirement.
Simple slot routing alone does not establish that saving, and the rejected
ready-first packet loop must not be restarted. Active-worker refill needs an
explicit atomic claim-versus-park protocol, truthful Actor affinity, fully
initialized publication, mandatory consumption of any queued wake token, and
exception/continuation/close draining. No new runtime handoff scheme is implemented
or claimed profitable in this result-construction experiment.

** Isolated one-shot capture design and admission

The proposed record is scoped to one isolated owner, one invocation
generation and one claimed gap. It carries the existing planned and
verified-progress epoch, a source phase and scalar frame identities.
A recovery seals the record only on a subsequent publication for an
idle-source gap, or on actual frame retirement for a held-credit gap.
A verified-progress write alone cannot seal it. A mismatched generation,
duplicate recovery, timeout or close cannot reopen a sealed record.
Publication/readout must occur on the owner or use an explicitly owned
scalar snapshot. Close invalidates the record and joins its reader before
dropping any borrowed state. Formatting and projection are outside the
measured call.

The onset classification requires these independent facts:

| Hypothesis | Needed trigger witness | Needed recovery witness |
|------------+------------------------+-------------------------|
| Zero-active source yield | No live frame, source at yield, due ordinal | Actual subsequent publication |
| Actor not started | Same live generation still queued | Worker entry followed by retirement |
| Ready but not sent | Ready generation and positive pre-enqueue evidence | Delivery followed by retirement |
| Reply still in Mailbox | Same immutable reply shown present at the trigger | Matching dequeue, then credit return after frame clearing |
| Reply already dequeued, credit held | Same ordinal already dequeued at the trigger and credit still held | Credit return after frame clearing |

A ready tag with an empty inbox cannot alone prove pre-enqueue; the
receiver may already have dequeued the reply. A snapshot acquired only
after a threshold is crossed cannot reconstruct the onset if a worker
or source advanced in between.

The existing runtime Mailbox read primitive advances or rewinds the
calling thread's cursor. It is not a read-only foreign snapshot of
another green thread's inbox. Calling it in the receiver's turn can
change the receive path, and a concurrent private inbox read has
neither a lifetime nor a synchronization guarantee. A lock-based probe
would also charge an unbounded wait to the boundary it is measuring.
Capturing a source safe point after the gap avoids the foreign access
but can miss the state change that decides the hypothesis. Maintaining
breadcrumbs at every publish/receive/retire would add recurring work,
outside this experiment's budget. No admitted implementation provides
both captures with only bounded one-shot work on the unchanged image.

The QNT cases check identity, actual recovery versus verified progress,
sealed/closed behavior and the distinction between ready and observed
delivery. They do not certify a runtime capture or an observation
overhead. The one-shot execution gate remains unmet, so no diagnostic
or workload was launched and no runtime code was changed.

** Separate the idle source edge from post-retirement refill

In op62 the positive-active arm validates the returned reply, releases
its frame and decrements active capacity. Control then goes directly to
the next drive iteration, which samples due work and scans free frames.
There is no explicit yield between retirement and that refill pass.

can yield based on an earlier arrival sample. If a request becomes due

an arrival immediately after the recheck would still have no wake edge.

of idle-source onset. A qualifying capture must distinguish the
zero-active arm from the receive arm, and identify publication of the

** Post-seal ordinal and peer state ownership

Only the source writes a slot ordinal at publication, retirement
and stop cleanup. Between the deadline check and the isolated
post-seal read, that source does none of those actions. The
ordinal tuple therefore remains valid through that interval.
Peer worker state is different: a worker writes running and
ready, and the seal copies the existing ten-million-bin histogram
before the ordinal read. A peer may progress during that interval.
Reading a peer's ready tag after the copy cannot show it was ready
at the deadline, even though its ordinal is unchanged. A ready tag
also precedes send. Retain the post-seal ordinal witness only for
request identity and occupied routes, and leave contemporaneous
peer state and inbox custody unknown.

Its receipts would cover only that first request. The retained low-rate

22.904542 ms from a later consecutive verified-progress interval of

** Reply-only wait with spare source credit

The retained forced deadline fixture offered 12 requests. At the
seal only four had been published, three retired, and one frame
remained charged. The source enters blocking receive whenever
active is positive, irrespective of spare capacity. In the fixture,
the next eight planned arrivals did not wake the source while it
waited for the delayed reply. This is a demonstrated supply
dependency under a forced worker delay. It does not establish that
the natural 57 ms gap or historical peak had the same cause.

A separate candidate can retain immediate refill and wait for
either a reply or the next eligibility time only when spare credit
exists and another arrival can become eligible. The fully occupied
path has no reason to wake on arrival. The wake must not return
credit, reset the existing completion-wait deadline, or shift the
offered schedule. For fractional rates the eligibility time needs
the inverse of the existing due count, not the floor-rounded
planned latency timestamp. A timeout wake and a real reply must
remain distinct. This direction needs a monotonic wait contract and
a generated-code cost gate before any integration.

** Arrival wake clock and deadline constraints

In the local Gambit source cache, a positive relative receive timeout
is converted to an absolute point using the processor's current-time
primitive. The frozen 7F image's current-time routine calls
=clock_gettime= with Darwin clock ID 0 (=CLOCK_REALTIME=), and its
separate monotonic routine calls =mach_absolute_time=. The source
arrival loop uses =CLOCK_UPTIME_RAW=. A relative numeric receive
timeout therefore does not by itself supply a monotonic guarantee
for the arrival edge. A recheck after waking can reject an early
wake, but it cannot bound a wake delayed by a backward wall-clock
change. The local source cache is newer than the frozen Gambit, so
the source inspection does not qualify the entire frozen wait path.

An arrival wake also must retain the original outstanding reply
deadline. Starting a new full receive interval after every arrival
can delay failure indefinitely. The source's next eligibility
clock is the ceiling of ordinal times the time unit divided by
rate, whereas the planned latency stamp uses the floor. These
coincide for integral periods but differ at fractional boundaries.
The regression tests retain both distinctions. No runtime wait
candidate or workload was executed.

** Existing timer cannot own the spare-credit arrival

The private Darwin SDK image already has a monotonic timer thread
in =ffi/instance_timer.h=. Its deadline and period implement the
image's =ITIMER_REAL= contract. It raises an SDK heartbeat, using the
existing masked and pending state. It does not publish a source
arrival to the Actor Mailbox or carry a request or wait generation.
An arrival deadline may be earlier than the heartbeat, but
overwriting the timer would also replace its period and notification
contract. A heartbeat interrupt alone does not make a reply-only
receive return a typed arrival result.

Reuse the monotonic deadline arithmetic as prior art, but keep
heartbeat ownership distinct. A compatible spare-credit wake needs
a source-owned, cancellable wait generation and an event that returns
control to the existing supply turn. It must keep the original reply
deadline and avoid recurring timer work on the full-credit path.
The existing timer does not qualify this candidate. No runtime
implementation or performance run was started.

An isolated public Gerbil Mailbox fixture verified the receiving
half of a typed arrival wake. The source discarded an old-generation
token, accepted the current token, and dispatched a second request
while the first worker was still held. Only actual replies returned
the two frame credits, and both workers joined. The fixture uses
controlled delivery, not a monotonic timer or an op62 workload.
It is retained under =.ci/op62-one-shot-boundaries/spare-credit-wake=.

Generation matching does not bound notification occupancy. If a stale
token owns the only notification slot, a fresh arrival can be blocked
even though it has a distinct generation. The source must consume the
old token and recheck the current monotonic eligibility before parking,
or the producer must atomically replace the pending slot under a
qualified protocol. The new QNT case records this failure shape;
the isolated fixture does not qualify either timer implementation.

An isolated Darwin C fixture demonstrated the sending-side rearm
contract. The old generation was already waiting on a three-second
deadline. Under the same mutex the source replaced it with a new
generation due in ten milliseconds and signaled the condition.
The notifier rechecked =CLOCK_UPTIME_RAW= after the relative wait,
delivered only generation two after its own deadline and before
the old deadline, then closed and joined. The fixture is retained
under =.ci/op62-one-shot-boundaries/monotonic-rearm=.

This verifies cancellable clock waiting under the forced ordering.
It does not connect the notifier to the Scheme Mailbox, measure
timer overhead on a workload, or establish a latency upper bound.
The remaining transport obligation is to carry at most one
pending wake without allowing a stale token to strand eligible
source work.

The standalone notification-slot fixture combines the existing
monotonic rearm test loop with a nonblocking one-byte pipe. The
byte is a readiness hint; the latest due generation is scalar
state under the same mutex as publication and acknowledgment.
Generation one remained unread while generation two became due.
One read drained exactly one byte and acquired generation two.
After the acknowledgment, generation three created a fresh byte.
Close woke and joined the notifier before closing descriptors.
The fixture is retained under
=.ci/op62-one-shot-boundaries/notification-slot=.

Reading the generation and acknowledging the byte in separate
transactions can lose a wake if a new generation becomes due
between them. The regression retains that interleaving. The C
fixture uses asserted I/O and tests only the successful transport
path. It does not qualify pipe error handling, Scheme port
integration, or steady-state workload cost.

The isolated port bridge connected the native notifier to the public
Scheme port and Mailbox. The C thread published only the pipe byte
and scalar generation. A Scheme observer read the port and sent the
typed arrival to the source. Generations one and two arrived in
order. Close joined the notifier, then the observer observed EOF and
joined before the port closed. The fixture is retained under
=.ci/op62-one-shot-boundaries/port-bridge=. Gambit generated the C
objects; the standalone default link failed on Darwin libc symbols,
and the existing system linker policy linked those objects.

The fixture arms the next generation only after the source receives
the previous token. It does not establish a bound under concurrent
cancel and rearm. A one-byte pipe alone does not bound the number of
forwarded Mailbox tokens if the observer acknowledges the pipe before
the source takes the forwarded token. A QNT counterexample retains
this distinction. Source acknowledgment must cover the entire
forwarding boundary for that interleaving. No performance test ran.

The follow-up isolated fixture moved acknowledgment to the source.
The Scheme observer forwards only a generic arrival token; the native
pending bit remains set until the source takes that token and reads
the latest generation under the notifier mutex. The fixture forced
generation two to become due after generation one's token had reached
the Mailbox but before the source took it. One token covered both
generations; the source observed generation two and found no second
token. Generation three published a fresh token after acknowledgment.
The notifier and observer both joined. Test-only polling forced the
ordering; it is not part of the proposed runtime protocol.
The fixture is retained under
=.ci/op62-one-shot-boundaries/source-ack=.

This closes the tested coalescing interleaving across the port and
Mailbox. It does not qualify hard I/O errors, a canceled generation
racing with close, or cost on the spare-credit path. No op62 or
