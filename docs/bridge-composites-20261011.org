* Library protocol, not benchmark-only support

=number_batch= takes a whole span of rooted component pairs. Scheme uses
official =/= or =make-rectangular=; rational construction requires exact
integers and nonzero denominators. Reduction, sign normalization, exactness
and real/complex collapse remain Scheme semantics. No text or f64 coercion
implements the number tower. Both batch construction and snapshot use one
whole-span foreign entry, not per-component Rust FFI.

=copy_number_components= retains alternating numerator/denominator or
real/imaginary references in one strong vector snapshot. It selects official
accessors once, writes directly into the destination vector, and avoids one
temporary two-element vector per input number. Exact bignums and rationals
remain Scheme objects and can use existing canonical binary integer APIs.
These references are NOT detached Rust integers or recursively serialized
values. Borrowed parts cannot outlive the snapshot; strongly rooted
=root_element= can survive snapshot release within the runtime lifetime.

=hash_table= constructs strong Gambit tables using explicit =eq?=, =eqv?=
or =equal?=. Duplicate keys follow that equality and last value wins.
Weak keys/values are deliberately excluded from this ownership protocol.
=copy_table_entries= preallocates one vector and uses official
=table-for-each proc table=, whose callback takes key and value. It does not
materialize an alist or sort the table. Ordering is unspecified; snapshots
are shallow and preserve identity and nested reachability, not deep-copy
semantics. This does not claim all Gerbil HashTable implementations or
arbitrary downstream POO objects have a serialized Rust representation.

Installed official source: =src/gerbil/runtime/hash.ss:75-76= delegates
Gambit table traversal to =table-for-each proc table=.
=src/gerbil/runtime/c3.ss:79-83= uses the three equality choices with
=make-table=. The existing registry uses the same official strong table
contract. Native SDK execution separately confirmed rational reduction,
complex components and callback arity.

Snapshot output is replaced only after a positive root, checked length
and complete even component count. Errors preserve the prior root. The
owner-local raw ABI requires valid readable root-ID spans and writable
metadata; it never retains Rust pointers. Positive tokens, not Scheme
word zero, identify registry roots. One output root retains all components
after releasing the source and forcing GC. Rust handles remain non-Send
and bounded by the runtime lifetime.

* Complete matched conversion matrix

Three families, loads 1,000/10,000/100,000, 20 batches per variant, ten ABBA
groups: 360 batches, 13,320,000 requests, eight objects or entries/request.
Five changing rows rotate each request. Numerical fixtures use exact
fixnum components; inexact and arbitrary-precision correctness is tested
separately, not inferred as their performance from these fixtures.

Both variants snapshot the SAME complete source first and validate the
same 16 fields, with no per-request Rust validation allocation. Control
then independently roots each field using the public element-root API;
bulk borrows the single rooted snapshot. This measures avoiding repeated
root registration/release, not an old rational/table implementation that
did not exist. Constructor setup and root-pair Vec allocations are outside
timing. Therefore these numbers do not qualify fresh-table construction or
a detached Rust serialization workload.

All nine gates passed total wall, pooled individual-request P95 and P99.

and scalar validation calls are included. They are not percentiles of

* Scheduling and final qualification

A separate candidate reserves one CPU budget for the synchronous owner
using =max(1, available_parallelism - 1)= Tokio workers. It is explicitly a
testable policy, not official proof of an optimum. Official Tokio 1.53.1
=runtime/builder.rs:477-519= documents that worker count defaults to available
cores and is configurable. Remote injection and lock paths are unchanged;
this candidate tests competition/runnable delays without replacing channels
or claiming measured mutex duration. Admission capacity and closed-loop
callers remain matched, with one Scheme owner and no parsing parallelism.
The complete seven-corpus matrix ran 840 batches, 31,080,000 requests and
20 batches per variant/load, with matched admission capacity and callers.
It failed 121 of 189 paired-median metric gates. The candidate is rejected;
the scheduling source is restored exactly to the parent. A zero diagnostic
exit means completion, not acceptance; =candidate_all_gates_pass=false=.

Both runtimes coexist; the host uses 12 versus 11 Tokio workers, with
24 closed-loop callers, capacity 12 and one shared Scheme owner. Rust queue
concurrency is not Scheme parsing parallelism. The 16-u64 observation rows
retain 2,560,000 / 25,600,000 / 256,000,000 bytes per variant at the three loads.
At 100,000 requests, the two variants retain 512 MB decimal before scratch.
Shared peak RSS is about 634.5 MB, not isolated per-variant memory. This
method tests worker scheduling, not a lower deployment-memory guarantee.

Per-service CPU/GC wake observers were disabled identically. Zero fields
therefore mean not collected, not zero owner CPU/GC. Process CPU, handoff,
parks, context-switch and high-water RSS counters remain in the raw log.
Wake-to-resume duration still combines synchronization, injection and
runnable delay; no exact mutex-wait duration is inferred from it.

1,108.944 ms, pooled response P99 from 722.917 to 1,168.792 µs, and throughput
fell from 105,973 to 90,176 requests/s. A smaller worker pool did not give a
uniformly better owner/response scheduling balance. Default Tokio policy
remains intact; no admitted scheduling speedup is claimed.
