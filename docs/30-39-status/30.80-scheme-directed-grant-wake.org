* Evidence and protocol

ABI23 corrected premature execution acknowledgement, but its matched capture
still regressed mixed short p99 and CPU owner completion spread. The native
budget selects one Scheme waiter while broadcasting to every registered waiter.
This is a concrete notification amplification mechanism, not proof that it is
the unique cause of wall-clock tails or cross-owner imbalance.

ABI24 preserves class selection, FIFO within each class, work bounds, immutable
specialized layout plans and receiving-thread first-grant settlement. Only a
contended acquisition creates a waiter with its own condition variable. The
existing budget mutex protects registration, selection and the wait predicate.
Selection records the owner before signaling that waiter's event. The receiver
checks actual ownership before acknowledging execution or copying permission.
A notification cannot acknowledge execution on behalf of another thread.

| Boundary | Ownership and lifetime |
|----------+------------------------|
| Uncontended acquisition | Existing direct path; no waiter/event allocation |
| Contended registration | One acquisition owns a thread/event pair in its class FIFO |
| Selection and notification | Pop one waiter; record its owner; signal its private event under the budget mutex |
| Receive/recheck | Atomic unlock-and-wait plus ownership predicate; spurious wakes do not grant execution |
| Suspension/reentry | Release the lease; subsequent acquisition has a fresh notification lifetime |
| First execution receipt | Existing Scheme ticket settles once; replay cannot settle twice |
| Terminal result | Existing independent result root and capacity retirement |

The private event is not a shared single-signal replacement: signaling an
arbitrary waiter on the old shared condition could leave the selected owner
asleep. No thread/event registry retains completed workers. Retained Scheme
continuations may retain their lexical state under ordinary GC. The queue
entry is removed at selection; its native event has no explicit OS handle
requiring Rust destruction. Additional allocation on contended acquisitions is
a cost to measure, not a claimed free optimization.

Rust timeout/cancellation abandons an observer, not an accepted Scheme worker.
Close drains selected and registered work through existing native completion
custody before joining. Externally terminating Scheme worker threads is not a
supported cancellation operation. Lock order remains service then budget;
selection adds no callback into the service mutex. A late arrival does not
revoke an already assigned grant or promise instruction-level preemption.

* Existing Runtime model refinement

The same model now separates selected waiter/notification from actual receiving
grant. Outstanding short execution debt survives selection and notification.
The selected worker owns the notification; an unrelated wake cannot consume it.
Close preserves this custody until execution/result drain. Mutation controls
reject a notification delivered to an unrelated waiter. Existing registration,
cache invalidation, replay/exception and root/capacity models remain controls.
Finite safety checks do not establish OS wake latency or starvation freedom
without progress assumptions.
