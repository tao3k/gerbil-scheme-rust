* Ring and business workloads must remain separate
The current example accepts a thread population parameter. With its default
round calculation m=floor(1000000/n), one go token makes n*m hops. This is not
necessarily one million when n does not divide one million. The timed transfer
region also includes neighbor delivery, thread starts and final join; it is not
an isolated steady-state service loop. Thread creation and the outer total time
have different scopes. The 2006 paper describes another ring measurement.

actor_service_calculus now makes population-dependent setup an explicit abstract
cost input. Its illustrative equation is not an exhaustive native cost model:
GC, scheduling and shutdown costs must still be accounted for where applicable.
Ring hop CPU averages cannot establish offered business capacity, end-to-end
p99, rejection rate, memory residency or a per-request fairness guarantee.

* Full-cycle optimization decision
The existing ownership chain remains:
planned arrival -> construction -> request enqueue -> Actor execution -> reply
enqueue -> source dequeue -> independent validation -> real frame return ->
immediate refill. Each intermediate position may carry live work; shifting its
name or releasing a credit early cannot reduce that work.

Resident Actors, runnable Actors, selected execution, charged frames and
completed-but-unconsumed results are distinct quantities. More resident Actors
can expose independent state and suspension opportunities, but do not increase
the CPU service budget of one owner. A valid scaling proposal must name the
suspension it overlaps and pay for construction, stack/continuation retention,
Mailbox traffic, validation, consumption and final lifecycle cleanup.

No extra completion FIFO, sleep registration layer or per-message probe is
introduced. The next candidate must eliminate an operation actually retained
in this application cycle and its matched generated code; it must not merely
move bookkeeping across a yield. No such runtime saving is certified here.

At one million planned messages/s, 128 messages represent 128 microseconds of
unserved arrivals when there is no compensating service. This is a necessary
budget sanity check, not a universal pause bound: already outstanding work,
bursts, service completions and spare recovery throughput must enter the bound.
A p99 observation alone cannot imply a maximum-backlog guarantee. The existing
service calculus requires an independently justified service curve and request
fairness before a delay bound is applicable. Those native timing assumptions
remain unknown; finite protocol checks cannot manufacture them.

* Model limits, counterexamples and regression wiring
mailbox_primitive refines one existing single-consumer Mailbox. Message IDs are
logical occurrence labels; OBJECTS permits aliases to the same payload. The
model is not a restriction on Scheme payload types or a second scheduler.
A caller supplies processor selection; mailbox_reply_refinement couples that
selection to the canonical Actor lease and request-credit state.

Protected queue mutations are atomic model steps. Other interleavings are
conservative source-level possibilities, not claims that every race is reachable
in the current single-owner SDK build. Closing the primitive means the library
has stopped admission after draining; it does not assert that Gambit thread-send
rejects every dead thread. Actual service termination/join remains a separate
canonical obligation. Memory units in actor_population are abstract ownership
budgets, not bytes or RSS. No unbounded liveness or scheduling-time proof is claimed.

Two explicit unsafe mutants retain the protected-recheck and mandatory-signal
counterexamples. Additional research-gate factors forbid treating wake as CPU,
dequeue as credit return, raw FIFO as a selective protocol, or ring averages as
business p99 without repairing their proof obligations. These are mechanism
counterexamples, not newly observed runtime failures.

An initial integration test incorrectly wrapped a multi-step action together
with a single other-module stay. Intermediate states then left that module
undefined. The test was repaired with explicit preservation at every microstep;
no native protocol or safety invariant was weakened. Earlier pinned-route test
errors and the Quint trace-recorder failure remain in the prior refinement note.

* Executable CPU / pause obligations (subsequent refinement)
The existing actor_service_calculus now includes cpuWorkFits, debtCuts and
pauseFits. These are projections and necessary budget checks, not another
Actor lifecycle and not measured native costs. Lifecycle, wake eligibility,
selection and real per-result credit return remain in the canonical models.

- cpuWorkFits charges source, construction, sends, execution, independent
  validation, consumption, observation, actual dispatches and extra setup to
  ONE non-SMP processor. Actor population does not divide those CPU costs.
  The paper's lightweight threads can expose independent state and overlap
  suspension; this does not certify zero creation/stack/GC cost or parallel CPU.
- debtCuts checks same-run prefix conservation and records peak outstanding
  arrivals minus REAL consumption. An eventually drained run and identical
  final message counts can have peaks 65 and 129. End-of-run throughput cannot
  certify the 128 constraint. The projection cannot authenticate counter labels:
  its consumed input must come from canonical real consumption, never wake,
  publication, receive or progress-heartbeat counters.
- pauseFits includes initial debt AND arrival phase. At a one-microsecond
  period, an empty-debt 128-microsecond no-consumption interval just fits at
  phase zero; 129 microseconds fails. Starting at debt 127 or another phase
  leaves less room. These are conditional arithmetic witnesses, not measured
  pauses, scheduler deadlines or permission to alter the waiting protocol.
- Lower steady CPU work does not establish a bounded next consumption
  opportunity. A 129-message peak cannot be undone by a later recovery window.
  The existing service-curve and per-request fairness obligations still apply.

The cost suite adds five executable checks for these distinctions. Its abstract
numbers are illustrative witnesses, not fitted phase costs or a proof that a
specific native wait caused the observed peak. Bounded tests do not prove
unbounded scheduler fairness, GC pause duration or current performance.

* Concrete optimization boundary and retained ABI counterexample
The currently examined two-entry consume/progress bridge is still an isolated
static question, not a Mailbox implementation change. Its isolated same-SDK
GCC -O2 gateway has an 80-byte generic C entry frame versus a 96-byte fused
entry frame. The sequential original entries do NOT imply a 160-byte peak.
The ordinary bound-provider call structure can fall from ten native calls
across two entries to three in one entry; full op62 caller costs, Scheme frame
saves, code size, fallback cost and actual VM evidence are not yet established.
No complete-cycle gain or runtime integration follows from these counts.

The isolated prototype exposed a real C-interop construction error before any
VM execution: ___return jumps out of generated C glue. An unconditional VOID
return after side effects would replay the old transaction; returning inside
the SDK result-conversion bracket would skip release of its foreign pin.
The prototype now assigns the result, completes the SDK conversion/root/release
protocol, and returns once. mailbox_consume_abi retains both counterexamples,
two original clock samples, histogram-before-progress ordering, original errors,
Scheme-owned frame return, pointer lifetime and the failed-control gate.
Unsupported inputs decline before effects or carry the already sampled clock
into the unchanged arithmetic suffix; they must not resample or replay effects.
Input progress conversion also moves before the first clock in this prototype:
positive S64 progress must be proved by the caller, or invalid-input exception
ordering would differ. This remains an explicit integration precondition.
