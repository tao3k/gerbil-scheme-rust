* Direct source probes and their limits

=runtime/scheduler/multi_thread/worker.rs::push_remote_task= is instrumented
at lock request, acquisition and immediately before unlock. Five atomic
statistics record count, total request-to-acquisition ns, total
acquisition-to-before-unlock ns and cumulative maxima. Statistic updates
execute AFTER releasing the guard. No additional lock guards the probe.
Wait includes lock acquisition CPU and any preemption; hold includes the
timestamp read and any preemption while holding the lock. Neither is a
pure uncontended instruction-cycle measurement. Unlock and parked-worker
notification are outside the measured hold interval. Other acquisitions
of =shared.synced= (e.g. dequeue/idle management) are not directly probed.

The original official worker source SHA-256 is
=b7860cfa69f197eb52f3374a1cf0fe6adc2ff82a6971d8d27985fea65c08d94c=.
The isolated diagnostic patch contains the exact source probe,
owner timing, manifest override and Justfile entry. To reproduce, create
an archive as =repo/= beside the cached source copy as =tokio/=, apply the
patch from their parent and run =just bridge-lock-profile= inside =repo/=.
The isolated lockfile resolves offline; it never replaces the production
lockfile. Reverse =git apply --check= validated the archived instrumentation.

Owner receive wall time brackets =blocking_recv= only. Native
=CLOCK_THREAD_CPUTIME_ID= reads bracket that operation, without process
statistics or Scheme GC reads. The CPU window also contains the wall clock
reads, so very short intervals can have CPU greater than measured wall.
Raw CPU and wall totals remain separate; wall-minus-CPU is published only
for explicitly counted comparable intervals. It is NOT summed with lock
wait: receive includes capacity-return wake work, so intervals overlap.
Receive intervals starting before the batch's epoch are excluded to avoid
counting report generation and interbatch idle time as request waiting.

* Source-guided coalescing candidate, not a new scheduler

Tokio =runtime/task/state.rs:253-279= coalesces notifications of already
notified/running tasks; idle independent caller tasks require separate
remote submissions. Official =futures-util 0.3.34=,
=stream/futures_unordered/task.rs:102-126=, queues a ready child only once
and wakes its parent. This existing ecosystem implementation can expose
many independently pending calls through one normally scheduled task.

The candidate uses one =tokio::spawn= coordinator on a host worker, with
24 independent caller futures in =FuturesUnordered= instead of 24 spawned
caller tasks. Same bounded mpsc, same one-per-request oneshot, same owner,
same per-caller sequential requests and changing payloads. It does not
poll callers on =Runtime::block_on='s external calling thread. Replies are
processed when ready, not retained for a response batch. No hand-written
ready queue, wake protocol, thread-affinity workaround or unsafe Scheme
cross-thread sharing is introduced. Both modes use the same caller body
and disable per-request CPU/GC/wake observers during acceptance.

* Candidate lock diagnostic and final checks

The isolated coalesced candidate completed all 420 batches for seven corpora,
three loads and 20 batches. It is temporally separate from the baseline
profile, not an ABBA speed comparison. Its role is to check injection-event
counts and scoped lock/receive intervals; only the uninstrumented matched
matrix above decides adoption. Complete candidate diagnostic,
complete isolated candidate probe patch. Reverse application checks
confirm this second archived patch matches the executed isolated sources.

For mixed text, baseline / coalesced injection events/request were
2.0064 / 0.5349 at 1,000; 1.9948 / 0.5357 at 10,000; and
1.9963 / 0.5714 at 100,000. The candidate's request-to-acquisition / hold
means at 100,000 were 0.199396 / 0.086127 µs/event. These separate runs
support the expected coalescing mechanism, not a paired wall-speed claim.
Candidate receive wall / CPU means were 2.210714 / 0.545929 µs/receive;
their unequal windows still prohibit indiscriminate subtraction. Candidate
diagnostic peak RSS was 78,315,520 bytes with batch-discarded observations,
not comparable to the acceptance harness's retained-history RSS.

The scoped evidence now rules out "the lock is still unmeasured" for the
remote push interval. It does NOT explain every long response outlier or
measure all scheduler lock sites. We have reduced remote injection events
in a prototype, but have not admitted a general-purpose faster scheduler.
The working checkout contains no rejected transport/dependency change.
Post-rollback =just bridge-workspace= passed 659 tests, zero failures,
eight existing ignored tests. =just bridge-actor-lint= and =just bridge-lint=
passed with warnings denied. Raw receipts are
=benchmarks/20261012-lock-owner-final-*.log=. The rejected code patch
passes =git apply --check= against the restored checkout. Production
source/manifests/lockfile have no diff against the frozen commit. README
and the evidence index now point to these scoped results. Exact-head
remote CI and downstream Org acceptance remain separate gates; no Scheme
SMP pass or net scheduler speedup is claimed.
